# SIEM与SOAR
> 关键词:SIEM,SOAR,安全信息与事件管理,安全编排自动化响应,ELK,Elastic Security,Splunk,QRadar,关联规则,Playbook,剧本,封禁IP,隔离主机,MTTD,MTTR,检测覆盖率,奇安信,绿盟

## 一、SIEM 概念与架构

SIEM(Security Information and Event Management,安全信息与事件管理)整合**日志管理(SIM)**与**安全事件管理(SEM)**,实现对安全数据的集中收集、关联分析与告警。

### 1.1 核心能力

- 日志集中与归一化:异构日志统一接入、标准化(见《日志管理与分析》)。
- 实时关联分析:跨日志源关联,发现单条日志看不出的攻击链。
- 告警与响应:按规则生成告警,推送工单/通知。
- 检索与取证:历史数据快速查询,支撑调查与审计。
- 报表与合规:出合规报表(等保日志留存、审计证据)。

### 1.2 标准架构(采集-归一化-关联-告警-存储)

```
数据源(网络/主机/应用/云/安全设备)
   ↓ 采集(Agent / Syslog / API / 流量)
[采集层] → 缓冲与队列(Kafka/Redis)
   ↓
[归一化层] → 解析、标准化、字段映射、富化(威胁情报/资产信息)
   ↓
[关联分析层] → 规则引擎(阈值/关联/频率/统计)、UEBA、ML 异常检测
   ↓
[告警层] → 告警生成、分级、去重、上下文丰富
   ↓
[存储层] → 热/温/冷分级存储,检索与归档
   ↓
[消费层] → 仪表盘、报表、工单、SOAR、威胁狩猎
```

## 二、主流 SIEM 产品

| 类别 | 产品 | 特点 | 适用 |
|------|------|------|------|
| 开源/自建 | ELK + Elastic Security | 灵活、生态大、成本低(需自运维)、KQL 检索强;Elastic Security 提供检测引擎、EDR 联动 | 有运维能力的团队 |
| 商业国际 | Splunk | 检索与分析最强(SPL)、生态成熟,许可成本高 | 大企业、合规要求高 |
| 商业国际 | IBM QRadar | 关联规则成熟、SOAR(编排)内置能力强 | 金融、电信 |
| 商业国际 | Microsoft Sentinel | 云原生、与 Azure/365 集成好、KQL 查询 | 微软云环境 |
| 国产 | 奇安信(态势感知/安全运营平台) | 国内合规适配好、与国产设备联动 | 政企、等保合规 |
| 国产 | 绿盟(安全运营平台/ESM) | 国产生态、报表合规 | 政企、行业 |
| 国产 | 深信服、安恒、天融信等 | 各自生态与行业案例 | 按行业选择 |

**选型要点**:

1. **数据接入能力**:能否覆盖你已有的日志源与格式(设备型号、云平台、国产设备)。
2. **查询与规则能力**:检索速度、规则语言易用性(对比 SPL/KQL/自定义 DSL)。
3. **扩展与成本**:按数据量计费的许可模式、扩容成本、运维人力。
4. **合规适配**:等保、数据安全、行业监管要求(国产化要求时优先国产)。
5. **生态与 SOAR 联动**:与现有 EDR/防火墙/工单系统集成深度。

> 经验:**先小规模 PoC(选 3-5 类核心日志)再全量建设**,用真实数据验证查询性能与规则命中,避免"买了大平台却只有少量日志"。

## 三、关联规则设计

### 3.1 规则分类

| 类型 | 逻辑 | 示例 |
|------|------|------|
| 阈值规则 | 指标超过阈值触发 | 5 分钟登录失败 ≥10 次 |
| 关联规则 | 多事件按条件关联触发 | 爆破失败后同源成功登录 |
| 频率规则 | 时间窗口内事件频率异常 | 1 小时外联 >50 次 |
| 黑名单规则 | 命中 IOC/信誉库 | 外联已知 C2 IP |
| 统计/基线规则 | 与历史基线偏离 | 该资产流量高于 30 天均值 3σ |
| 行为规则 | 特定行为序列 | 创建新账号→加入管理员组→登录 |

### 3.2 关联规则编写要点

- **明确的触发条件与时间窗口**:窗口太短漏关联,太长误报多,建议从 5-30 分钟起步。
- **字段质量前提**:规则依赖的字段(源/目的 IP、账号)必须归一化完成且填充率达标。
- **关联要有业务意义**:关联结果要能回答"这说明什么攻击阶段",而不是为关联而关联。
- **抑制与去重**:同源同类告警合并,避免告警风暴。
- **测试与回放**:用历史数据回放估算误报;用模拟攻击验证命中。

### 3.3 关联规则示例(伪 DSL / 通用逻辑)

```
RULE 爆破后登录成功
  WHEN:
    STEP1: 时间窗 5 分钟,登录失败 >= 5 次,按 (source.ip, user.name) 分组
    STEP2: 紧随 STEP1 之后 10 分钟内,同一 (source.ip, user.name) 登录成功
  THEN: 生成 High 告警,附 STEP1/STEP2 证据事件
  动作: 调用 SOAR 剧本 → 验证账号会话 → 通知资产负责人
```

## 四、SIEM 建设步骤与常见坑

### 4.1 建设步骤

1. **需求与范围**:明确要检测什么(合规/威胁/业务)、接哪些日志、谁使用。
2. **选型与 PoC**:按选型要点做小规模验证。
3. **平台部署**:采集器部署、网络打通、高可用、容量规划。
4. **数据接入**:逐类接入日志源,建立字段映射与数据质量检查。
5. **规则与告警建设**:分批上线规则,先核心场景后扩展。
6. **流程接入**:告警对接值班/工单/SOAR,明确 SLA。
7. **运营迭代**:误报治理、规则 review、覆盖度审计、指标汇报。

### 4.2 常见坑

| 坑 | 表现 | 规避 |
|----|------|------|
| 日志接不全 | 关键源缺失,检测是瞎子 | 接入清单 + 覆盖度季度审计 |
| 数据质量差 | 字段空、时间乱,规则失效 | 接入时做字段填充率校验,统一 NTP |
| 规则一拥而上 | 上线即告警风暴,人人疲劳 | 分批上线,先回放估算 |
| 只建平台不运营 | 平台吃灰,价值为零 | 明确运营团队与 KPI |
| 容量规划不足 | 高峰丢日志,分析失真 | 按峰值 2 倍预留,监控采集链路 |
| 存储与合规脱节 | 留存不足,审计被问责 | 按合规要求配置分级存储 |
| 权限与审计缺失 | 平台自身被滥用 | 平台账号权限最小化、操作审计 |

## 五、SOAR 概念(编排/自动化/响应)

SOAR(Security Orchestration, Automation and Response,安全编排、自动化与响应)解决"告警太多、人手不足"的问题,把重复性响应动作自动化、流程化。

| 能力 | 说明 |
|------|------|
| 编排(Orchestration) | 串联多个工具与系统(防火墙、EDR、工单、情报),编排响应流程 |
| 自动化(Automation) | 将标准动作(查情报、封 IP、隔离主机、发通知)自动化执行 |
| 响应(Response) | 按剧本(Playbook)执行完整响应流程,含人工审批节点 |

**SOAR 适用动作示例**:查询威胁情报 → 判定恶意 → 封禁源 IP → 隔离失陷主机 → 通知负责人 → 创建工单 → 记录处置日志。

**适用判断标准**:动作是否"高频、标准、可脚本化"?是 → 自动化;否(需要专业研判/高风险操作)→ 保留人工审批节点。

## 六、剧本(Playbook)设计示例

### 6.1 示例:恶意外联告警 → 封禁 IP → 隔离主机 → 通知

```
剧本:恶意外联响应(级别:High)
触发:SIEM 告警"主机外联已知恶意IP"

1. [自动] 查询威胁情报 API,确认 IOC 家族与置信度
   ├─ 置信度 < 60% → 标记待研判,通知值班分析师 → 结束
   └─ 置信度 ≥ 60% → 继续
2. [自动] 查询 CMDB,获取主机信息(业务、负责人、是否生产)
   ├─ 生产核心系统 → 转人工审批节点(见 4a)
   └─ 非核心系统 → 继续
3. [自动] 在边界防火墙封禁恶意 IP(双向),记录变更单
4. [自动/审批] 隔离主机:调用 EDR 断网隔离
   ├─ 4a. 生产系统:通知负责人审批 → 确认后隔离
   └─ 4b. 非生产:直接隔离
5. [自动] 主机取证:EDR 提取进程链/文件哈希 → 上传沙箱分析
6. [自动] 创建工单(关联告警、处置动作、证据),通知安全群与负责人
7. [人工] 分析师复核:确认处置有效 → 关闭工单 / 升级事件响应
8. [自动] 记录处置日志到台账,供复盘与规则调优
```

**设计原则**:①高危动作(隔离生产主机)必须有人工审批节点;②剧本要有失败分支与超时处理;③每个动作要可回滚(解除封禁、恢复网络);④剧本运行全程留痕,满足审计。

### 6.2 其他常用剧本

- 暴力破解响应:封禁源 IP → 检查受害账号 → 强制改密 → 通知用户。
- 钓鱼邮件响应:邮件网关撤回 → 检查点开人员 → 主机排查 → 清除。
- 勒索软件响应:隔离主机 → 终止恶意进程 → 快照取证 → 通知 IR。
- 新漏洞应急(如 Log4j):资产定位(SBOM)→ 缓解(ACL/WAF)→ 补丁跟踪。

## 七、SIEM 与 SOAR 集成

- **数据流**:SIEM 产生告警 → 通过 API/Webhook 推送 SOAR → SOAR 执行剧本 → 动作结果回写 SIEM 工单/状态。
- **双向联动**:SOAR 执行封禁/隔离后,把"已处置"状态回写 SIEM,避免重复告警;SIEM 的规则更新也可由 SOAR 触发(如情报更新后刷新规则)。
- **集成形态**:商业 SOAR(如 Splunk SOAR、QRadar SOAR、国产安全运营平台内置编排)、自研脚本编排(工作流引擎 + 各系统 API)。
- **集成清单**:至少要打通 EDR、防火墙、威胁情报、工单/IM(钉钉/企微)、邮件这五类系统。

**轻量替代方案**:预算有限时可先用"SIEM 告警 → 自动查询情报/CMDB 富化 → 推送到 IM 群 → 值班人员点按钮触发预设脚本"的半自动模式,再逐步升级全自动剧本。

## 八、指标评估(检测覆盖率、MTTD、MTTR)

| 指标 | 定义 | 评估方法 | 目标参考 |
|------|------|---------|---------|
| 检测覆盖率 | 已知威胁场景中被规则覆盖的比例 | 用攻击链清单核对规则覆盖(红队演练验证) | ≥ 80% 核心场景 |
| 告警准确率 | 有效告警 ÷ 总告警 | 月度统计 | ≥ 70%(误报 < 30%) |
| MTTD | 平均检测时间 | 事件复盘:攻击开始→检出 | 核心威胁 < 1 小时 |
| MTTA | 平均确认时间 | 告警时间→分析师接手 | < 15 分钟 |
| MTTR | 平均修复/恢复时间 | 事件确认→遏制/恢复 | 严重事件 < 4 小时 |
| 自动化率 | 自动化处理的告警占比 | SOAR 运行统计 | 高频场景 > 50% |
| 剧本成功率 | 剧本执行成功比例 | SOAR 统计 | > 90% |

**评估节奏**:

- **月度**:告警量、误报率、MTTA、自动化率,驱动日常调优。
- **季度**:红蓝演练验证检测覆盖率,更新规则清单;复盘重大事件修正 MTTD/MTTR。
- **年度**:平台价值汇报(投入产出、事件避免损失、合规达成),规划下一年建设。

> 核心原则:**指标不是装饰,而是改进的起点**——MTTD 高了查规则与数据源,误报高了查规则与白名单,覆盖率低了补规则与日志源。指标必须能指向具体改进动作。
