# 漏洞管理
> 关键词:漏洞管理,漏洞闭环,CVSS,EPSS,漏洞扫描,优先级,修复时限,漏洞台账,MTTR,修复率,供应链漏洞,漏洞评估,缓解措施,复测验证

## 一、漏洞管理闭环

漏洞管理(Vulnerability Management)的核心是**闭环**:发现 → 评估 → 处置 → 复测 → 台账跟踪,而不是"扫一次出一份报告"。

```
发现 → 评估与优先级 → 处置(修复/缓解/接受/转移) → 复测验证 → 台账与KPI → 复盘改进
  ↑                                                                          ↓
  └────────────────────── 持续扫描 + 新漏洞情报输入 ───────────────────────────┘
```

闭环关键点:

1. **持续发现**:固定频率扫描 + 漏洞情报实时推送,不是"季扫"。
2. **按风险排序**:不是"先修高危",而是"先修高风险的"——风险 = 严重性 × 可利用性 × 资产重要性 × 暴露面。
3. **处置有策略**:修复不了就缓解、接受、转移,但必须留痕。
4. **复测验证**:修复后必须复测确认漏洞真实消失。
5. **台账说话**:用 KPI 向上汇报,驱动资源投入。

## 二、漏洞发现(扫描/众测/情报/通报)

| 发现渠道 | 方式 | 频率 | 产出 |
|---------|------|------|------|
| 漏洞扫描 | 扫描器(如 Nessus、OpenVAS、绿盟、奇安信)对内网/云资产定期扫描 | 高危资产每周、一般资产每月 | 资产漏洞清单 |
| 渗透测试 | 人工渗透测试关键业务 | 半年/年或上线前 | 深度漏洞与利用链 |
| 众测(SRC) | 众测平台/自有 SRC(漏洞赏金) | 持续 | 外部视角漏洞 |
| 情报/通报 | CNNVD、CNVD、厂商安全公告、威胁情报订阅 | 实时 | 新漏洞预警 |
| 基线核查 | 配置核查工具检查弱口令、默认配置 | 每月 | 配置类漏洞 |
| CI/CD 集成 | DevSecOps 流水线中嵌入扫描 | 每次构建 | 开发期漏洞 |

> 经验:**扫描器漏掉的比扫出来的更重要**。扫描覆盖盲区(云上临时资产、容器镜像、API 服务)要用资产测绘补全;开发期漏洞要在 CI 阶段拦截,成本最低。

## 三、漏洞评估与优先级

### 3.1 严重性:CVSS v3/v4

CVSS(Common Vulnerability Scoring System)是漏洞严重性评分标准:

- **CVSS v3.1**:Base 评分 0.0-10.0,分级:0.1-3.9 低(Low)、4.0-6.9 中(Medium)、7.0-8.9 高(High)、9.0-10.0 严重(Critical)。
- **CVSS v4.0**:引入更多环境维度(如攻击复杂性细化、自动化能力),评分粒度更细,并区分 Base / Threat / Environmental / Supplemental 指标组。

评分维度(以 v3 为例):攻击向量(AV:网络/邻接/本地/物理)、攻击复杂度(AC)、所需权限(PR)、用户交互(UI)、影响(CIA 三性)。

### 3.2 可利用性:EPSS

EPSS(Exploit Prediction Scoring System)预测漏洞**在未来 30 天被利用的概率**(0-100%),是"严重性"之外的关键补充——严重但不被利用的漏洞,优先级可以降低。

- EPSS > 0.9(约 0.1% 的漏洞):几乎必然被利用,应加急。
- EPSS 0.5-0.9:很可能被利用,优先处理。
- EPSS < 0.05:利用概率低,可排队。

### 3.3 资产重要性与暴露面

- **资产重要性**:关键业务系统、核心数据库、对外服务 > 内部测试系统。用资产分级(Critical/High/Medium/Low)加权。
- **暴露面**:是否公网可达、是否可被互联网直接访问。公网资产 + 可利用漏洞 = 最高风险组合。

### 3.4 优先级评分示例表

| 漏洞 | CVSS v3 | EPSS | 资产重要性 | 暴露面 | 综合优先级 | 理由 |
|------|---------|------|-----------|--------|-----------|------|
| 某 OA 系统 RCE | 9.8 | 0.92 | 高(核心办公) | 公网可达 | **P0 立即** | 可利用性极高+公网+核心资产 |
| 某中间件反序列化 | 9.0 | 0.85 | 中(内部业务) | 仅内网 | P1 24h 内 | 可利用但暴露面有限 |
| 某 CMS XSS | 6.1 | 0.03 | 低(展示站) | 公网 | P3 常规排期 | 影响小、利用概率低 |
| 某数据库 CVE | 7.5 | 0.60 | 高(核心库) | 仅内网+白名单 | P1 24h 内 | 影响大、暴露受限 |
| 某组件 DoS | 7.8 | 0.02 | 中 | 公网 | P2 一周内 | 可利用性低 |

**推荐评分模型(可配置)**:

```
风险分 = CVSS(0-10) × 0.4 + EPSS概率(%)/10 × 0.3 + 资产重要性(1-5) × 1.0 + 暴露面加成(公网+2/内网+0)
```

> 判断标准:风险分 ≥ 某阈值(如 6)进入当周修复队列;CVSS ≥ 9 且 EPSS ≥ 0.9 且公网可达 → P0。**优先级排序的最终依据是"被利用的现实风险",不是 CVSS 数值本身**。

## 四、漏洞处置策略(修复/缓解/接受/转移)

| 策略 | 适用场景 | 做法 |
|------|---------|------|
| 修复(Remediation) | 有补丁、可升级 | 打补丁、升级版本、更新组件——首选方案 |
| 缓解(Mitigation) | 暂无补丁或无法停机 | WAF 规则拦截、网络 ACL 限制、停用受影响功能、隔离 |
| 接受(Acceptance) | 风险极低、修复成本极高 | 由资产负责人签字确认接受,记录风险与到期复查时间 |
| 转移(Transfer) | 云服务商/第三方组件 | 依赖云厂商修复(如云平台漏洞)、与供应商 SLA 约定修复时限 |

**决策树**:有补丁且可停机 → 修复;有补丁不可停机 → 评估维护窗口+缓解并行;无补丁 → 缓解 + 持续跟踪补丁发布;利用概率极低且资产非关键 → 接受(需签字)。

## 五、修复时限分级

| 优先级 | 定义依据 | 修复时限(参考) | 说明 |
|--------|---------|---------------|------|
| P0 | CVSS≥9 且公网可达,或已被利用(有攻击迹象) | ≤ 24 小时 | 先缓解遏制,再打补丁;超时应上报 |
| P1 | CVSS≥7 且暴露面较高,或 EPSS 高 | ≤ 7 天 | 高危漏洞标准时限 |
| P2 | 中危或可利用性一般 | ≤ 30 天 | 常规排期修复 |
| P3 | 低危或利用概率极低 | ≤ 90 天(或季度) | 随版本升级一并处理 |

> 时限从**漏洞确认并定级**起算;被利用或出现公开 PoC 的漏洞,时限应自动升级。P0 修复率与及时率应作为安全团队核心 KPI 汇报。

## 六、复测验证

- **复测方式**:重新扫描确认漏洞消失;人工验证(渗透测试确认利用链失效);配置类漏洞用基线核查确认。
- **复测时机**:修复完成后立即复测;紧急修复(绕过补丁的缓解措施)每 30 天复查有效性。
- **复测记录**:复测结果写入台账,"已修复(复测通过)""缓解中(复查日期)""接受(签字+到期日)"。
- **失败处理**:复测未通过 → 退回处置流程并升级提醒;连续两次未通过 → 上报安全负责人协调资源。

## 七、漏洞台账与 KPI

### 7.1 台账字段

漏洞台账(可基于工单系统或漏洞管理平台)至少包含:漏洞 ID(CVE/CNVD)、资产(IP/主机名/业务系统/负责人)、严重性(CVSS)、EPSS、发现渠道、发现时间、定级、处置策略、处置状态、责任人、修复时限、复测结果、关闭时间。

### 7.2 核心 KPI

| KPI | 定义 | 目标参考 |
|-----|------|---------|
| 漏洞修复率 | 已修复漏洞 ÷ 应修复漏洞 | ≥ 90%(P0/P1 接近 100%) |
| MTTR(漏洞) | 平均修复时间:发现到复测通过 | P0 < 1 天、P1 < 7 天 |
| P0 及时率 | 按时限完成的 P0 比例 | ≥ 95% |
| 逾期未修数量 | 超时限未处置漏洞数 | 趋近 0,持续下降 |
| 存量漏洞趋势 | 各等级未修复漏洞数(月度) | 呈下降趋势 |
| 重复漏洞率 | 复测后再次出现的漏洞占比 | < 10%(说明修复质量) |

> 汇报口径:向管理层报告"存量高危数、P0 修复率、逾期清单",用趋势图说明改善;台账要与"变更、资产管理、情报"联动(见下)。

## 八、与变更管理联动

- **修复即变更**:漏洞修复(打补丁、升级)必须走变更流程,涉及生产系统需评估业务影响与回滚方案。
- **变更窗口**:与运维约定维护窗口,批量修复减少中断;重大漏洞修复可走"紧急变更"通道。
- **变更回滚**:变更失败或引入新问题,台账状态回退,记录原因。
- **新资产入口**:新系统上线前必须完成漏洞扫描,无高危漏洞方可上线(接入 CMDB 与上线流程)。

## 九、供应链漏洞管理

供应链漏洞(第三方组件、开源库、云服务、外包系统)是近年高危来源(如 Log4j 类事件):

1. **资产清点**:建立软件物料清单(SBOM),记录每个系统使用的组件与版本。
2. **组件扫描**:CI/CD 与运行时扫描开源依赖(SCA 工具,如 Trivy、Snyk、国内开源安全平台)。
3. **情报预警**:订阅关键组件(Web 框架、中间件、开发框架)的安全公告,新漏洞 24h 内评估影响。
4. **版本策略**:不使用 EOL(停止维护)组件;升级策略明确(如"重大版本 ≤3 个月、安全修复 ≤2 周")。
5. **云与供应商**:云服务漏洞依赖厂商修复,签订 SLA;外包系统漏洞由供应商按约定时限修复,纳入台账跟踪。
6. **应急场景**:出现 Log4j 类 0day 时,启动专项应急:SBOM 定位受影响组件 → 临时缓解(网络隔离/WAF)→ 等待官方补丁 → 全量修复与复测。

> 一句话总结:**漏洞管理拼的不是扫描次数,而是"发现-排序-处置-验证"的闭环速度与台账质量**。
