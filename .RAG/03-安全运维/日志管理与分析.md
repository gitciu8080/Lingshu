# 日志管理与分析
> 关键词:日志管理,日志采集,Syslog,Agent,日志标准化,CEF,LEEF,JSON,ELK,KQL,Splunk,SPL,日志保留,防篡改,登录失败,异常外联,横向移动,数据外传,日志分析

## 一、日志管理全流程

日志管理是安全分析的基础设施,全流程为:**采集 → 传输 → 标准化 → 存储 → 分析 → 归档/销毁**。任何一环缺失都会导致"查不到、对不上、留不住"。

流程要点:

1. **采集**:覆盖所有关键日志源,确保"采得到"。
2. **传输**:加密、可靠传输,避免丢日志与篡改。
3. **标准化**:统一字段模型,确保"对得上"。
4. **存储**:分级存储 + 合规保留,平衡成本与查询性能。
5. **分析**:查询、关联、狩猎,支撑调查与检测。
6. **归档**:冷存储长期保留,满足合规与取证。

## 二、日志来源类型

| 类型 | 典型来源 | 关键内容 |
|------|---------|---------|
| 系统日志 | Windows Event Log、Linux syslog(/var/log) | 登录、进程、服务、内核事件 |
| 应用日志 | Web 服务器、中间件、业务系统 | 请求、错误、业务操作、用户行为 |
| 安全日志 | 防火墙、IDS/IPS、WAF、EDR、杀软 | 攻击特征、阻断/放行、恶意文件 |
| 网络设备日志 | 交换机、路由器、负载均衡 | 接口状态、ACL 命中、流量异常 |
| 云日志 | 云审计、云监控、对象存储访问 | 云上操作、资源变更、API 调用 |
| 身份与访问 | AD 域控、SSO、堡垒机、VPN | 登录成功/失败、权限变更、会话 |
| 数据层 | 数据库审计、DLP、文件服务器 | SQL 操作、敏感文件访问/外发 |

> 判断日志质量三问:**有没有**(覆盖)、**全不全**(字段)、**准不准**(时间同步,NTP 必须统一)。

## 三、日志采集方式

| 方式 | 适用场景 | 优点 | 缺点 | 典型工具 |
|------|---------|------|------|---------|
| Agent 采集 | 服务器/终端主机 | 字段丰富、可采集文件型日志 | 需部署维护、占资源 | Filebeat、Fluent Bit、Telegraf |
| Syslog 转发 | 网络/安全设备 | 配置简单、设备原生支持 | 明文默认、字段少、UDP 易丢包 | rsyslog、syslog-ng |
| API 拉取 | 云平台、SaaS | 结构化、实时性好 | 依赖厂商 API 限流 | 云审计 API、厂商 SDK |
| 数据库/文件拉取 | 传统应用 | 无需装 Agent | 时效性差 | JDBC 采集、定时任务 |
| 抓包/流量镜像 | 网络流量分析 | 无侵入、可还原会话 | 存储大、性能开销 | 流量采集器、NetFlow/IPFIX |

**采集可靠性建议**:关键日志使用 TCP/TLS Syslog 或 Agent 缓冲队列;采集端配置"失败重试 + 本地缓冲",防止日志源抖动导致丢日志。日志源时间务必统一 NTP,否则关联分析时间轴对不上。

## 四、日志标准化(CEF/LEEF/JSON)与字段映射

### 4.1 三种标准格式

| 格式 | 全称 | 特点 | 适用 |
|------|------|------|------|
| CEF | Common Event Format(ArcSight) | 以 `|` 分隔,头 + key=value 扩展 | 安全设备日志对接 |
| LEEF | Log Event Extended Format(QRadar/IBM) | 以 tab 分隔,key=value 扩展 | QRadar 生态 |
| JSON | JavaScript Object Notation | 结构化、易解析、字段可嵌套 | 现代采集链路首选 |

**CEF 示例**:
```
CEF:0|Vendor|Product|1.0|1001|Login Failed|5|src=10.1.1.2 dst=10.1.1.1 suser=admin
```

**JSON 示例**:
```json
{"event_time":"2024-01-01T10:00:00Z","src_ip":"10.1.1.2","dst_ip":"10.1.1.1","user":"admin","action":"login_failed","severity":5}
```

### 4.2 字段映射(统一模型)

| 语义字段 | 别名 | 说明 |
|---------|------|------|
| event_time / @timestamp | 事件时间 | 必须与采集时间区分 |
| src_ip / source.ip | 源 IP | 攻击来源/发起方 |
| dst_ip / destination.ip | 目的 IP | 攻击目标/外联对象 |
| src_port / dst_port | 端口 | 服务与协议判断 |
| user / user.name | 账号 | 溯源关键 |
| action / event.action | 动作 | login/success/deny 等 |
| severity / event.severity | 严重度 | 1-10 或 info/warn/error/critical |
| host / host.name | 主机 | 资产定位 |
| message / 原始日志 | 原文 | 必须保留原始字段用于取证 |

> 映射原则:**保留原始日志全文**(message 字段),同时提取关键字段到独立字段;任何转换都不要丢失原文,否则无法取证。

## 五、日志存储与保留策略(合规要求)

### 5.1 保留时长依据

| 要求来源 | 要求 |
|---------|------|
| 网络安全法(中国) | 网络日志留存 ≥ 6 个月 |
| 等级保护 2.0(等保) | 日志留存 ≥ 6 个月(三级及以上建议更长) |
| 数据安全法 | 处理活动记录可追溯 |
| 行业要求 | 金融(如 JR/T 0076)通常要求交易日志、审计日志更长(如 1-3 年) |
| 企业自定 | 结合取证与溯源能力,建议热数据 30-90 天、冷数据 6-24 个月 |

### 5.2 分级存储策略

| 层级 | 存储介质 | 保留周期 | 用途 |
|------|---------|---------|------|
| 热存储 | SSD/高性能 | 30-90 天 | 实时查询、告警关联 |
| 温存储 | 普通磁盘/对象存储 | 6-12 个月 | 历史调查 |
| 冷存储 | 归档存储(磁带/低频对象) | 12-24 个月或按合规 | 合规留存、重大事件取证 |

**容量估算公式**:每日日志量(GB)= Σ(每秒日志条数 × 平均单条大小 × 86400) × 冗余系数(1.2-1.5)。建议先按峰值流量的 2 倍预留,避免高峰期丢日志。

## 六、日志分析场景

| 场景 | 分析思路 | 关键证据 |
|------|---------|---------|
| 登录失败/暴力破解 | 按 src_ip 聚合失败次数、失败后是否成功 | 失败→成功的关联、爆破字典特征 |
| 异常外联 | 外联目的 IP/端口、外联频率、时间规律 | 非业务端口(如 443/53 外联)、C2 特征 |
| 横向移动 | 内网主机间异常连接、新 RDP/SMB 会话 | 非预期主机对、Pass-the-Hash 特征 |
| 数据外传 | 大流量上传、压缩包创建+外发、异常时间传输 | 批量文件操作、外联 + 上传组合 |
| 权限提升 | 特权账号创建、域管组变更、计划任务注册 | 新账号、组变更、注册表持久化 |
| 挖矿/恶意软件 | 高 CPU 主机、矿池域名、可疑进程链 | 进程创建链、已知矿池 IOC |

**通用分析步骤**:①确定时间窗与关键词 → ②按 IP/账号聚合 → ③拉原始日志看上下文 → ④跨日志源关联(认证+网络+主机)→ ⑤形成结论并留存证据。

## 七、分析技巧与查询示例

### 7.1 ELK(Elasticsearch KQL)

```kql
// 1. 某 IP 5 分钟内登录失败 TOP 账号
event.dataset: "auth" and event.outcome: "failure" and source.ip: "10.1.1.2"
| stats count() by user.name, bin(@timestamp, 5m)

// 2. 外联非标准端口(非 80/443)的主机
event.dataset: "netflow" and destination.port not in (80, 443, 53, 22)
| stats count() by host.name, destination.ip

// 3. 同一账号在多个主机登录失败(横向移动前兆)
event.dataset: "auth" and event.outcome: "failure"
| stats dc(host.name) as host_count by user.name
| where host_count > 3
```

### 7.2 Splunk SPL

```spl
// 1. 登录失败统计(按源 IP)
index=auth action=failure | stats count by src_ip | sort - count | head 20

// 2. 爆破后成功登录
index=auth action=failure | stats count by src_ip user | where count>5
  | join type=inner src_ip user [search index=auth action=success | stats count by src_ip user]

// 3. 数据批量导出(按用户聚合 1 小时窗口)
index=db_audit | timechart span=1h sum(export_size) by user | where sum > 5000000000
```

### 7.3 分析技巧清单

- **先看时间线再看字段**:用时间轴定位"异常窗口",再钻取具体字段。
- **善用聚合而非逐条看**:海量日志用 stats/count 聚合找"出头鸟"。
- **跨源关联**:同一 IP 同时出现在防火墙、认证、DNS 日志中才是强证据。
- **保存查询为仪表盘**:常用调查模板(登录、外联、爆破)固化为 dashboard。
- **建立时间基线**:对比"今天 vs 上周同期",基线偏离本身就是异常信号。

## 八、日志完整性与防篡改

| 手段 | 说明 |
|------|------|
| 集中采集 | 日志即时转发到集中平台,减少在主机上被篡改的窗口 |
| 独立日志服务器 | 日志服务器与业务主机分离,攻击者难以同时清除两端 |
| 权限控制 | 日志平台管理、删除权限最小化,操作留痕 |
| 只读/不可变存储 | 对象存储 WORM(Write Once Read Many)或 S3 Object Lock |
| 哈希校验 | 定期对归档日志计算哈希并记录,用于完整性比对 |
| 区块链/可信日志(可选) | 高合规场景对关键日志做链式哈希存证 |
| 时间同步 | NTP 统一,防止时间被篡改导致证据失效 |

> 常见错误:日志与业务部署在同一台机器且权限过大——攻击者提权后可直接"删日志灭迹"。日志权限必须与业务权限隔离。

## 九、常见日志分析误区与排查思路

### 9.1 常见误区

| 误区 | 后果 | 纠正 |
|------|------|------|
| 日志不接或漏接 | 事件溯源无依据 | 按接入清单定期盘点,新增资产必须接日志 |
| 只看告警不看原始日志 | 误判 | 告警只是线索,结论必须回到原始日志 |
| 时间不同步 | 关联分析错位 | 全链路 NTP 统一并校验 |
| 字段没标准化 | 查询困难、无法关联 | 建设统一字段模型(见第四节) |
| 日志保留不足 | 事后无法调查 | 按合规要求配置冷归档 |
| 只保留汇总不保留明细 | 丢失取证细节 | 明细日志单独保留 |
| 采集丢日志无感知 | 分析结果不可信 | 采集端加缓冲与对账,统计各源日志量基线 |

### 9.2 排查思路(调查方法论)

1. **还原时间线**:以事件时间为锚,向前推 24-72 小时回溯"入侵前",向后追踪"扩散后"。
2. **找初始入口**:登录日志找异常账号,邮件网关找钓鱼邮件,Web 日志找漏洞利用。
3. **跟随横向移动**:用认证+网络日志追踪失陷主机访问过的其他主机。
4. **确认数据影响**:数据库审计、DLP、文件日志确认数据是否外传、外传多少。
5. **固化证据链**:按"时间-源-动作-目标"整理证据,输出调查报告。

**排查黄金问题**:日志里"谁、何时、从哪里、做了什么、结果如何"?五个问题答完,调查基本成形。
