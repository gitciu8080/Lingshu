# 安全监控与告警
> 关键词:安全监控,监控体系,告警规则,告警分级,SLA,误报,告警疲劳,降噪,上下文丰富,监控盲区,SIEM,IDS,EDR,NTA

## 一、监控体系建设总览

安全监控的目标是"**及时、准确、可处置**":及时发现异常,告警准确不泛滥,每条告警都能被处置并闭环。体系建设遵循五步:

1. **摸资产**:梳理监控对象,明确"要保护什么、什么算异常"。
2. **接数据**:按日志源接入清单采集日志与流量(详见《日志管理与分析》)。
3. **定规则**:分层设计检测规则,覆盖已知威胁与可疑行为。
4. **立流程**:告警分级 + SLA + 值班响应流程。
5. **持续优化**:统计误报率、覆盖率,定期复盘规则质量。

## 二、监控对象分层

监控对象按五个层次覆盖,每层有对应的检测手段:

| 层次 | 监控对象 | 主要手段 | 典型检测点 |
|------|---------|---------|-----------|
| 网络层 | 南北向/东西向流量、边界设备 | NTA、IDS/IPS、防火墙日志 | 异常外联、C2 通信、端口扫描、DDoS |
| 主机层 | 服务器、终端、数据库主机 | EDR、HIDS、Sysmon | 恶意进程、异常登录、提权、持久化 |
| 应用层 | Web/中间件/API/业务系统 | WAF、应用日志、RASP | SQL 注入、越权、暴力破解、业务逻辑滥用 |
| 数据层 | 数据库、文件共享、对象存储 | 数据库审计、DLP、文件监控 | 批量导出、异常查询、敏感文件外传 |
| 用户行为层 | 账号、身份、权限 | UEBA、IAM 审计 | 账号共享、异常时间登录、权限提升、离离职账号 |

> 原则:**分层不是割裂**。同一攻击往往跨多层,如"钓鱼邮件 → 主机沦陷 → 横向移动 → 数据外传",需要靠关联规则把各层告警串起来(见第五节)。

## 三、关键指标(KPI)与安全事件类型

### 3.1 监控类 KPI

| 指标 | 定义 | 目标参考 |
|------|------|---------|
| MTTD(Mean Time to Detect) | 平均检测时间:攻击发生到被发现 | < 1 小时(中大型企业) |
| MTTA(Mean Time to Acknowledge) | 平均确认时间:告警产生到分析师接手 | < 15 分钟 |
| MTTM(Mean Time to Mitigate) | 平均遏制时间:确认到完成遏制 | < 4 小时 |
| 告警量/日 | 每 24 小时产生告警总数 | 与团队处置能力匹配 |
| 误报率(False Positive Rate) | 误报告警占告警总量比例 | < 30% |
| 告警闭环率 | 已处置并归档的告警占比 | > 95% |
| 漏报率 | 事后确认的未检出事件占比 | 趋近 0(通过复盘估算) |

### 3.2 常见安全事件类型(检测覆盖清单)

- 账号类:暴力破解、撞库、异常登录(异地/新设备/非工作时间)、账号共享、僵尸账号登录。
- 恶意代码类:已知恶意软件、勒索软件行为(批量加密、删除卷影)、挖矿(高 CPU、异常外联矿池)。
- 网络攻击类:端口扫描、漏洞利用尝试、Web 攻击(SQLi/XSS/RCE)、DDoS、DNS 隧道。
- 数据泄露类:大批量查询/导出、敏感文件外发、异常上传、数据库拖库。
- 内网渗透类:横向移动(异常 SMB/RDP 连接)、提权、域内侦察(LDAP 查询、BloodHound 行为)。
- 供应链类:异常更新包、可疑第三方组件行为、CI/CD 管道异常。
- 物理与合规类:非法外设接入、违规外联、配置变更(未走变更流程)。

## 四、日志源接入清单

| 日志源类型 | 具体来源 | 采集方式 | 优先级 |
|-----------|---------|---------|--------|
| 网络设备 | 防火墙、路由器、交换机、负载均衡 | Syslog | P0 |
| 安全设备 | IDS/IPS、WAF、沙箱、VPN、DLP | Syslog / SNMP / API | P0 |
| 主机系统 | Windows 安全日志、Linux syslog、Sysmon | Agent / Syslog | P0 |
| 终端 | EDR 终端、杀软客户端 | Agent(厂商平台转发) | P0 |
| 应用系统 | Web 服务器(IIS/Nginx/Tomcat)、业务应用、中间件 | Agent / 文件采集 / API | P1 |
| 数据库 | Oracle/MySQL/SQL Server 审计日志 | Agent / 数据库审计设备 | P1 |
| 身份认证 | AD 域控、统一认证(SSO)、堡垒机 | Syslog / API | P0 |
| 云平台 | 云审计(如云平台操作审计)、云安全组、对象存储访问 | API / 事件总线 | P1 |
| 邮件 | 邮件网关、Exchange Online 审计 | API / Syslog | P1 |
| DNS | 内网 DNS 解析日志 | Syslog / 抓包 | P1(外联分析利器) |

> 接入优先级原则:先接**登录认证、边界网络、主机行为**三类日志,这是发现大多数事件的基础;再逐步覆盖应用、云与业务日志。

## 五、告警规则设计

### 5.1 规则构成要素

一条合格告警规则至少包含:检测逻辑(阈值/关联/频率)、数据来源(索引/字段)、时间窗口、触发条件、告警级别、去重与抑制策略、处置建议(Playbook 链接)。

### 5.2 规则语法示例(以 Elasticsearch Query DSL / KQL 风格为例)

**示例一:阈值规则——同源 IP 登录失败过多**

```
// KQL 查询(时间窗口 5 分钟)
event.dataset: "auth" AND event.outcome: "failure"
// 阈值:同一 source.ip 失败次数 >= 10
// 触发后:source.ip 加入观察名单 30 分钟
```

**示例二:关联规则——爆破成功后异常登录**

```
步骤 A:5 分钟内登录失败 >= 5 次(source.ip, user.name)
步骤 B:A 中同一 source.ip 随后 10 分钟内登录成功
关联条件:user.name 相同
结论:高可疑爆破成功 → 升级为 High 告警并触发账号锁定核查
```

**示例三:频率规则——数据批量导出**

```
字段:user.name + data.export.volume
时间窗口:1 小时
条件:导出记录数 >= 50 条 且 导出量 > 5GB
备注:需结合业务基线,先建模学习正常导出量
```

**示例四:黑名单规则——外联已知恶意 IP**

```
字段:destination.ip
匹配:威胁情报 IOC 库(信誉库)
触发:立即告警,关联资产信息与负责人
```

### 5.3 规则设计要点

- **先基线后规则**:新规则先用历史数据回放(backtest),估算正常触发量,避免一上线就爆量。
- **场景化分组**:按攻击阶段(侦察/入侵/横向/外传)组织规则,便于覆盖度审计。
- **规则要有"户口"**:每条规则记录负责人、数据源、有效期、定期 review 日期。
- **低危规则只记录不打扰**:中低危告警入库(如 ES 索引),供检索与狩猎,不推送给值班。

## 六、告警分级与响应时限(SLA)

| 级别 | 定义 | 示例 | 响应时限(接警到确认) | 处置时限(确认到闭环) | 通知对象 |
|------|------|------|---------------------|---------------------|---------|
| 严重(Critical) | 已确认入侵/大规模数据泄露/核心业务瘫痪 | 勒索软件加密、域控失陷、拖库 | ≤ 10 分钟 | ≤ 2 小时 | 安全负责人、业务负责人、必要时管理层 |
| 高(High) | 高度疑似入侵,影响面大 | 爆破成功、Webshell 上传、C2 通信确认 | ≤ 30 分钟 | ≤ 8 小时 | 安全团队 + 资产负责人 |
| 中(Medium) | 可疑行为,需人工研判 | 端口扫描、异常登录失败、可疑外联 | ≤ 2 小时 | ≤ 24 小时 | 值班分析师 |
| 低(Low) | 信息性/基线偏离 | 配置漂移、非工作时段计划外重启 | ≤ 8 小时 | ≤ 72 小时 | 记录 + 周报 |

> SLA 约定要点:①时限从**告警触发**起算,不是从值班看到起算;②超时自动升级(如 Medium 超 2 小时未确认自动升 High);③每周统计 SLA 达成率,低于 90% 要调整人力或降噪。

## 七、误报与告警疲劳治理

告警疲劳(Fatigue)是指海量告警淹没真实威胁,导致分析师"看了也当没看"。治理手段:

1. **分级降噪**:低危转日志库、高危才推送,推送渠道也分级(严重走电话/短信,高危走 IM)。
2. **去重与聚合**:同一事件在 5 分钟内只报 1 条;按 source.ip/user/host 聚合后合并。
3. **白名单管理**:对已知正常的源(如内部扫描器、监控探针)建白名单,白名单必须有审批与过期时间。
4. **规则回放调优**:每周把规则触发量与真实命中数对比,误报率 > 50% 的规则强制 review。
5. **上下文丰富**:告警自动附带资产信息、负责人、历史行为、威胁情报,让分析师 1 分钟内可判,减少"点开看"的疲劳。
6. **机器学习辅助**:对高频基线行为(如固定时段批量任务)用异常检测替代硬阈值。

**误报率计算**:误报率 = 判定为误报的告警数 ÷ 总告警数。建议月度统计,按规则维度排名,TOP 10 规则单独治理。

## 八、告警降噪与上下文丰富

- **上下文丰富的字段清单**:资产 IP/主机名/负责人/业务系统、账号与角色、地理位置(出口 IP 归属)、威胁情报命中(恶意 IP/域名/哈希)、过去 24h 该资产行为画像、关联事件链(同源其他告警)。
- **丰富方式**:告警触发时调用 CMDB 与情报 API 自动填充(SOAR 可编排,见《SIEM与SOAR》)。
- **降噪进阶**:使用"风险评分"替代单一阈值——如登录失败次数 × 账号重要度 × 来源信誉,评分超阈值才告警。

## 九、监控覆盖盲区检查

每季度做一次覆盖度审计,重点检查:

| 盲区类型 | 检查问题 | 典型发现 |
|---------|---------|---------|
| 数据源缺失 | 是否还有设备/系统未接入日志? | 新上云资源未接审计日志 |
| 字段缺失 | 关键字段(源/目的 IP、账号)是否完整? | 应用日志无用户字段,无法溯源 |
| 规则缺口 | 攻击链各阶段是否有规则覆盖? | 只有边界规则,无东西向流量检测 |
| 时序缺口 | 非工作时间、节假日告警是否有人盯? | 周末无人值班,告警积压 |
| 绕过风险 | 加密流量、云原生动态 IP 是否可检测? | TLS 加密隧道无法分析 |
| 演练验证 | 规则是否经过红蓝演练验证? | 规则从未被真实触发,可能是死规则 |

**盲区验证方法**:定期开展"模拟攻击演练"(如用原子红队工具模拟扫描、爆破、外传),验证规则能否命中;命中不了的规则要么修要么删。

## 十、监控项清单表(建设参考)

| 序号 | 监控项 | 数据源 | 规则类型 | 建议级别 |
|------|--------|--------|---------|---------|
| 1 | 同源 IP 登录失败 ≥10 次/5min | AD/SSO 日志 | 阈值 | 中 |
| 2 | 爆破后登录成功 | 认证日志 | 关联 | 高 |
| 3 | 非工作时间特权账号登录 | 认证日志 + 时间基线 | 阈值+基线 | 中 |
| 4 | 主机外联已知恶意 IP | 流量/DNS + 情报 | 黑名单 | 高 |
| 5 | DNS 解析量突增(隧道嫌疑) | DNS 日志 | 频率 | 中 |
| 6 | 同主机多账号登录失败 | 认证日志 | 关联 | 低 |
| 7 | 数据库批量导出 >5GB/1h | 数据库审计 | 阈值+基线 | 高 |
| 8 | 新进程创建于临时目录并外联 | EDR | 关联 | 高 |
| 9 | Web 攻击特征命中(SQLi/XSS) | WAF | 特征 | 中 |
| 10 | 端口扫描(1min 内 >100 端口) | NTA/防火墙 | 阈值 | 低 |
| 11 | 敏感文件外发(邮件/上传) | DLP/邮件网关 | 特征 | 高 |
| 12 | 配置未经变更流程修改 | CMDB/设备日志 | 审计 | 中 |

> 使用建议:表内 12 项是起步清单,可按"每层至少 2 条规则"扩展;每条规则上线前务必用真实历史数据回放验证。
