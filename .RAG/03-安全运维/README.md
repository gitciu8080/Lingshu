# 安全运维(SecOps)
> 关键词:安全运维,SecOps,安全运营中心,SOC,监控,告警,日志,威胁情报,漏洞管理,SIEM,SOAR,应急响应,MTTD,MTTR

## 一、什么是安全运维

安全运维(Security Operations,SecOps)是将**安全能力**与**运维流程**融合的运营体系,核心目标是把安全事件从"发现"到"处置"的全链路跑通、跑快、跑稳。它不再是单纯的"装设备、看告警",而是以**检测、响应、修复、改进**四件事为循环的持续运营。

SecOps 的三条主线:

| 主线 | 解决的问题 | 对应模块 |
|------|-----------|---------|
| 看得见 | 网络上发生了什么?哪里被攻击了? | 监控告警、日志分析、SIEM |
| 判得准 | 这是攻击还是误报?威胁有多大? | 威胁情报、关联分析、漏洞评估 |
| 处置快 | 如何遏制、修复、闭环? | 漏洞管理、SOAR 编排、应急响应 |

## 二、职责范围

SecOps 团队(通常对应 SOC, Security Operations Center)的典型职责清单:

1. **安全监控**:7×24 监控网络流量、主机行为、应用日志、云平台事件,发现异常与攻击迹象。
2. **告警分析与分级**:对告警做初步研判(Triage),区分误报、可疑、确认攻击,并按严重程度升级。
3. **威胁检测规则维护**:编写、调优 SIEM / IDS / EDR 检测规则,降低误报率。
4. **威胁情报运营**:收集、评估、落地 IOC(失陷指标),将情报转化为检测能力。
5. **漏洞管理**:漏洞发现、评估、修复跟踪、复测,维护漏洞台账与 KPI。
6. **事件响应(IR)**:对确认的安全事件执行遏制、消除、恢复、复盘。
7. **日志合规与留存**:满足等级保护、数据安全法等对日志留存(通常≥6 个月)的要求。
8. **安全基线与加固**:主机、网络设备、云资产的配置基线核查与加固。
9. **红蓝对抗配合**:为攻防演练、渗透测试结果提供修复与复盘支撑。
10. **度量与汇报**:向管理层输出 MTTD(平均检测时间)、MTTR(平均修复时间)、漏洞修复率等指标。

## 三、与其他模块的边界

- **与攻防对抗(02)**:攻防发现的问题由安全运维闭环修复;红队的攻击手法反过来喂给检测规则。
- **与合规审计**:安全运维产生的日志、台账、处置记录是等保、ISO 27001 审计的取证来源。
- **与开发安全(DevSecOps)**:CI/CD 中的漏洞扫描结果汇入漏洞管理台账,统一跟踪。

## 五、核心方法论

SecOps 的落地可归纳为五个步骤,也是本模块各文件的阅读顺序:

1. **建基线**:先搞清楚有哪些资产、哪些日志、哪些正常行为(对应监控与日志两篇)。
2. **布检测**:用规则 + 情报 + 关联分析覆盖已知威胁(对应 SIEM、威胁情报两篇)。
3. **定流程**:明确告警怎么分级、漏洞怎么排期、事件怎么响应(SLA 与台账)。
4. **自动化**:把高频重复动作剧本化,交给 SOAR 执行。
5. **看指标**:用 MTTD、MTTR、误报率、漏洞修复率驱动持续改进。

> 一句话原则:**先有数据,再有检测;先有流程,再上自动化**。没有稳定日志源的告警规则是空中楼阁。

## 八、与合规要求的关系

安全运维是等保、ISO 27001、数据安全法落地的**执行层**:

- **等保 2.0**:安全计算环境/区域边界/管理中心的安全审计要求,对应日志采集与留存(≥6 个月);入侵防范要求对应监控告警;漏洞和风险管理对应漏洞管理闭环。
- **ISO 27001**:A.12.4(日志与监控)、A.12.6(技术漏洞管理)、A.16(信息安全事件管理)直接对应本模块。
- **数据安全法**:数据处理活动记录可追溯,要求日志与台账可审计。

> 合规不是目的,是底线;安全运维的产出(日志、台账、处置记录)同时是合规审计的"证据链"。

## 九、运营成熟度模型(自评参考)

| 等级 | 特征 | 典型表现 |
|------|------|---------|
| L1 被动 | 有设备无运营 | 告警堆在设备里,没人看、没流程 |
| L2 响应 | 有流程但靠人 | 告警人工研判,无规则体系,误报高 |
| L3 主动 | 规则+情报驱动 | 分层检测规则、告警分级 SLA、台账 KPI |
| L4 自动化 | 编排自动化 | SOAR 剧本化处置,自动化率 >50% |
| L5 预测 | 攻击面+狩猎驱动 | 主动狩猎、攻击面管理、持续红蓝验证 |

自评问题:日志接全了吗?规则有人维护吗?告警有 SLA 吗?处置有台账吗?指标在改善吗?答不上来,说明还没到 L3。

## 十、常见挑战与应对

| 挑战 | 表现 | 应对 |
|------|------|------|
| 告警疲劳 | 分析师忽略真实告警 | 分级降噪、规则回放、上下文丰富(见监控篇) |
| 日志孤岛 | 各系统日志各管各 | 集中采集 + 统一字段模型(见日志篇) |
| 漏洞修不动 | 业务方不配合停机 | 修复时限分级 + 管理层 KPI 汇报 + 缓解措施兜底 |
| 情报用不上 | 买了情报没落地 | 明确落地动作:规则/信誉库/狩猎(见情报篇) |
| 平台吃灰 | SIEM/SOAR 建成无人运营 | 配运营团队、定月度指标、红蓝演练验证(见 SIEM 篇) |
| 人手不足 | 7×24 难保障 | 自动化 + 外包值守 + 分级上报,把人力用在关键研判上 |

## 十一、阅读与落地建议

- **新团队起步**:先读《日志管理与分析》《安全监控与告警》,把"数据+规则"地基打好。
- **已有平台**:读《SIEM与SOAR》《威胁情报》,做规则调优与自动化。
- **向上汇报**:读《漏洞管理》与各篇 KPI 章节,用指标说话。
- **建设顺序**:日志平台 → 监控规则 → 漏洞闭环 → 威胁情报 → SOAR 自动化,一步一个闭环,不要贪大求全。
