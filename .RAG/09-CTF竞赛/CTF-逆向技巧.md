## 一、z3 约束求解

### 适用场景

程序将输入经过**数学运算**(线性方程、位运算、密码轮函数)后与固定值比较,且运算可表达为约束时,用 z3 SMT 求解器直接求解,避免手动逆算法。

### 使用模板

```python
from z3 import *

# 1. 定义变量
v = [BitVec(f'inp{i}', 32) for i in range(11)]   # 位向量,适合位运算
# 或 Int(...) 适合整数方程

s = Solver()

# 2. 添加约束(程序里的比较条件)
s.add(v[0]*52 + v[1]*93 + ... - 786241466532 == 0)
s.add(...)

# 3. 添加已知约束(如已知的固定字符)
s.add(v[0] == ord('N'))

# 4. 求解
if s.check() == sat:
    m = s.model()
    print(bytes([m[i].as_long() for i in v]))
```

### 要点

- 位运算用 `BitVec`,纯算术用 `Int`;浮点系数转精确整数(乘 10 的幂去小数)。
- 约束缺失导致多解时,补充字符集约束(`0x20 <= v[i] <= 0x7e`)或已知片段。
- z3 也常用于解决线性方程组、简单加密链、迷宫题约束等。

## 二、UPX 加壳与修复

### 常规脱壳

```bash
upx -d program    # 直接脱壳
```

### 壳修复常见场景(本题:节区名被改)

- 程序节区名(UPX0/UPX1/UPX2)被改成别的名字后 `upx -d` 失败;
- 修复:用十六进制编辑器把节区名改回 `UPX0`、`UPX1`、`UPX2`(在节表处,注意大小写与对齐),再 `upx -d`;
- 或直接手动脱壳:dump 内存 + 修复导入表(用 Scylla/ImpRec)。

### 要点

- 识别壳:`file`、`Detect It Easy (DIE)`、`Exeinfo PE`;
- 判断"伪壳":节名异常、EP 特征不符;
- 脱壳失败优先检查节区名、校验和、覆盖数据(overlay)。

## 三、魔改加密算法还原(以 DES/RC4 为例)

### 场景

程序把标准算法(DES/AES/RC4 等)魔改(改 S-box、改轮数、删步骤、改密钥调度),直接调用标准库无法解密,需要**按程序逻辑还原算法后写逆**。

### 方法论

1. **识别算法**:搜索字符串/常量特征(如 DES S-box 常数、RC4 的 256 字节初始化、AES 的 S-box 表)。
2. **对比标准实现**:拿到 mbedTLS/OpenSSL 源码,与反编译代码逐段对比,找出差异点:
   - 密钥调度是否完整;
   - 轮数/轮顺序;
   - S-box 是否被替换;
   - 加密轮宏是否被改(如 `DES_ROUND_dec` 与加密版混用)。
3. **保留数据表**:S-box、置换表、RC4 流表按程序原样保留,不依赖标准库。
4. **写逆**:加密是"正着走",解密按逆轮序/逆操作(异或自逆、S-box 反查表、轮密钥倒序)。
5. **验证**:用已知明文-密文对(题目常给样例)验证还原正确性。

### 本题结构示例

```
RC4(流加密) → 魔改 DES(ECB 逐块) → RC4
```

还原思路:写出 `des_crypt_ecb_dec`(逆轮),把加密数据逐 8 字节块解密;再处理 RC4 流(注意两次 RC4 的密钥与作用位置)。

### 实用提示

- 解密脚本可基于标准库**改源码**而非重写:拷贝 mbedTLS DES 实现,只改被魔改的部分;
- 关注数据流向:程序可能先 RC4 再 DES 再 RC4,解密顺序相反;
- 输出可能是明文 flag 或仍需进一步编码转换。

## 四、VM 类题目(虚拟机保护)

### 场景

程序用自定义字节码解释器(VM)执行核心逻辑,静态分析困难。

### 通用分析流程

1. **定位 VM 主循环**:找 `while` 循环 + 取 opcode + switch/dispatch 表。
2. **还原指令集**:逐一记录 opcode → 操作(栈/寄存器/内存读写、算术、比较、跳转)。
3. **分析数据流**:输入如何进入 VM、加密结果如何比较。
4. **策略选择**:
   - 完整还原字节码程序(工作量大);
   - **动态插桩 + 测信道**(见下);
   - 补丁跳过校验 / hook 比较函数。

### 测信道爆破(本题 ezVM 思路)

若 VM 对**每个输入字符独立加密**(单字符加密),可利用"程序执行路径/执行次数与输入正确性相关"的侧信道:

- 用 **Frida** hook 配置 opcode 的代码处,统计执行次数;
- 对每个字符位置遍历候选字符,记录执行次数;
- **正确字符时执行次数最多**(加密路径走完/比较更深入);
- 逐位爆破得到完整 flag(本题运行约两小时)。

```javascript
// Frida 脚本思路:hook 指定地址,计数
Interceptor.attach(Module.findBaseAddress('xxx').add(0x1234), {
  onEnter(args) { count++; }
});
```

### 要点

- 测信道不限于执行次数:分支跳转次数、比较循环长度、时间差异都可利用;
- 单字符加密是测信道爆破的前提;若是整段加密则优先还原算法。

## 五、字符串混淆与自定义编码还原

### 场景(本题 Jvav)

Java 程序使用混淆器(字符串解密函数 `ALLATORIxDEMO`/`A`/`L`/`d` 等),且用**自定义编码表**(如 64 个 emoji 字符按 6-bit 分组编码)比较输入。

### 分析步骤

1. **还原字符串解密函数**:混淆字符串在运行时通过解密函数还原,把函数逻辑翻译成脚本(Python)即可还原所有字符串。
2. **识别自定义编码**:比较逻辑中出现"字符表 + 位分组"(如 `v3 |= byte << (8 - v4); v4 += 8; while v4 >= 6: 输出 6bit 索引; v3 <<= 6`),本质是自定义 base64。
3. **还原编码表**:把密文字符串映射回表索引(注意 emoji 代理对/变体选择符)。
4. **z3 建模或脚本逆推**:把编码过程写成约束求解(或直接按位流逆推),得到原始字节。
5. **去混淆**:异或密钥、去填充(首字节填充长度、尾部填充串)后还原输入。

### 通用要点

- Java 混淆特征:`ALLATORIxDEMO`、`StackTraceElement` 取调用者、双字符异或轮换;
- 自定义编码与标准 base64 的区别是**字母表不同 + 分组偏移可能魔改**(如 `(v5 >> 4 | v5 << 2) & 0x3F`);
- 编码逆推三要素:字母表、分组位数、填充规则。
