# 补丁与配置管理

> 关键词:补丁管理,漏洞修补,补丁评估,灰度发布,变更窗口,变更审批,回滚预案,补丁台账,覆盖率KPI,CVE,NVD,厂商公告,CMDB,配置漂移,配置审计,云环境补丁,镜像更新,自动伸缩组,虚拟补丁,老旧系统,缓解措施

## 补丁管理的目标

补丁管理(Patch Management)的目标不是"最新",而是"可控":在漏洞风险与业务可用性之间取得平衡,做到**应知尽知、应评尽评、应补尽补、可回滚、可度量**。它属于安全运营的持续性工作,与《基线核查.md》互为表里——基线核查发现补丁差距,补丁流程负责消除。

## 补丁管理全流程

```
识别(漏洞情报) → 评估(影响/兼容/紧急度) → 测试(测试环境)
→ 审批(变更窗口) → 发布(灰度→全量) → 验证 → 台账更新 → 定期复盘
```

## 补丁来源与订阅

| 来源 | 内容 | 订阅方式 |
| --- | --- | --- |
| NVD(美国国家漏洞库) | CVE 编号、CVSS 评分、描述 | NVD API/邮件订阅 |
| CNVD/CNNVD(国内) | 国内漏洞通报,含受影响产品 | 官网/公众号订阅 |
| 厂商公告 | Microsoft Security Response Center、Red Hat CVE 页面、Ubuntu USN、Oracle Critical Patch Update、思科/华为安全公告 | RSS/邮件/厂商门户 |
| 威胁情报 | 已遭在野利用(Exploited in the wild)标记、勒索软件常用漏洞 | 情报平台(如 CISA KEV 目录) |
| 扫描器输出 | 漏洞扫描结果映射到补丁 | 扫描报告对接工单 |

重点关注 **CISA KEV(Catalog of Known Exploited Vulnerabilities)**:被标记"已利用"的漏洞应视为最高优先。

## 补丁评估(三要素)

1. **影响范围**:受影响资产数量、是否在边界/DMZ、是否公网可达;
2. **兼容性**:与业务中间件/依赖/自研代码的兼容风险,厂商是否报告已知问题(如特定补丁导致重启、功能回归);
3. **紧急程度**:
   - 紧急:已公开利用、影响边界资产、CVSS>=9.0 或 KEV 收录 → 应急窗口(24~72 小时);
   - 高:CVSS 7.0~8.9、大范围影响 → 常规月度窗口尽快排期;
   - 中低:CVSS<7.0、本地利用 → 按月度/季度窗口。

评估结论输出《补丁评估单》:补丁号、漏洞、受影响资产清单、风险等级、建议时间窗口、回滚方案。

## 补丁测试环境与灰度发布

- **测试环境**:搭建与生产一致的测试环境(同版本 OS/中间件/应用),先安装补丁执行:功能回归、性能基线、重启验证、监控确认。
- **灰度发布(Canary/Phased Rollout)**:

```
第 1 批(Canary):1~2 台低价值/可替代实例 → 观察 24~48 小时(日志/监控/告警)
第 2 批(试点):每个业务取 10% 实例 → 观察
第 3 批(全量):分批滚动,避免同时重启导致业务中断
```

- 有条件时采用**蓝绿/金丝雀发布**:新补丁版本构建新实例组,流量切换验证后再下线旧组。
- 云环境优先"**打补丁不如换镜像**"(见"云环境补丁")。

## 变更窗口与变更审批

- 定义固定变更窗口(如每周四凌晨),紧急补丁走应急窗口但同样要审批留痕。
- 变更审批要素:变更内容(补丁号/影响范围)、实施人、回滚方案、影响评估、业务方确认、审批人。
- 变更单与补丁台账关联,实施记录(开始/结束时间、结果)自动回写。
- 失败变更立即按回滚预案处理,并复盘改进;高频失败的变更类型需优化测试流程。

## 回滚预案

| 补丁类型 | 回滚方式 | 示例 |
| --- | --- | --- |
| Windows 补丁 | 卸载更新 | `wusa /uninstall /kb:xxxx`、控制面板卸载 |
| RPM 包 | 降级 | `yum downgrade <pkg>-<version>` |
| DEB 包 | 降级 | `apt install <pkg>=<旧版本>` |
| 内核补丁 | 回退内核 | 引导旧内核条目(`grub2-set-default`),再删除新内核包 |
| 应用/中间件补丁 | 回退版本 | 恢复原版本目录备份+重启 |
| 云镜像更新 | 回滚伸缩组 | 伸缩组回退到旧镜像版本/旧启动模板 |

原则:回滚方案在发布前书面化;关键系统发布前保留**配置备份+版本备份**;回滚操作同样走变更记录。

## 补丁台账与覆盖率 KPI

- **补丁台账**:按资产记录 补丁号/漏洞编号/适用资产/状态(待评估、已测试、已发布、已确认、回滚、例外)/发布时间/责任人。
- **核心 KPI**:

| KPI | 定义 | 目标参考 |
| --- | --- | --- |
| 补丁覆盖率 | 已安装/应安装资产比例 | 高危>=98%,整体>=95% |
| 高危补丁及时率 | 高危补丁在时限内完成比例 | 应急 72h、常规 30 天内 100% |
| 平均修复时间(MTTR) | 从漏洞披露到修复完成 | 高危<=7 天 |
| 例外占比 | 例外资产/应补资产 | <=5%,且每季度复审 |
| 回滚率 | 发布后回滚比例 | <=2% |
| 已知未修复高危数 | 台账中待处理高危项 | 趋近于 0 |

- 台账与漏洞扫描数据联动:扫描发现的新漏洞自动生成补丁任务,补丁完成后复扫确认。

## 补丁管理工具链

- **操作系统分发**:WSUS/SCCM(Windows)、Red Hat Satellite/Spacewalk(RHEL)、Ubuntu Landscape/APT 源镜像、Ansible/AWX 批量执行。
- **中间件与容器**:容器镜像扫描(Trivy/Clair/Anchore)+ 镜像仓库策略,阻止含高危漏洞镜像上线。
- **漏洞管理平台**:对接扫描器(如 Nessus/Qualys/绿盟/极光)+ 工单系统,形成"扫描→任务→修复→复扫"闭环。
- **云平台**:云安全中心补丁管理、自动伸缩组滚动更新、镜像版本生命周期管理。

## 应急补丁流程(紧急漏洞)

```
1) 情报确认(利用情况/PoC 公开度/POC 有效性)与影响面圈定;
2) 若厂商已出补丁:评估后按应急窗口发布(可先压测再上);
3) 若厂商未出补丁:先用临时缓解(虚拟补丁/访问控制/禁用功能,见"老旧系统缓解");
4) 补丁发布后 24 小时内验证并更新台账;持续监控利用迹象。
```

## 云环境补丁

- **镜像更新(Golden Image/AMI)**:维护基线镜像(打好补丁的操作系统+中间件),新实例一律从最新基线镜像创建,杜绝"新实例带老漏洞"。
- **自动伸缩组替换(Rolling Replace)**:扩容/滚动更新时用新镜像替换旧实例,而不是对存量实例打补丁:

```
1) 构建新基线镜像(含最新补丁);
2) 更新启动模板/伸缩组镜像版本;
3) 滚动替换实例(先建新实例、验证、再下线旧实例);
4) 缩容策略优先回收旧实例。
```

- 云托管服务(数据库/RDS、K8s 集群、Serverless):由云厂商负责底层补丁,但需关注**版本升级窗口与兼容性**;容器镜像用 Trivy/Clair 扫描后发布。
- 无状态应用:直接替换实例最安全;有状态应用(数据库)需评估升级窗口与备份恢复。

## 配置管理(CMDB 与漂移检测)

- **CMDB(配置管理数据库)**:记录资产、责任人、版本、配置基线、依赖关系;是补丁管理与基线核查的基础数据源。
- **配置漂移检测**:定期将设备/服务器当前配置与 CMDB 基线快照比对,发现未授权变更:

```bash
# 示例:Linux 关键文件哈希基线
sha256sum /etc/ssh/sshd_config /etc/sysctl.conf > baseline.sha256
sha256sum -c baseline.sha256           # 检测变更
# 网络设备:每日抓取 running-config 与基线 diff
```

- **配置审计**:变更审批制(见上)+ 日志审计 + 定期复核 CMDB 数据准确性;审计发现的问题纳入整改闭环。
- 自动化工具:Ansible/Puppet 等配置管理工具"声明式"收敛配置,配置与基线不一致自动修复或告警;云环境用 IaC(Terraform/CloudFormation)管理安全配置。

## 老旧系统无法打补丁时的缓解措施

当系统因 EOL(停止支持)、供应商失联、兼容性等原因无法安装补丁时,按"**虚拟补丁→访问控制→隔离**"三层缓解,并登记例外(见《基线核查.md》例外审批):

1. **虚拟补丁(Virtual Patching)**:
   - WAF 规则封堵漏洞利用特征(针对该 CVE 定制 SQL 注入/XSS/路径遍历规则);
   - IDS/IPS 特征库拦截已知攻击载荷;
   - 主机层 HIDS/RASP 拦截漏洞触发的行为(如反序列化、命令执行);
   - 应用网关层临时禁用受影响功能/接口。
2. **访问控制收敛**:
   - 网络 ACL/防火墙仅放行必要来源与端口,管理接口限堡垒机;
   - 账号最小化、强制强口令+双因素,收紧应用侧权限;
   - 关闭不必要的服务与端口,缩小攻击面。
3. **隔离(Isolation)**:
   - 老系统迁移到独立 VLAN/安全组,与核心业务网络隔离;
   - 仅允许经跳板机/堡垒机访问;必要时单独网段并加严监控;
   - 关键老系统做高可用与备份,降低被攻破后的损失。
4. **升级替代**:制定迁移计划,逐步将老系统替换为受支持版本或等价替代方案;迁移完成前持续监控漏洞利用迹象。

缓解措施有效性需定期验证(渗透测试/规则命中测试),并在基线核查中展示例外项与补偿控制,确保"打不了补丁"不等于"不设防"。

## 常见问题

- **补丁影响业务怎么办?**:先评估,测试环境验证,灰度发布,选低峰变更窗口,备好回滚;绝不因怕影响业务而不打高危补丁,改用临时缓解并排期。
- **服务器太多打不过来?**:按资产价值与暴露面分级,高危优先;用自动化工具(Ansible/SCCM)批量执行;云环境用镜像替换。
- **厂商不再支持(EOL)?**:升级迁移是根本解;过渡期采用虚拟补丁+隔离+访问控制,并登记例外定期复审。
