# 密码学与身份认证

> 关键词:密码学,加密,对称加密,非对称加密,哈希,数字签名,密钥交换,身份认证,授权,访问控制,MFA,SSO,JWT,会话管理,RBAC,零信任,PKI,证书,X.509,CA,TLS,HTTPS,mTLS,国密,密评

## 模块定位

本模块是网络安全知识库的第 08 模块,系统讲解**密码学基础**、**身份认证与访问控制**、**PKI 与 TLS**三大主题。密码学是所有安全机制(加密传输、身份认证、完整性校验、数字签名)的数学地基;身份认证与访问控制决定"谁能进来、能做什么";PKI 与 TLS 则解决"网络上的对方是谁、通道是否加密"这两个根本问题。三者环环相扣,是安全体系的信任根基。

## 关键结论速查

- 加密通道必须用 **AEAD 或 TLS 1.3**:对称加密首选 AES-256-GCM 或 ChaCha20-Poly1305,禁用 ECB、RC4、DES、3DES。
- 非对称加密:新系统优先 **ECC(P-256)/Ed25519**,兼容性场景 RSA-2048 起步;国密场景用 SM2。
- 口令存储一律使用 **bcrypt / argon2id / scrypt**,任何明文、MD5、无盐 SHA 存储都视为安全事故。
- 身份认证:所有高价值系统启用 **MFA**,首选 TOTP 或 FIDO2 硬件 Key,避免短信验证码。
- 传输安全:全站 **HTTPS + TLS 1.2+**,关闭 SSLv3/TLS1.0/1.1,证书走 ACME 自动续期,禁止关闭证书验证。

## 常见问题 FAQ

**Q1:HTTPS 加密了,为什么还会被中间人攻击?**
HTTPS 只加密"通道",不验证"对方是谁"由证书完成。若客户端关闭了证书验证、或证书校验存在漏洞(主机名不匹配、过期证书被忽略),攻击者可伪造证书完成中间人。详见 PKI与TLS.md"证书与 TLS 的常见攻击"。

**Q2:密码存数据库前用 SHA-256 哈希一下就安全吗?**
不安全。无盐 SHA 可被彩虹表/字典攻击秒破,且相同口令产生相同哈希便于批量比对。必须用 bcrypt/argon2id/scrypt 等慢哈希并加盐,详见 密码学基础.md"口令存储规范"。

**Q3:短信验证码作为 MFA 第二因素够吗?**
不够强。短信可被 SIM 卡劫持(SIM swap)与 SS7 攻击,OWASP 建议避免作为唯一第二因素;高价值系统首选 TOTP 或 FIDO2 硬件 Key,详见 认证与访问控制.md。

**Q4:为什么 Let's Encrypt 证书只有 90 天?**
短有效期倒逼自动化续期(ACME),降低私钥泄露与吊销失效的风险窗口——证书吊销机制本身并不即时生效,短生命周期是更可靠的缓解手段,详见 PKI与TLS.md。

**Q5:自签名证书用于生产环境可以吗?**
不可以。自签名证书不在客户端信任库中,客户端会报错或(在关闭验证时)被中间人利用。内部服务应自建内部 CA 统一签发,详见 PKI与TLS.md。

**Q6:JWT 里能存用户手机号、身份证号吗?**
不能。JWT 的 Payload 只是 Base64 编码,任何人都可解码读取;只能放非敏感 claims(sub、exp、角色等),敏感数据走服务端存储,详见 认证与访问控制.md。

**Q7:等保/密评对密码算法有什么要求?**
关键信息基础设施与涉密业务须使用商用密码算法(SM2/SM3/SM4)并通过商用密码应用安全性评估;合规场景的 TLS 需用国密 SSL(GM/T 0024),详见 PKI与TLS.md"国密 SSL"。
