# 认证与访问控制

> 关键词:身份认证,认证因素,知识因素,持有因素,生物因素,口令,密码策略,密码管理器,口令喷洒,MFA,2FA,TOTP,HOTP,短信验证码,硬件Key,FIDO2,WebAuthn,SSO,单点登录,SAML,OAuth2,OIDC,ID Token,Access Token,JWT,签名,过期,会话管理,会话固定,会话劫持,Cookie,Secure,HttpOnly,SameSite,访问控制,RBAC,ABAC,DAC,MAC,最小权限,职责分离,零信任

## 认证(Authentication)与授权(Authorization)

- **认证**:验证"你是谁"(身份真实性)。回答 *Who are you?*
- **授权**:认证通过后决定"你能做什么"(权限)。回答 *What can you do?*
- 二者必须分离:先认证、再授权;授权数据(权限表)与认证凭据分开管理。常见事故是"认证绕过后直接拿到高权限",根源往往是授权判断依赖可伪造字段。

## 认证因素

| 因素 | 含义 | 示例 | 弱点 |
| --- | --- | --- | --- |
| **知识因素**(你知道的) | 记忆中的秘密 | 口令、PIN、安全问题答案 | 易泄露、易猜测、可钓鱼;安全问题答案常可从社交网络推断 |
| **持有因素**(你拥有的) | 物理设备 | 手机(TOTP/短信)、硬件 Key、智能卡、OTP 令牌 | 设备丢失/被盗;短信可被 SIM 卡劫持 |
| **生物因素**(你是什么) | 生理/行为特征 | 指纹、人脸、虹膜、声纹 | 不可撤销(泄露后无法更换);识别率与假阳/假阴权衡 |
| 其他 | 位置、行为上下文 | 登录地点、设备指纹、行为习惯 | 只能作风险信号,不能单独作为强认证 |

- **强认证 = 多因素组合**:单一因素无论多强都面临该因素特有风险,因此高价值系统必须多因素认证(MFA)。
- 生物特征一般只作为"便利因素",与口令/设备组合使用;生物模板在服务端不得明文存储。

## 口令安全策略

### 设计要点(NIST SP 800-63B 为基线)

- **长度优先**:至少 8 位,建议 15 位以上;支持粘贴长口令(为密码管理器生成的长随机串留空间)。
- **不强制周期性更换**:除疑似泄露外,不必每 90 天强制换密——强制换密反而导致用户加数字后缀,降低安全性。
- **检查泄露口令**:登录/注册时对照公开泄露库(如 HIBP)拒绝已泄露口令。
- **拒绝常见弱口令**:如 `123456`、`password`、`admin`、键盘序列。
- **不限制特殊字符组合**:复杂的"必须含大写+小写+数字+符号"规则收益低;若使用,应同时要求足够长度。
- **防枚举**:登录接口限速、验证码、统一错误提示("用户名或口令错误"而非分别提示)、账号锁定需防被利用做 DoS。

### 密码管理器

- 个人与运维人员都应使用密码管理器(如 KeePass、Bitwarden、1Password),为每个站点生成独立高熵口令,主口令用 passphrase(多个随机单词)。
- 好处:消除口令复用(撞库攻击的根本原因)、防键盘记录(自动填充)、便于轮换。

### 口令喷洒(Password Spraying)与防御

- **口令喷洒**:对大量账号尝试少量常见口令(如 `Spring2024!`),利用"账号锁定策略只锁单账号"和低频特征绕过传统防爆破。与"撞库/暴力破解(单账号高频)"相反。
- 防御:① 全账号统一的失败计数与自适应锁定;② 登录源 IP/设备/时间异常检测;③ 强制 MFA(喷洒即使成功也过不了第二因素);④ 监控大范围登录失败模式;⑤ 泄露口令黑名单。

## MFA / 2FA

### 原理

- MFA 要求用户提供**两个及以上不同类别**的认证因素;2FA 是最常见形态(通常 = 口令 + OTP/设备)。
- 核心价值:单一凭据泄露(如口令被钓鱼)不足以登录,显著提高攻击成本。

### 常见第二因素类型对比

| 类型 | 原理 | 优点 | 风险 |
| --- | --- | --- | --- |
| **TOTP**(时间型一次性口令) | 基于 HOTP(RFC 4226)+ 时间戳(RFC 6238),每 30 秒生成 6 位码,密钥存在用户设备 | 离线可用、标准成熟、成本低 | 依赖设备;可被钓鱼网站实时转发(实时钓鱼) |
| **短信验证码** | 服务端下发一次性码到手机 | 普及率高 | **最弱**:SS7 信令漏洞、SIM 卡劫持(SIM swap)、短信嗅探;OWASP 建议避免作为唯一第二因素 |
| **推送通知(MFA Push)** | 手机 App 弹出确认请求 | 体验好 | 疲劳轰炸(MFA fatigue)后可被用户误点 |
| **硬件 Key(FIDO2/WebAuthn)** | 密钥对存在硬件,挑战-应答,绑定站点域名 | **抗钓鱼**、抗中间人、私钥不出设备 | 成本、丢失需备用 Key;手机可用平台通行密钥(Passkey) |
| 邮箱验证码 | 发到邮箱 | 易实现 | 邮箱本身是薄弱环节,仅适合低风险场景 |

### TOTP 要点

- 共享密钥(secret)在服务端与用户设备各持一份;验证时校验时间窗口(通常允许 ±1 个窗口防时钟漂移)。
- 服务端应以**恒定时间比较**验证;防止重放需一次性消费;应支持密钥轮换与恢复流程(备用码)。

### FIDO2/WebAuthn 与 Passkey

- WebAuthn(W3C 标准):浏览器通过公钥密码完成无口令认证,凭证绑定**来源(origin)+ 域名**,钓鱼网站无法重放——这是与 TOTP 的根本区别。
- 现代趋势:手机/系统级通行密钥(Passkey)将 FIDO2 凭证与生物识别结合,兼顾安全与体验。

## SSO 单点登录与联合身份协议

### 概念

- **SSO**:一次登录即可访问多个应用系统(企业内网门户、Google 全家桶等)。
- **联合身份(Federation)**:由身份提供方(IdP)统一认证,服务提供方(SP)信任 IdP 的断言,跨组织共享身份信任。

### 三种主流协议

| 协议 | 定位 | 消息格式 | 典型场景 |
| --- | --- | --- | --- |
| **SAML 2.0** | 企业级 SSO/联合身份 | XML 断言(Assertion),经 HTTP Redirect/POST 传输,可签名 | 企业门户、SaaS 集成、与 Active Directory 联合 |
| **OAuth 2.0** | **授权框架**(非认证!),委托授权 | JSON,Access Token(通常不透明) | 第三方应用申请访问用户资源(如"用微信登录/授权读取头像") |
| **OIDC(OpenID Connect)** | 基于 OAuth 2.0 的**身份认证**层 | JSON,新增 **ID Token**(JWT 格式) | 现代 Web/App 登录("Sign in with Google/GitHub") |

### 流程简介

- **SAML**:用户访问 SP → 重定向到 IdP → IdP 认证后生成签名的 SAML Assertion → 返回 SP → SP 验证签名与受众(Audience)后放行,建立本地会话。
- **OAuth 2.0**(授权码模式):用户访问第三方 App → App 重定向到授权服务器 → 用户登录并授权 → 授权服务器发**授权码**给 App → App 用授权码+Client Secret 换 **Access Token** → App 持 Token 调 API。关键安全点:授权码须绑定 client 与 redirect_uri。
- **OIDC**:在 OAuth 流程之上,授权服务器额外签发 **ID Token(JWT)**,App 验证其签名、`iss`、`aud`、`exp` 后即完成用户认证;用户信息也可从 UserInfo 端点获取。

### 选型与安全要点

- 认证用 OIDC(或 SAML),授权委托用 OAuth 2.0——不要把 OAuth 2.0 当认证协议(经典误区:拿到 Access Token 不等于验证了用户身份)。
- 关键校验:Token/Assertion 的**签名、有效期、issuer、audience、redirect_uri、state 参数(防 CSRF)**。
- 统一使用成熟库(如 Spring Security、Ory、Keycloak),自行解析 SAML/XML 极易中 XXE/签名绕过。

## JWT(JSON Web Token)

### 结构

`Header.Payload.Signature` 三段 Base64URL 编码,以点号分隔:

- **Header**:`{"alg":"RS256","typ":"JWT"}` —— 签名算法。
- **Payload**:声明(claims),如 `sub`(主体)、`exp`(过期时间 Unix 秒)、`iat`、`nbf`、`iss`、`aud`、`jti`。
- **Signature**:`HMACSHA256(base64url(header) + "." + base64url(payload), secret)` 或 RSA/ECDSA 私钥签名。

> 注意:Payload 只是 Base64 编码,**任何人都能解码读取,不可存放敏感数据**(如口令、身份证号);安全性完全依赖签名防篡改。

### 安全使用规范

- **签名算法**:**HS256** 用共享密钥(服务端保管,适用于单一信任方);**RS256/ES256** 用公私钥(适用于多方验证)。优先 RS256/ES256。
- **过期**:必须设置 `exp` 并严格校验;使用短有效期(如 15 分钟~2 小时)+ Refresh Token 刷新机制。
- **常见漏洞**:
  - `alg: none` 绕过:服务端未校验算法白名单,攻击者去掉签名直接伪造(经典漏洞,务必拒绝 `none`);
  - **算法混淆(RS256→HS256)**:攻击者把公钥当 HMAC 密钥用,若服务端不固定算法即被伪造;
  - 弱密钥:HS256 使用可猜测的共享密钥 → 暴力破解签名;
  - 不校验 `exp`/`aud`/`iss`:过期或跨应用 Token 被复用;
  - 密钥泄露/硬编码:JWT 密钥必须走密钥管理,定期轮换;
  - 日志泄露:JWT 出现在 URL/日志中,被中间人/日志采集者窃取。
- 使用签名库时应显式白名单算法(如 `jose`/`jjwt` 的 `JWSAlgorithm` 白名单),并校验 `exp`、`iss`、`aud`。

## 会话管理

### 会话(Session)机制

- 服务端会话:登录成功后服务端生成会话 ID,存于 Cookie;会话状态存服务端(内存/Redis/DB)。
- 无状态替代:JWT 等自包含令牌,但吊销困难(需黑名单),适合短生命周期 API 场景。
- 会话生命周期:创建(登录)→ 活跃(超时滑动)→ 过期(绝对超时)→ 注销(服务端销毁 + 客户端清 Cookie)。

### 会话固定(Session Fixation)

- 攻击者**预先**获取/伪造一个会话 ID,诱导受害者用它登录,随后攻击者复用该会话。
- 防御:登录成功后**无条件轮换会话 ID**(`session_regenerate_id`),并绑定用户/设备指纹;Cookie 使用新 ID。

### 会话劫持(Session Hijacking)

- 窃取有效会话 ID 后冒充用户:途径包括 XSS 偷 Cookie、网络嗅探(明文 HTTP)、恶意浏览器扩展、日志泄露。
- 防御:全站 HTTPS;Cookie 加 `HttpOnly`(防 XSS 读取)与 `Secure`;绑定 IP/UA(需谨慎,移动网络会误伤);异常检测;短会话超时。

### Cookie 属性(必会)

| 属性 | 作用 | 建议 |
| --- | --- | --- |
| `Secure` | 仅 HTTPS 传输,防明文网络窃听 | 必须设置 |
| `HttpOnly` | 禁止 JavaScript 读取(document.cookie),防 XSS 窃取 | 会话 Cookie 必须设置 |
| `SameSite` | 限制跨站请求携带:`Strict`(完全同站)、`Lax`(顶级导航可带,默认)、`None`(需配 Secure) | 优先 `Lax`/`Strict`,防 CSRF |
| `Domain`/`Path` | 限定作用域 | 收敛到最小作用域 |
| `Max-Age`/`Expires` | 有效期 | 会话 Cookie 不设或短设 |
| `__Host-` 前缀 | 强制 Secure、无 Domain、Path=/ | 高安全站点建议使用 |

- 附加:登录态变更(改密、提权)后应吊销旧会话;注销必须同时失效服务端会话与客户端 Cookie。

## 访问控制模型

| 模型 | 全称/核心 | 特点 | 典型场景 |
| --- | --- | --- | --- |
| **DAC** | 自主访问控制:资源所有者自行决定谁可访问 | 灵活但易失控;基于 ACL | 文件系统权限(Windows/Unix 常规文件) |
| **MAC** | 强制访问控制:系统按安全标签(如密级)强制决策,用户不可更改 | 高安全、管理严格;BLP 模型等 | 军用/政务、SELinux、强制策略 |
| **RBAC** | 基于角色:权限赋给角色,用户挂角色 | 管理成本低、易审计,当前最普及 | 企业应用、数据库权限、云 IAM |
| **ABAC** | 基于属性:按主体/资源/环境属性与策略规则动态决策 | 表达力强、细粒度,复杂策略引擎(XACML/PDP) | 云平台细粒度策略、多租户、动态风控 |

- 选型经验:多数业务系统从 **RBAC 起步**,权限粒度不足时引入 **ABAC** 补充(如"仅允许本部门员工在工作时间访问财务数据")。
- 实现注意:服务端强制鉴权,前端隐藏按钮只是体验不是安全;每次请求都做授权判断,杜绝"仅 URL 访问控制"。

## 最小权限与职责分离

- **最小权限(Least Privilege)**:任何主体只拥有完成任务所需的最小权限;管理员账号不用于日常操作,普通用户不开提权通道。
- **职责分离(SoD,Separation of Duties)**:敏感流程拆给多人——如"申请权限的人"与"审批权限的人"分离、"提交发布"与"审批发布"分离,防止单人滥用(内鬼/被攻破账号)。
- 落地:权限申请-审批-定期复审(季度/年度);特权账号(管理员、root)用 PAM/堡垒机托管,操作留痕;云环境用 IAM 角色代替长期密钥。

## 零信任简介

- 核心思想(NIST SP 800-207):**永不信任,始终验证(never trust, always verify)**——不再假设"内网即安全",每个请求(无论来自内网外网)都必须认证、授权、加密,并持续评估风险。
- 关键要素:身份与设备验证(含 MFA)、最小权限、微隔离(东西向流量控制)、持续信任评估(UEBA/风控)、全流量加密(默认拒绝)。
- 落地形态:ZTNA(零信任网络访问)替代传统 VPN;SDP;身份为中心(IdP + 设备目录 + 策略引擎)。
- 与等保 2.0 的关系:等保 2.0 的"可信验证、动态策略"要求与零信任理念一致,国内合规建设常以零信任架构落地。

## 协议对比速查表

| 维度 | SAML 2.0 | OAuth 2.0 | OIDC | JWT |
| --- | --- | --- | --- | --- |
| 本质 | 认证+授权的联合协议 | 授权委托框架 | 认证协议(建在 OAuth 2.0 上) | 令牌格式(不是协议) |
| 数据格式 | XML Assertion | JSON Token | JSON(ID Token=JWT) | Base64URL 三段式 |
| 是否携带用户身份 | 是(Subject/Attribute) | 否(仅授权范围) | 是(ID Token) | 取决于 claims |
| 典型用途 | 企业门户/SaaS 联合 | 第三方授权 API | Web/App 登录 | API 无状态认证 |
| 核心安全点 | 断言签名+受众校验 | code+redirect_uri+state | 校验 ID Token 签名/iss/aud/exp | 算法白名单+exp 校验 |
| 现状 | 存量企业系统仍多 | 事实标准 | 现代登录首选 | 与 OIDC 深度绑定 |
