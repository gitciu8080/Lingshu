# 密码学基础

> 关键词:对称加密,AES,DES,3DES,SM4,分组密码模式,ECB,CBC,CTR,GCM,AEAD,非对称加密,RSA,ECC,SM2,密钥长度,哈希函数,SHA-2,SHA-3,MD5,SHA-1,SM3,盐值,加盐,HMAC,密钥交换,Diffie-Hellman,ECDHE,前向保密,随机数,CSRNG,数字签名,暴力破解,字典攻击,彩虹表,中间人,填充预言,bcrypt,argon2,scrypt,口令存储,密码强度

## 密码学基本概念

### 密码学的安全目标(CIA)

- **机密性(Confidentiality)**:只有授权方才能读取内容,靠**加密**实现。
- **完整性(Integrity)**:内容未被篡改,靠**哈希 / MAC** 实现。
- **真实性(Authenticity)**:内容确实来自声称的发送方,靠**MAC / 数字签名**实现。
- 另含**不可否认性(Non-repudiation)**:发送方无法否认发送行为,靠**数字签名**实现。

### 对称加密与非对称加密

| 对比项 | 对称加密 | 非对称加密(公钥加密) |
| --- | --- | --- |
| 密钥 | 加解密同一把密钥 | 公钥加密、私钥解密(或反之用于签名) |
| 速度 | 快(硬件加速,GB/s 级) | 慢(比对称慢 2~3 个数量级) |
| 用途 | 批量数据加密 | 密钥交换、数字签名、少量数据加密 |
| 典型算法 | AES、SM4、ChaCha20 | RSA、ECC(SM2、Ed25519) |
| 关键难题 | 密钥分发与密钥管理 | 私钥保护、公钥真实性(靠 PKI) |

实践中两者总是组合使用:用非对称算法安全地协商/分发**会话密钥**,再用对称算法加密实际数据,即"混合加密"(如 TLS 中的 ECDHE + AES-GCM)。

### 加密 ≠ 编码

Base64、Hex 只是**编码**(可逆、无密钥),不是加密,不提供任何机密性;真实世界常见把 Base64 误当加密的案例。

## 对称加密算法

### AES(Advanced Encryption Standard)

- 分组大小固定 **128 bit**,密钥长度 128 / 192 / 256 bit,对应轮数 **10 / 12 / 14** 轮。
- FIPS 197 标准(2001),目前全球最广泛使用的分组密码,硬件(AES-NI 指令)加速成熟。
- 实际部署应使用 **AES-256-GCM**(AEAD)等模式,而非裸 AES。

### DES 与 3DES(已淘汰,仅需了解)

- **DES**:56 bit 有效密钥(64 bit 含奇偶校验位),1999 年 EFF Deep Crack 已能在一天内穷举破解;1998 年后不再安全,任何场景禁用。
- **3DES**:对数据执行三次 DES(EDE),有效强度约 112 bit,但因 64 bit 分组受 **Sweet32(2017)生日攻击**影响;NIST 已明确 2023 年后禁用 3DES。存量系统应迁移至 AES。

### SM4(国密分组密码)

- 中国国密标准 **GB/T 32907-2016**,分组 128 bit、密钥 128 bit、32 轮非线性迭代。
- 用于国内合规场景(密评、等保),TLS/SSL 国密套件中的批量数据加密。

### 分组密码工作模式(核心必会)

| 模式 | 特点 | 适用场景 | 主要风险 |
| --- | --- | --- | --- |
| **ECB** | 每块独立加密 | 几乎不适用(仅加密随机性强的单块,如密钥) | 相同明文块产生相同密文块,泄露数据模式,禁用 |
| **CBC** | 每块与前一密文块异或;需随机 IV;加密串行、解密可并行 | 旧系统、文件加密(需配 HMAC) | 无认证(密文可被篡改);填充预言攻击;IV 重用泄露首块模式 |
| **CTR** | 计数器加密后与明文异或,流式;可全并行 | 磁盘加密、旧 TLS 套件 | 无认证;nonce/计数器重用导致异或直接泄露明文 |
| **GCM** | CTR + GHASH 认证,AEAD,一次完成加密+完整性校验 | **现代首选**(TLS 1.2/1.3、VPN、消息加密) | nonce 重用是灾难性漏洞(可恢复密钥流);需防长度扩展滥用 |

> 结论:**任何面向网络传输的对称加密都应使用 AEAD(认证加密)模式**,首选 AES-256-GCM;无 AES 硬件加速的嵌入式场景可用 ChaCha20-Poly1305(RFC 8439)。CBC/CTR 若单独使用必须另配 HMAC,并妥善管理 IV/nonce。

## 非对称加密算法

### RSA

- 安全性基于**大整数分解**难题;支持加密与签名。
- 密钥长度与安全性(参照 NIST SP 800-57):**1024 bit 已不安全**(约 80 bit 对称强度,2010 年后被弃用);**2048 bit ≈ 112 bit 对称强度(当前最低要求)**;3072 bit ≈ 128 bit;7680 bit ≈ 192 bit。
- 新系统建议 3072 bit 或直接转向 ECC;签名使用 **RSA-PSS** 填充而非 PKCS#1 v1.5(更健壮)。

### ECC(椭圆曲线密码)

- 安全性基于**椭圆曲线离散对数(ECDLP)**难题,密钥更短、计算更快:256 bit 曲线(P-256 / secp256r1)约等于 **128 bit 对称强度**,384 bit ≈ 192 bit,521 bit ≈ 256 bit。
- 现代主流:签名用 **Ed25519(RFC 8032,基于 Curve25519)**,性能与安全性俱佳;TLS 密钥交换用 X25519。
- 风险点:必须使用经过审计的标准曲线(如 NIST P-256、Curve25519),自制曲线极易出安全漏洞。

### SM2(国密椭圆曲线)

- 国密标准 **GB/T 32918**,256 bit 素域椭圆曲线,用于签名、密钥交换、加密;国内合规场景替代 RSA/ECDSA。

### 密钥长度对照表

| 对称强度 | RSA | ECC | 状态 |
| --- | --- | --- | --- |
| 80 bit | 1024 | 160 | 已不安全,禁用 |
| 112 bit | 2048 | 224 | 当前最低要求 |
| 128 bit | 3072 | 256(P-256/SM2) | 推荐基线 |
| 192 bit | 7680 | 384 | 高安全/长期 |
| 256 bit | 15360 | 521 | 极高安全 |

## 哈希函数

### SHA-2 与 SHA-3

- **SHA-2**:SHA-256 / SHA-384 / SHA-512(FIPS 180-4),目前通用基线;SHA-256 输出 256 bit,碰撞安全强度 128 bit。
- **SHA-3**:Keccak 算法(FIPS 202,2015),结构与 SHA-2 不同(海绵结构),作为 SHA-2 的备选;SHA3-256 等。
- 哈希特性:固定长度输出、单向(不可逆)、抗碰撞、雪崩效应(输入微变输出大变)。
- 哈希不提供认证——任何知道原文的人都能重算哈希,所以口令/消息完整性必须配合**盐或密钥**(HMAC)。

### MD5 与 SHA-1 为何不安全

- **MD5**(128 bit):1996 年发现碰撞弱点,2004 年王小云团队给出实用的碰撞构造;可用于校验非对抗性数据,但**任何安全场景(签名、口令、证书)一律禁用**。
- **SHA-1**(160 bit):理论强度 80 bit 已低于基线;2017 年 Google/CWI 发布 **SHAttered** 攻击,首次给出真实的选择前缀碰撞(用于伪造 PDF 等);2020 年后主流浏览器与 CA 已全面移除 SHA-1 证书。
- 判断标准:安全哈希输出至少 **256 bit**(SHA-256 及以上)。

### SM3(国密哈希)

- 国密标准 **GB/T 32905-2016**,输出 256 bit,基于 Merkle-Damgård 结构,用于国密 SSL、SM2 签名、密评场景。

### 盐值(加盐)与 HMAC

- **加盐(Salt)**:为每个口令附加一段随机数据再哈希。作用:① 使相同口令产生不同哈希;② 使预计算(彩虹表)与批量破解成本爆炸式上升。盐必须随机、每个用户唯一、长度充足(≥16 字节)。
- **HMAC(哈希消息认证码)**:`HMAC(key, message)`,基于哈希函数 + 共享密钥,同时提供**完整性 + 真实性**;典型 HMAC-SHA256。与普通哈希的本质区别:没有密钥就无法重算,防止伪造。应用:TOTP、TLS、API 签名、JWT(HS256)。

## 密钥交换

### Diffie-Hellman(DH)

- 经典 DH(1976):双方在不安全的信道上协商出共享密钥,安全性基于**离散对数**难题;但**本身不提供身份认证**,中间人可以分别与双方完成交换(必须配合签名/证书)。
- **DHE**:临时 DH 参数,每次会话新生成,提供**前向保密**。
- **ECDHE**:基于椭圆曲线的临时 DH,更高效,是现代 TLS 的主密钥交换方式,提供前向保密。

### 前向保密(Forward Secrecy)

- 含义:即使服务器长期私钥事后泄露,已发生的会话密钥也无法被回溯解密。
- 实现:每次握手用临时密钥对(ephemeral)做 ECDHE,会话密钥不落盘。
- 教训:早期 TLS 使用静态 RSA 密钥交换,私钥泄露即历史流量全部可解;因此 TLS 1.3 已彻底移除静态 RSA 密钥交换,只保留 ECDHE。

## 随机数

- 密码学要求 **CSPRNG(密码学安全伪随机数生成器)**:不可预测、不可由输出反推内部状态。Linux 用 `/dev/urandom` / getrandom,Windows 用 CNG(CryptGenRandom)。
- 常见开发语言:`secrets`(Python)、`crypto.randomBytes`(Node.js)、`SecureRandom`(Java);**禁止用 `random()`/`Math.random()`/`time()` 生成密钥、IV、nonce、盐**。
- 真实事故:2008 年 Debian OpenSSL 因注释掉熵源导致 SSH 密钥可预测(CVE-2008-0166);2013 年 Android 比特币钱包因 ECDSA 随机数重用导致私钥泄露。

## 数字签名原理

1. 发送方对消息做**哈希**,用**私钥**对哈希签名,把 `消息 + 签名` 发出;
2. 接收方用发送方**公钥**验证签名:重算哈希并与签名中恢复的哈希比对,一致则消息未被篡改且确实来自私钥持有者。
- 性质:完整性 + 真实性 + 不可否认性。
- 典型算法:RSA-PSS、ECDSA、Ed25519、SM2。
- 高危教训:ECDSA 要求每次签名使用唯一随机数 k,nonce 重用即可解出私钥(2010 年 PS3 签名密钥被提取、2013 年 Android 钱包事件),这也是为什么现代方案偏爱确定性签名 Ed25519。

## 密码学攻击概念

| 攻击 | 原理 | 防御 |
| --- | --- | --- |
| **暴力破解** | 穷举所有可能密钥/口令,复杂度取决于密钥空间 | 长密钥(≥128 bit)、强口令、速率限制、锁定策略 |
| **字典攻击** | 用常见口令/泄露密码库批量尝试 | 口令策略、泄露口令黑名单、防喷洒 |
| **彩虹表** | 预计算"明文→哈希"链式表,破解无盐哈希极快 | **加盐**(每用户唯一盐使彩虹表失效) |
| **中间人(MITM)** | 攻击者同时冒充通信双方,截获/篡改/转发流量 | 证书验证、密钥固定(pinning)、mTLS、端到端认证 |
| **填充预言(Padding Oracle)** | 利用解密时填充错误反馈逐字节还原明文(针对 CBC) | 用 AEAD(GCM)替代 CBC;统一错误信息;恒定时间比较 |
| 生日攻击 | 利用碰撞概率,攻击哈希/分组密码(如 Sweet32) | 输出/分组 ≥128 bit,弃用 64 bit 分组密码 |
| 侧信道 | 通过时间、功耗、电磁等物理量推断密钥 | 恒定时间实现、掩码;信任审计过的库 |

## 密码强度评估与口令存储规范

### 密码强度评估

- **长度优先于复杂度**:NIST SP 800-63B 建议口令至少 8 位、推荐 15 位以上;强制"大写+小写+数字+符号"组合往往导致用户加 `!1` 尾巴,实际安全性提升有限。
- 评估维度:口令长度、字符集、**是否在已知泄露库中**、是否与用户名/邮箱/常见模式相关。
- 破解时间模型(参考,GPU 集群):8 位纯小写约秒级~分钟级;12 位随机字符约数十年;随机生成的 16 位以上密码在离线暴力下实际不可行。
- 工具:hashcat、John the Ripper 用于自测口令强度(见 `06-安全工具/密码破解工具.md`)。

### 口令存储规范(OWASP Password Storage Cheat Sheet)

| 方案 | 推荐参数(2023 基线) | 说明 |
| --- | --- | --- |
| **Argon2id**(首选) | m=19 MiB(19456 KiB),t=2,p=1 | 内存硬,抗 GPU/ASIC;OWASP 第一推荐 |
| **scrypt** | N=2^17(128 MiB),r=8,p=1 | 内存硬,历史方案 |
| **bcrypt** | cost=12(可调 10~14) | 经典慢哈希,单口令输入最长 72 字节 |
| PBKDF2-HMAC-SHA256 | 迭代 600,000 次 | 仅当兼容旧系统时使用 |

- **禁止**:明文、MD5、无盐 SHA-1/SHA-256、可逆加密存储口令。
- 每个用户独立随机盐(≥16 字节);慢哈希算法自带盐(如 bcrypt 的 salt 内嵌在哈希串中)。
- 口令哈希的慢哈希参数应随硬件逐年上调,并在登录时校验是否需重新哈希升级。
- 验证比较使用**恒定时间比较**,防时序侧信道。

## 算法选择建议表

| 用途 | 推荐选择 | 明确禁用 |
| --- | --- | --- |
| 传输加密(对称) | AES-256-GCM、ChaCha20-Poly1305 | DES、3DES、RC4、ECB 模式 |
| 静态数据加密 | AES-256-GCM / XTS-AES-256(磁盘) | ECB、无认证的 CBC |
| 密钥交换/协商 | ECDHE(X25519)、ECDHE P-256 | 静态 RSA 密钥交换、DHE 512 bit |
| 签名 | Ed25519、ECDSA P-256、RSA-PSS 3072 | MD5、SHA-1、1024 bit RSA、ECB 签名 |
| 哈希 | SHA-256/384、SHA3-256 | MD5、SHA-1(仅限非对抗校验) |
| 消息认证 | HMAC-SHA256、AES-GCM 内建认证 | 裸哈希、无密钥 MAC |
| 口令存储 | Argon2id、scrypt、bcrypt | 明文、MD5、SHA 系列(无慢哈希) |
| 国密合规场景 | SM2(签名/交换)、SM3(哈希)、SM4(加密) | 通用算法用于密评必须替换为国密 |

> 通用原则:① 用**经过审计的标准库**(OpenSSL、libsodium、Java JCE、Go crypto),不自己实现密码算法;② 优先 **AEAD**;③ 密钥管理(生成、轮换、吊销、HSM/KMS)与算法同等重要;④ 一切凭"自定义算法/隐藏实现"保证安全的说法都是反模式(Kerckhoffs 原则:安全性只应依赖密钥保密)。
