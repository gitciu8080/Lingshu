# 数据泄露处置(Data Breach Response)

> 关键词:数据泄露,数据泄漏,数据外泄,Data Breach,泄露发现,暗网监测,止损,吊销凭据,下线服务,影响评估,通知义务,监管通报,个人信息保护法,数据安全法,公关,二次泄露,合规改进,泄露评估清单,通报时限

## 一、泄露发现途径(Detection Channels)

数据泄露(Data Breach)指未经授权访问、窃取、披露或破坏数据的事件。发现途径多样,要建立多渠道监测:

| 发现途径 | 说明 | 常见信号 |
| --- | --- | --- |
| 内部监测 | SIEM/EDR 告警、数据防泄漏(DLP)告警、数据库审计异常 | 大流量外传、异常导出、账号异常访问 |
| 业务反馈 | 用户/客户反馈数据异常 | 收到陌生邮件、账号被盗用、数据被篡改 |
| 外部通报 | 安全厂商、合作伙伴、托管方通知 | 第三方监测到泄露 |
| 暗网监测 | 暗网论坛/泄露站点兜售数据 | 检测到本组织数据被售卖(需订阅暗网监测服务) |
| 监管通知 | 监管机构告知 | 数据出现在泄露数据库中 |

**发现后的第一判断**:是否**真泄露**(区别于误报、测试)、泄露的**数据范围**、是否**仍在泄露**(正在外传还是历史事件)。

## 二、响应行动(Response Actions)

按"**止损 → 评估 → 通知 → 修复 → 复盘**"推进,止损优先。

**1. 止损(立即执行)**:

- **吊销泄露凭据**:立即重置/吊销受影响账号口令、API 密钥、令牌、证书;强制全员改密(MFA 一并重置)
- **下线暴露服务**:临时关闭被攻破的服务、对外接口、数据库对外开放端口;隔离失陷主机与网段
- **阻断外传**:在防火墙/代理/DLP 侧阻断异常外联(封禁 C2 IP、可疑目的地址、大流量通道)
- **封禁攻击者**:封禁攻击源 IP、撤销被滥用会话、踢出异常在线会话
- **保全证据**:先镜像/留存相关日志、数据库导出记录、网络流量,再执行修改操作(与取证原则一致)

> 止损动作**先于**全面排查:哪怕还不清楚完整范围,先把明显的外传通道和失陷凭据处理掉。

**2. 范围与影响评估(Scoping & Impact Assessment)**:

| 评估维度 | 检查项 |
| --- | --- |
| 数据类型 | 个人信息(PII)、财务数据、商业机密、源代码、健康数据、支付数据(PCI)等 |
| 数据规模 | 涉及记录数、文件数、数据库表、是否全量泄露 |
| 涉事系统 | 哪个系统/数据库/账号被攻破,攻击入口与路径 |
| 时间范围 | 泄露起止时间(决定影响人群与通知范围) |
| 敏感性 | 是否含敏感个人信息(如身份证、银行卡、健康、位置)、是否已公开传播 |
| 业务影响 | 客户流失、监管处罚、诉讼、声誉损失、业务中断预估 |

**3. 泄露评估清单(快速打分)**:

```markdown
[ ] 泄露的数据类型是什么?(个人/财务/机密/其他)
[ ] 涉及记录数量级?(百/千/万/百万级)
[ ] 数据是否包含敏感个人信息?(身份/支付/健康/生物特征)
[ ] 数据是否已公开或正在暗网售卖?
[ ] 泄露是否仍在持续?(外传通道是否已阻断)
[ ] 涉事系统是否影响核心业务?
[ ] 是否涉及未成年人/特殊人群数据?
[ ] 是否有法律/合同/监管的通报时限要求?
[ ] 是否已保全证据?是否已通知管理层?
```

得分越高,升级响应级别,启动对外通报流程。

## 三、通知义务(Notification Obligations)

**1. 通报时限对照表**(以中国现行法规为主,结合通用国际实践):

| 对象 | 依据 | 时限要求 |
| --- | --- | --- |
| 监管部门(网信办等) | 《网络安全法》第 42 条、《数据安全法》第 29 条、《个人信息保护法》第 57 条 | **发生个人信息泄露时立即采取补救措施,并按规定通知履行个人信息保护职责的部门**;部分行业规定 1 小时/24 小时内报告(以行业监管细则为准) |
| 受影响用户 | 《个人信息保护法》第 57 条 | 泄露可能危害个人权益时**及时通知个人**,告知泄露情况、风险、补救措施 |
| 行业监管(金融/医疗/运营商等) | 银保监、卫健委、工信部等行业规定 | 金融行业一般要求 2 小时内上报、24 小时内书面报告(以具体办法为准) |
| 执法部门 | 视案件性质 | 涉嫌犯罪时向公安机关报案 |
| 合作伙伴/客户(合同义务) | 合同条款 | 按合同约定时限(常为 24~72 小时) |
| 保险机构 | 网络保险条款 | 通常要求 72 小时内申报,逾期可能拒赔 |

> ⚠️ 时限是硬约束:通报前需完成**影响评估**与**证据保全**,但"等查清楚再报"不可取——先按已知信息通报,后续补充。各国要求不同(如欧盟 GDPR 为 72 小时),跨国业务须按属地法评估。

**2. 通知内容要点**:事件发生时间与经过、泄露数据类型与范围、已采取的补救措施、建议用户采取的保护措施(改密、关注账户)、联系渠道。

**3. 通报注意事项**:

- 通报前内部统一口径,指定发言人
- 记录通报时间、对象、方式,留档备查
- 不得隐瞒、拖延、谎报(监管处罚与声誉双重风险)

## 四、泄露根因排查与修复(Root Cause & Remediation)

**1. 根因排查**:按攻击链还原入口与路径:

- 是否弱口令/爆破(查 4625/4624 登录日志)
- 是否漏洞利用(Web 漏洞、VPN/堡垒机漏洞、0day)
- 是否钓鱼/社工(查邮件日志、终端)
- 是否内部人员(查访问审计、离职账号、特权账号)
- 是否供应链(第三方系统/外包人员)

**2. 修复措施**:

- 修补被利用漏洞、加固入口(改口令策略、上 MFA、收敛暴露面)
- 重置全部受影响与高危账号凭据,清理异常账号与权限
- 完善数据库/API 访问控制与审计、DLP 策略
- 修复后验证(复扫、渗透测试确认入口已堵)

## 五、对外沟通与公关(Communication & PR)

- **内部沟通**:先向管理层与法务汇报,再按需告知员工(防内部恐慌与信息外泄)
- **对外声明原则**:**及时、透明、负责、有行动**——说明发生了什么、影响了什么、正在做什么、用户该做什么
- **口径统一**:所有对外信息经法务与 PR 审核,由指定发言人发布;禁止员工私下对外评论
- **媒体与监管应对**:准备 FAQ、设置用户咨询渠道(客服/邮箱/页面);主动配合监管调查
- **防二次泄露**:对外披露时**不得公布敏感数据细节**(避免公开具体记录、避免提供可被利用的示例),只给必要的受影响人群发个性化通知

## 六、防止二次泄露(Prevent Secondary Breach)

- 泄露数据被公开后,攻击者/围观者可能基于泄露信息进行**二次攻击**(钓鱼、撞库、社工):
- 提醒受影响用户:警惕冒充本组织的钓鱼邮件/电话(泄露信息常被用于精准钓鱼)
- 监控泄露数据的再传播(暗网、群聊、文库),出现大规模公开时评估是否升级通报
- 对泄露样本本身(如数据库转储)做脱敏处理后再用于分析,防止分析过程再次泄露
- 涉事系统在修复完成前保持隔离,防止攻击者"回访"

## 七、复盘与合规改进(Lessons Learned & Compliance)

**1. 复盘内容**:

- 事件报告:完整时间线、根因、影响评估、处置记录(模板见 `应急响应流程.md` 第七章)
- 评估各环节表现:发现速度、止损时效、通知时效、内部协作
- 计算指标:检测时间(MTTD)、响应时间(MTTR)、泄露数据规模变化

**2. 合规与改进项**:

- 对照法规(网络安全法、数据安全法、个人信息保护法、行业办法)与合同条款,核查是否履行全部义务,补齐遗漏
- 改进方向:数据分类分级落地、DLP 与暗网监测部署、特权账号治理、备份与容灾、应急演练(含数据泄露场景)
- 更新预案与联系人清单,把本次 IOC 与手法沉淀进检测规则
- 涉及法律追责的,配合执法与司法程序,保留证据链

**3. 常用法规速查**:

| 法规 | 与数据泄露相关要点 |
| --- | --- |
| 《网络安全法》 | 网络运营者泄露个人信息需立即补救并告知用户,及时向主管部门报告 |
| 《数据安全法》 | 数据处理者发生数据安全事件应依法处置并报告;重要数据泄露从严 |
| 《个人信息保护法》 | 泄露/篡改/丢失个人信息须立即补救并通知监管与个人(第 57 条) |
| 《刑法》253 条之一 | 侵犯公民个人信息罪(涉及犯罪的报案依据) |
| GDPR(欧盟,涉欧业务) | 72 小时内通报监管机构,高风险情形通知数据主体 |

> 处置完成 ≠ 事件结束:合规义务(报告、通知、整改)履行完毕、整改项闭环后,事件方可关闭。
