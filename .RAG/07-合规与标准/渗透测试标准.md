# 渗透测试方法论与标准

> 关键词:渗透测试、PTES、OSSTMM、OWASP WSTG、测试授权书、保密协议、测试报告、红队评估、等保测评渗透、OSCP、CISP-PTE、CEH

## 概述

渗透测试(Penetration Testing)是在**获得授权**的前提下,模拟攻击者的思路与方法,对目标系统进行安全测试,以发现可利用漏洞并验证其实际影响的安全评估活动。它区别于漏洞扫描(自动化发现)与安全审计(合规核查),核心价值是**证明"漏洞是否真的可以被利用、会造成什么后果"**。

渗透测试的开展必须建立在**合法授权**基础上,否则与黑客攻击无异。行业通行的方法论与标准包括:PTES(渗透测试执行标准)、OSSTMM(开源安全测试方法论)、OWASP WSTG(Web 安全测试指南)等,以及配套的授权、合同、保密与报告规范。

## PTES 七个阶段

PTES(Penetration Testing Execution Standard)是业界最常用的渗透测试流程框架,将测试划分为七个阶段:

| 阶段 | 英文 | 核心工作 |
| --- | --- | --- |
| 1. 前期交互 | Pre-engagement Interactions | 明确测试范围、目标、时间、规则与限制,签署授权书与合同(见下文"授权书要素") |
| 2. 情报收集 | Intelligence Gathering | 收集目标公开信息(OSINT):域名、IP 段、子域名、员工信息、技术栈、泄露数据;区分被动(不接触目标)与主动(扫描探测)收集 |
| 3. 威胁建模 | Threat Modeling | 基于情报分析攻击面与潜在攻击路径,确定最可能的攻击向量与测试优先级 |
| 4. 漏洞分析 | Vulnerability Analysis | 结合自动化扫描与人工分析,识别目标存在的漏洞并验证其可利用性、评估影响 |
| 5. 渗透利用 | Exploitation | 实际利用漏洞获取访问权(如 RCE、SQL 注入、弱口令),验证漏洞真实影响 |
| 6. 后渗透 | Post-Exploitation | 权限提升、横向移动、内网信息收集、持久化验证(注意:持久化是否执行需按授权约定);验证被攻陷资产的价值与影响范围 |
| 7. 报告 | Reporting | 汇总发现,按风险等级输出漏洞清单、利用复现步骤、影响分析与修复建议(见下文"报告规范") |

PTES 还提供各阶段的技术指南(如情报收集的详细方法与工具建议),适合作为测试项目的**流程管理与文档框架**。

## OSSTMM 简介

OSSTMM(Open Source Security Testing Methodology Manual,开源安全测试方法论)由 ISECOM 发布,是一套基于**科学方法**、强调**可度量与可重复**的安全测试方法论。要点:

- 将测试对象按**通道**划分:人力(Human)、物理(Physical)、无线(Wireless)、电信(Telecommunications)、数据网络(Data Networks);
- 强调测试的**操作安全(OpSec)**与测试范围(Rav, Risk Assessment Vectors)管理;
- 输出可量化的指标:**RAV(实际安全漏洞, Actual Security)** 与 **RCAV(潜在安全漏洞, Potential Security)**,用数字呈现目标的安全态势;
- 与其他方法论相比,OSSTMM 更偏重**过程规范与结果可复现**,适合需要严格审计记录的测试项目,但在国内实际项目中使用不如 PTES/OWASP 普及。

## OWASP Testing Guide(WSTG)

OWASP Web Security Testing Guide(WSTG,现行 v4.2,正演进至 v5)是 **Web 应用安全测试**的事实标准,按测试类别组织,包含 19 个测试类别、200+ 个测试用例。主要类别:

| 测试类别 | 关注点(典型测试项) |
| --- | --- |
| 信息收集 | 搜索引擎发现、指纹识别、目录枚举、子域/Web 资产发现 |
| 配置与部署管理 | 默认账号、测试/备份文件、错误处理暴露、管理接口暴露 |
| 身份管理 | 用户枚举、账户注册流程、账户锁定 |
| 认证测试 | 弱口令、暴力破解、会话固定、多因素绕过 |
| 授权测试 | 水平/垂直越权、IDOR、强制浏览 |
| 会话管理测试 | Cookie 属性、会话过期、CSRF |
| 输入验证测试 | SQL 注入、XSS、命令注入、文件上传、SSRF、XXE |
| 错误处理 | 信息泄露、堆栈跟踪暴露 |
| 加密测试 | 弱加密、TLS 配置、敏感数据明文传输 |
| 业务逻辑测试 | 支付流程篡改、限额绕过、竞态条件 |
| 客户端测试 | DOM XSS、点击劫持、跨域策略 |
| API 测试 | REST/GraphQL 认证与授权、参数校验、批量分配 |

WSTG 每个测试用例均给出目标、方法、测试工具与通过判据,可直接作为 Web 渗透测试的**测试用例清单**与报告依据。

## 渗透测试授权书要素

授权书(Authorization Letter / Rules of Engagement)是渗透测试**合法性的核心文件**,必须由目标系统**所有权方或获得其书面授权的主体**签署。应包含要素:

| 要素 | 说明 |
| --- | --- |
| 测试范围 | 明确的 IP 段、域名、URL、系统/应用清单、测试账号;排除项(第三方系统、未授权资产) |
| 测试时间 | 起止时间与每日测试时段;是否允许非工作时间、是否允许周末 |
| 测试类型与深度 | 黑盒/灰盒/白盒;是否包含内网测试、社工、钓鱼、物理渗透;是否允许漏洞利用与权限提升 |
| 禁则(限制条款) | 禁止 DoS/DDoS、禁止破坏数据、禁止勒索类行为、禁止对无关第三方系统测试、禁止安装持久化后门(如需验证须约定) |
| 应急联系人 | 甲方安全负责人/运维值班电话、乙方项目负责人;发现严重危害(如可入侵生产库)时的上报路径与叫停机制 |
| 应急与免责 | 测试导致业务影响的处理流程;双方责任划分 |
| 保密与数据 | 测试数据、漏洞信息的保密约定(可与保密协议并列) |
| 双方签章 | 甲方授权人签字/盖章、乙方签字,注明日期 |

> 授权书建议与《测试合同》《保密协议》配套签署,授权范围越明确,事后争议越少。

## 测试合同与保密协议要点

- **测试合同**(服务合同):服务内容与交付物(测试报告、复测);项目周期与里程碑;费用与支付;双方权利义务;责任与赔偿条款(明确因测试造成的损失界定);知识产权(测试结果、报告归属);人员(测试人员资质、驻场安排);违约责任与争议解决。
- **保密协议(NDA, Non-Disclosure Agreement)**:双向保密,保护范围包括:测试发现的漏洞细节、系统架构与配置、源代码、业务数据、报告内容;保密期限(常约定 1~3 年或永久);保密义务(不复制、不泄露、测试后清除本地数据);违约责任。
- **数据保护**:测试涉及的真实数据(生产数据、个人数据)的处理规则,必要时采用脱敏/沙箱环境测试;符合《个人信息保护法》等要求。
- **复测与整改条款**:约定漏洞修复后的复测范围、次数与费用,保证整改闭环。

## 渗透测试报告规范

一份合格的渗透测试报告应分层呈现、可执行:

| 章节 | 读者 | 内容要点 |
| --- | --- | --- |
| 执行摘要 | 管理层 | 测试概况、总体风险评级(高/中/低)、关键发现 Top 风险、结论与整改优先级 |
| 测试范围与方法 | 技术审核 | 范围、时间、测试类型、工具清单、方法论(PTES/WSTG 等) |
| 风险统计 | 管理层 | 漏洞数量分布(按风险等级/类型)、复现率、系统分布 |
| 漏洞详情 | 技术团队 | 每个漏洞:编号、风险等级(参照 CVSS 评分)、漏洞描述、复现步骤(含截图/请求包)、影响分析、修复建议 |
| 附录 | 技术团队 | 测试环境信息、工具输出摘要、未利用但需关注的观察项、二次测试建议 |

报告规范要点:漏洞风险等级分级标准明确(如按 CVSS v3 分级 严重/高/中/低);复现步骤可被开发人员独立验证;**修复建议具体到配置或代码层面**;对"无法复现"与"已验证可利用"明确区分;报告版本与密级标注,按保密协议管控分发。

## 红队评估与渗透测试的区别

| 维度 | 渗透测试 | 红队评估(Red Team) |
| --- | --- | --- |
| 目标 | 发现并验证漏洞 | 检验整体防御体系(人员、流程、技术)能否阻止真实攻击者 |
| 范围 | 限定的目标与时间 | 可覆盖整个组织、多攻击面,时间通常更长(数周~数月) |
| 对抗性 | 低,通常不规避防御 | 高,主动规避检测、模拟真实 APT 战术(TTP) |
| 方式 | 以漏洞利用为主 | 综合社工、钓鱼、物理渗透、供应链、横向移动、持久化 |
| 输出 | 漏洞清单+修复建议 | 攻击路径故事线+防御缺口+提升建议,常配套蓝队演练(紫队) |
| 风险 | 可控,按授权书禁则执行 | 较高,需严格 ROE 与叫停机制 |

两者互补:渗透测试是"点"的验证,红队是"面"的对抗检验;一般先做渗透测试整改,再开展红队评估检验真实防御。

## 合规驱动型测试

- **等保测评中的渗透**:等级保护测评(GB/T 28448-2019)的"测试"环节包含漏洞扫描与渗透测试,作为核查安全控制有效性的手段,尤其针对三级及以上系统;渗透测试结果直接影响高风险项判定与测评结论。需注意:等保测评的渗透测试由**测评机构在授权范围内**执行,重点是验证测评对象的安全控制,不同于独立的深度渗透项目。
- **金融行业渗透要求**:金融监管对银行业金融机构的网络安全提出持续安全评估要求,如定期开展渗透测试与攻防演练;相关行业规范(如网上银行安全通用规范、金融业等级保护实施指引等)明确要求对网上银行、移动金融等重要系统开展渗透测试,频率通常不低于每年一次,重大版本上线前也须测试。
- **其他监管场景**:关键信息基础设施(CII)运营者按要求定期开展安全检测评估(含渗透测试);供应链审查、等保三级备案、ISO 27001 认证审核、上市合规尽调等场景常要求提供近期渗透测试报告。
- 合规驱动测试的注意点:满足合规最低频率之外,应结合重大变更、重大事件开展;测试范围要与合规要求的"应测对象"对齐,报告留档备查。

## 测试人员认证概览

| 认证 | 颁发机构 | 定位与特点 |
| --- | --- | --- |
| OSCP | OffSec(Offensive Security) | 国际最受认可的一线渗透测试认证;基于 Kali 的 PEN-200 课程;**24 小时实操考试**,须真实攻破多台靶机并撰写渗透报告,强调实战能力 |
| CISP-PTE | 中国信息安全测评中心 | 注册渗透测试工程师;国内政企招投标认可度高;偏重 Web 渗透、内网渗透、漏洞挖掘的实操考试 |
| CISP-PTS | 中国信息安全测评中心 | 注册渗透测试专家;PTE 的高级进阶,要求更强的综合渗透与漏洞分析能力,考试难度更高 |
| CEH | EC-Council | 注册道德黑客;覆盖面广、偏理论,常作为入门与合规"敲门砖",实操深度弱于 OSCP |
| 其他参考 | OffSec(OSWE)、CREST(CCT)、GPEN(GIAC) | OSWE 偏 Web 源码审计、CREST 受金融行业认可、GPEN 偏渗透测试通用技能 |

选择建议:国内从业者与投标项目优先 CISP-PTE/PTS;追求国际认可与实战口碑选 OSCP;入门选 CEH;认证只是起点,持续跟靶场(如 HackTheBox、VulnHub)与实战积累才是核心。
