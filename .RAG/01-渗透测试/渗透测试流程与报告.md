# 渗透测试流程与报告(Penetration Testing Process & Reporting)

> 关键词:渗透测试流程, 授权书, PTES, 测试范围, Rules of Engagement, 黑盒测试, 白盒测试, 灰盒测试, 渗透测试报告, CVSS, 风险评级, 复测, 交付物, 保密协议, NDA

## 概述

一次规范的渗透测试 = **合规授权 + 标准流程 + 高质量报告**。本章覆盖:授权与合规(书面授权书要素)、PTES 七个阶段、测试范围与规则(Rules of Engagement)、测试方法选择(黑盒/白盒/灰盒)、报告结构与风险评级(CVSS)、复测与交付物、保密协议。

> ⚠️ **合规底线**:没有书面授权的渗透测试即属违法(我国《网络安全法》《刑法》285/286 条均规制未授权侵入与破坏计算机信息系统)。本章流程是「合法渗透测试」的作业规范。

## 授权与合规

### 书面授权书(Authorization Letter)要素

授权书是渗透测试的**法律依据**,必须包含以下要素:

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| 授权主体 | 资产所有者/甲方单位名称(公章) | XX 科技有限公司 |
| 受托方 | 测试执行方名称 | XX 安全服务公司 |
| 测试对象 | 明确 IP/域名/系统/应用清单 | `www.example.com`、`10.0.0.0/24` |
| 测试范围 | 允许测试的网段、系统、时间窗口 | 2025-01-01 至 2025-01-15,每日 09:00-21:00 |
| 测试方法 | 允许使用的技术(是否含爆破/DoS/社工) | 允许漏洞利用,禁止 DoS |
| 明确禁止项 | 不可触碰系统(生产数据库等)、禁止行为 | 禁止对支付系统实施破坏性测试 |
| 应急联络 | 双方紧急联系人、异常处理流程 | 发现高危漏洞 2 小时内电话通报 |
| 保密条款 | 双方保密义务、数据处置 | 测试数据仅限本次项目使用 |
| 签署 | 双方签字盖章、日期 | — |

**合规要点**:
- 授权书必须由**资产所有者**签署(IT 部门≠法定所有者,需公司层面)。
- 授权范围之外的资产即使同网段也不得测试。
- 测试产生的数据(抓包、凭据、报告)按保密协议处置,项目结束后销毁或归还。
- 涉及个人信息/隐私(摄像头、邮件)的测试需额外评估合规风险。

## PTES 七个阶段

PTES(Penetration Testing Execution Standard)是最通用的渗透测试流程标准:

| 阶段 | 英文 | 核心工作 | 输出 |
| --- | --- | --- | --- |
| 1. 前期交互 | Pre-engagement Interactions | 商务对接、授权书、RoE、范围确认 | 授权书、测试计划 |
| 2. 情报收集 | Intelligence Gathering | OSINT、被动/主动信息收集(见《信息收集.md》) | 资产清单、攻击面 |
| 3. 威胁建模 | Threat Modeling | 分析资产价值、攻击面、潜在攻击路径、优先级 | 威胁模型、测试优先级 |
| 4. 漏洞分析 | Vulnerability Analysis | 扫描、枚举、版本匹配、CVE 关联(见《漏洞扫描与枚举.md》) | 漏洞清单 |
| 5. 渗透利用 | Exploitation | 利用漏洞获取权限、验证危害(见《Web/主机/内网/无线各篇》) | 漏洞利用证明 |
| 6. 后渗透 | Post-Exploitation | 提权、横向移动、数据访问证明、权限维持(授权演练) | 影响评估 |
| 7. 报告 | Reporting | 汇总发现、风险评级、修复建议、复测 | 最终报告 |

**阶段要点**:
- 阶段 2-5 可循环迭代:利用失败 → 补充信息收集 → 重新分析。
- 威胁建模决定投入:核心资产(域控、数据库、交易系统)优先测试。
- 报告阶段贯穿全程:每发现一个漏洞即时记录证据,避免事后补记失真。

## 测试范围与规则(Rules of Engagement, RoE)

RoE 是与甲方约定的**行为准则**,防止测试失控:

```text
RoE 核心条款示例:
1. 范围:允许测试资产清单(附 IP/域名);禁止:核心生产数据库、第三方托管系统。
2. 时间:工作日 09:00-21:00 测试;扫描器限速(Nessus 并发≤X,nmap -T≤3)。
3. 允许的技术:端口扫描、漏洞利用、弱口令尝试(限速);禁止:DoS、社工、破坏性 payload。
4. 敏感操作:涉及删除/写入/锁定的操作需提前报备。
5. 应急响应:触发甲方告警时,甲方可随时暂停测试;双方 24 小时联络畅通。
6. 数据处置:获取的凭据/数据仅用于证明危害,项目结束销毁。
7. 越界处理:意外发现范围外漏洞 → 记录但立即停止,通报甲方评估。
```

**范围定义常见陷阱**:
- 云资产归属不清(子域名指向第三方服务)需提前确认。
- CDN/负载均衡导致源站真实 IP 需在 RoE 中补充说明。
- 内网渗透的横向范围需单独授权(见《内网渗透.md》)。

## 测试方法选择(黑盒 / 白盒 / 灰盒)

| 维度 | 黑盒测试(Black Box) | 灰盒测试(Gray Box) | 白盒测试(White Box) |
| --- | --- | --- | --- |
| 信息掌握 | 无内部信息,仅公开渠道 | 部分信息(如普通账号、架构图) | 全部信息(源码、配置、文档) |
| 模拟对象 | 外部攻击者 | 已获低权限的内部人员/攻击者 | 内部人员/审计视角 |
| 测试深度 | 浅,重攻击面发现 | 中,覆盖已授权功能 | 深,覆盖代码级问题 |
| 周期成本 | 长/高 | 中 | 短(相对)但需源码配合 |
| 适用场景 | 外部暴露面评估 | 常规年度测试 | 合规审计、上线前代码安全 |

**选型建议**:
- 外部资产/新系统上线 → 黑盒。
- 常规年度渗透(兼顾效率与深度)→ 灰盒(提供普通账号)。
- 等保测评、代码审计、重大系统上线 → 白盒。
- 实战中常组合:黑盒为主,关键系统辅以白盒/灰盒补充。

## 报告结构

报告是渗透测试的**核心交付物**,应让管理层看得懂风险、让技术人员能复现与修复。

### 标准报告结构

```text
1. 封面:项目名称、甲方/乙方、时间、密级
2. 目录
3. 摘要(Executive Summary)
   - 项目概述:范围、方法、周期
   - 总体结论:安全状况评级(如 良好/一般/较差)
   - 风险统计:Critical/High/Medium/Low 数量
   - 亮点与优先事项:TOP 风险 3-5 条(管理层视角)
4. 测试概述
   - 测试范围与方法(黑盒/灰盒)
   - 测试时间、工具清单、参与人员
   - 局限性说明(时间、范围、技术限制)
5. 风险评级体系说明(CVSS 等)
6. 发现列表(Findings)
   - 按严重级别排序的漏洞清单(含编号)
7. 每个漏洞详情(见下)
8. 复测结果(整改后)
9. 附录:测试证据、资产清单、参考资料
```

### 单个漏洞详情模板

```text
漏洞编号:VULN-001
漏洞名称:XX 系统 SQL 注入(报错注入)
风险评级:高危(CVSS 8.6)
涉及资产:http://www.example.com/product?id=1
漏洞描述:参数 id 未参数化,可注入 SQL 语句读取数据库内容
复现步骤:
  1) 访问 http://www.example.com/product?id=1'
  2) 响应返回 SQL 语法错误,暴露 MySQL 版本信息
  3) 使用 sqlmap 确认可读取 users 表(见附录截图)
影响分析:可导致数据库数据泄露(约 10 万用户记录),潜在撞库与数据滥用风险
修复建议:
  1) 使用参数化查询/预编译语句
  2) 数据库账号最小权限,关闭 file 权限
  3) 部署 WAF 作为纵深防御
参考:OWASP SQL Injection Prevention Cheat Sheet;CWE-89
```

### 风险评级:CVSS 使用要点

- CVSS v3.1 评分向量由 8 个指标组成,使用官方计算器(https://www.first.org/cvss/calculator/3.1)。
- 常用指标:AV(攻击向量:N 网络/A 相邻/L 本地)、AC(复杂度)、PR(所需权限)、UI(用户交互)、C/I/A(机密性/完整性/可用性影响)。
- **评级修正**:CVSS 是通用评分,报告应按业务影响调整:如核心交易系统即使 CVSS 中危也应上调实际风险;隔离网段内的低危漏洞可下调。
- 结合 EPSS/KEV(见《漏洞扫描与枚举.md》)给出修复优先级(P0-P3)。

## 复测与交付物

### 复测(Remediation Verification)

```text
复测流程:
1. 甲方按报告修复漏洞,提供修复说明(版本/配置变更)
2. 乙方对每个已修复漏洞逐一复测(重点:原利用路径是否已封堵)
3. 复测方式:重放原 PoC、重扫相关模块、人工确认
4. 输出:复测报告(修复状态:已修复/部分修复/未修复/误报剔除)
5. 遗留风险:未修复漏洞明确风险等级与负责人、计划修复时间
```

**复测注意**:
- 修复验证要验证**根因修复**而非表面绕过(如只加 WAF 规则但未修代码)。
- 部分修复可能引入新漏洞(如加过滤器绕过),需回归测试。
- 复测范围与授权书一致,不得扩大。

### 交付物清单

| 交付物 | 内容 | 接收方 |
| --- | --- | --- |
| 渗透测试报告 | 完整报告(发现+修复建议) | 甲方安全/IT 部门 |
| 复测报告 | 整改后复测结果 | 甲方 |
| 原始扫描数据 | XML/CSV 扫描结果 | 甲方(存档) |
| 演示材料(可选) | 汇报 PPT:风险概览与优先事项 | 管理层 |
| 漏洞工单(可选) | 漏洞跟踪系统条目 | 甲方 |

## 保密协议(NDA)与数据安全

1. **双方保密义务**:乙方对测试中发现的信息(漏洞、凭据、业务数据)承担保密义务;甲方对测试方法与工具保密。
2. **数据最小化**:仅收集证明漏洞所需的证据(截图、请求包),不批量下载业务数据。
3. **凭据处置**:测试获取的密码哈希、明文凭据加密存储,项目结束后删除(报告保留必要脱敏证据)。
4. **报告分级**:报告按内部机密管理,分发范围受限;电子版加权限控制。
5. **日志留存**:乙方留存测试日志备查(供甲方审计),周期按约定(如 1 年)。
6. **第三方合规**:涉及等保/行业监管的测试,报告格式需满足监管要求(如等保测评报告格式)。

## 常见问题(FAQ)

- **Q:扫描就算渗透测试吗?** A:不算。渗透测试必须包含人工分析与利用验证,扫描只是其中一步。
- **Q:测试中发现高危漏洞怎么办?** A:按 RoE 应急流程立即通报甲方,可暂停测试,评估影响后再继续。
- **Q:报告该写多详细?** A:可复现(步骤到命令与 URL)、可修复(建议到具体措施)、可决策(风险与优先级)。
- **Q:误报怎么处理?** A:报告前逐一复现核实;无法复现的降级为「待确认」或剔除,并在报告中说明。
- **Q:测试失败(无漏洞)怎么办?** A:同样交付报告,说明测试过程、覆盖范围与局限性,这本身就是合规有效的交付。
