# 灵枢（Lingshu）核心技术特点

> 多智能体授权安全测试系统技术亮点、创新设计与评比说明

## 1. 技术定位

灵枢不是单一大模型加命令行工具的简单封装，而是一套以 AgentScope 2.0.6 为基础、面向授权安全测试与 CTF 场景的多智能体工程平台。

系统同时覆盖：

- 多智能体任务规划与协作。
- 网络目标和本地附件两种任务路由。
- 人工审批和动态授权范围控制。
- 专业安全工具与 MCP 工具集成。
- RAG 知识库和长期任务记忆。
- 会话级 Workspace、检查点和崩溃恢复。
- React/Vite 实时可视化 WebUI。
- 多用户、超级管理员和模型 API 管理。
- Markdown 总结和中文 PDF 报告。

一句话概括灵枢的技术特点：

> 将大模型的规划与推理能力，放入一个具有专业分工、确定性安全边界、证据闭环和完整生命周期管理的多智能体系统中。

## 3. 多智能体分层架构

### 3.1 战略、战术、执行三层分离

```text
战略层：Brain
  └── 理解目标、查询知识、制定结构化计划

战术层：Orchestrator
  └── 调度专家、推进阶段、审批、范围管理、任务收尾

执行层：Recon / ArtifactTriage / Analysis / Attack / Reverse
  └── 收集证据、专业研判、验证和逆向分析

治理层：ScopeAuditor
  └── 独立审核新增 IP/网段授权

交付层：Summary
  └── 汇总完整会话并生成报告
```

这种分层使每个 Agent 的输入、工具和权限与职责匹配，避免单 Agent 同时承担计划、执行、审批和总结而导致决策失控。

### 3.2 唯一状态决策者

灵枢规定只有 Orchestrator 可以修改 MissionState。

执行 Agent 只能返回结果：

- Recon 返回侦察报告。
- Analysis 返回漏洞研判。
- Attack 返回验证与利用报告。
- Reverse 返回静态/动态分析报告。
- ScopeAuditor 返回批准或拒绝意见。

Orchestrator 根据当前阶段、证据和审批结果决定是否写入任务状态。

这一机制是系统区别于“多个 Agent 自由聊天”方案的重要架构特征。

## 4. 状态机驱动的任务治理

### 4.1 显式阶段

```text
PLANNING
   ↓
RECON
   ↓
ANALYSIS
   ↓ 人工审批
EXPLOITATION
   ↓
POST_EXPLOITATION
   ↓
COMPLETED
```

异常或用户终止分别进入 FAILED、CANCELLED。

### 4.2 合法迁移白名单

阶段迁移不是由模型自由输出，而是由确定性 `_ALLOWED_TRANSITIONS` 白名单控制。非法迁移直接抛出错误。

状态机带来的价值：

- 防止未侦察直接攻击。
- 防止执行 Agent 自行宣布任务完成。
- 防止终态任务再次执行工具。
- 支持证据不足时回退补充侦察。
- 支持崩溃恢复时确定当前安全位置。

## 5. 人机协同审批

### 5.1 多方案审批

首次进入 EXPLOITATION 前，Orchestrator 根据真实侦察依据生成 2～3 个候选方案。

用户可以：

- 选择执行方案。
- 调整方案优先级。
- 拒绝本轮攻击。
- 要求补充侦察或调整计划。

### 5.2 双重审批闸门

审批不仅存在于提示词中：

1. Orchestrator 被要求主动调用审批工具。
2. `dispatch_attack` 在代码层再次检查 `exploitation_approved`。

即使模型跳过审批请求，也无法直接进入攻击阶段。

### 5.3 审批持久化

审批结果和用户选定方案保存在 MissionState：

- `exploitation_approved`
- `approved_attack_plan`

任务恢复后不会重复询问已经完成的审批，也不会丢失用户调整后的方案顺序。

## 6. 动态授权范围

### 6.1 ScopeRegistry

系统维护结构化授权范围：

- 基础目标主机。
- 已授权 IP。
- 已授权主机名。
- 经审批增加的私有 IP。
- 经审批增加的网段。
- 每次扩展的证据和批准者。

### 6.2 ScopeAuditor 独立审核

当工具发现新的内网 IP 时，Orchestrator 必须将证据交给 Grace－授权范围审计专家。

审核规则包括：

- 公网 IP 默认拒绝。
- 证据中必须明确出现申请 IP。
- 证据必须来自可信工具输出。
- 单 IP 证据不能无理由扩大成大网段。

### 6.3 scoped_shell 确定性约束

所有本地网络命令在执行前检查：

- 命令中出现的 IPv4 地址是否已授权。
- 网络工具是否显式包含当前目标。
- 是否命中破坏性命令规则。
- 命令长度和字符是否合法。

安全边界由代码控制，不依赖模型自律。

## 7. 证据驱动与审计哈希链

### 7.1 证据闭环

灵枢要求任务结论能够回溯到：

- 用户输入。
- 工具调用参数。
- 工具返回结果。
- Workspace Artifact。
- 人工审批。
- 状态迁移事件。

计划项标记 completed 时必须提供 evidence，防止模型无证据完成任务。

### 7.2 审计事件

每个 AuditEvent 保存：

- 单调递增序号。
- 时间戳。
- 行为者。
- 动作。
- 当前阶段。
- 结构化详情。
- 前一事件哈希。
- 当前事件哈希。

### 7.3 SHA-256 前向哈希链

事件使用规范化 JSON 计算 SHA-256，并连接前一事件哈希。历史记录被修改后，后续链路校验会失败。

这使灵枢具备比普通聊天记录更强的审计可信度。

## 8. 严格工具调用协议

### 8.1 StrictJSONToolkit

模型工具参数在执行前必须通过：

- 严格 JSON 解析。
- 顶层 Object 检查。
- 重复字段检测。
- 非标准数字检测。
- JSON Schema 验证。

### 8.2 一次修复、二次熔断

工具参数首次错误时只允许一次短提示修复。第二次仍失败：

- 不执行工具。
- 保存工具名、错误、参数预览和参数哈希。
- 写入审计事件。
- 进入安全收尾或备用模型策略。

### 8.3 原子计划提交

Brain 默认使用 SubmitPlan 一次提交完整计划：

- 全部校验成功后才写入。
- 任一条目失败不会留下半份计划。
- 减少本地模型长工具参数损坏概率。
- 保留逐条 AddPlan 兼容模式。

## 9. 重复动作识别与自动熔断

系统根据以下内容计算动作指纹：

```text
动作类型 + 授权目标 + 规范化参数 + 任务描述 + 证据版本
```

同一动作在无新证据的情况下重复执行会被拒绝。相同动作与相同错误达到阈值后，系统自动熔断对应计划项。

技术价值：

- 防止 Agent 无限循环。
- 防止只改写自然语言后重复调用。
- 减少无意义 Token 和工具成本。
- 强制 Agent 补充证据或切换策略。

## 10. Network 与 Artifact 双路由

### 10.1 网络目标

NetworkRecon 仅进行低影响侦察：

- 端口和服务指纹。
- HTTP HEAD/GET。
- 页面源码和响应头。
- 明确 CVE 编号的有限公开情报查询。

禁止在侦察阶段发送利用 Payload 或执行远程命令。

### 10.2 文件目标

ArtifactTriage 对本地附件进行静态分流：

- ELF/PE/APK/PCAP/镜像/脚本识别。
- checksec、readelf、strings、capinfos 等基线分析。
- OCR 图片识别。
- TonyEnc 固定格式识别和解码。
- 自动题型分类。

文件目标不会错误地走网络扫描路径。

## 11. Workspace v2 会话隔离

### 11.1 用户与会话级物理隔离

工作区路径由 `(user_id, session_id)` 确定：

```text
WorkDir/v2/sessions/u{user_id}/{session_id}/
```

每个会话独立保存：

- 上传输入。
- Agent 角色上下文。
- 工具 Artifacts。
- PDF 报告。
- Mission 检查点。
- MCP 与 Workspace 数据。

### 11.2 内容寻址 Blob Store

上传文件按 SHA-256 保存：

```text
WorkDir/v2/blobs/{sha256}/source
```

同一文件可以跨会话复用底层 Blob，同时会话内仍保持独立路径。

### 11.3 工具输出 Artifact 化

长命令输出不全部塞进模型上下文，而是：

- stdout/stderr 流式写入 Artifact 文件。
- 计算字节数和 SHA-256。
- 模型只接收尾部摘要与相对路径。
- 前端和报告仍可引用完整证据。

这一设计同时优化上下文长度、内存使用和证据保真度。

## 12. 安全检查点与崩溃恢复

检查点保存：

- 当前任务阶段。
- 结构化计划。
- 审批状态。
- 活动计划项。
- 挂起动作。
- 动作指纹和重试次数。
- Agent 上下文引用。

恢复状态包括 fresh、running、resumable、uncertain 和 terminal。

系统不会盲目重放可能已经产生副作用的工具调用；不确定动作需要人工确认。

## 13. AgentScope 官方中断机制

用户发送补充情报时，系统取消正在执行的 AgentScope `reply_stream` Task，而不是等待模型自然结束。

同时处理：

- 嵌套 Agent task。
- 正在运行的工具协程。
- Shell 进程组。
- 部分模型输出。
- 未发送消息队列。
- 下一轮 Orchestrator 情报注入。

这使长任务具备真正的实时人工介入能力。

## 14. 动态 Skills 路由

项目保存：

- 11 组核心 CTF Skills。
- 121 个 CyberPenda 扩展 Skills。

系统不会一次加载全部 Skills，而是根据题型选择相关能力：

| 题型 | 动态 Skills |
|---|---|
| Web | ctf-web、api-security、pentest-tools |
| Pwn | ctf-pwn、pwn-chain |
| Reverse | ctf-reverse、reverse-skill-router、reverse-engineering |
| Crypto | ctf-crypto、ctf-sandbox-orchestrator |
| Forensics | ctf-forensics、digital-forensics |
| Malware | ctf-malware、malware-analysis |
| OSINT | ctf-osint、pentest-tools |
| AI/ML | ctf-ai-ml、llm-security |

`attack-chain` 和 `ctf-writeup` 作为通用能力加载。

这一机制降低无关知识干扰，并控制模型上下文规模。

## 15. RAG 与长期记忆

### 15.1 本地 Markdown RAG

`.RAG/` 中的 Markdown 文档经过切片、Embedding 和 Milvus Lite 索引，为 Agent 提供本地知识检索。

支持：

- 状态查询。
- Top-K 搜索。
- 索引同步和重建。
- Embedding 模型和维度管理。
- Collection 自动重新加载。
- AgentScope RAG Middleware 注入。

### 15.2 AgenticMemory

任务结束后将成功攻击链和总结写入长期经验，并归档为 Markdown。

历史经验只作为候选策略，当前任务仍需使用真实证据重新验证。

## 16. 专业 MCP 工具融合

### 16.1 AntSword MCP

Attack 拥有完整 37 工具 WebShell 能力：

- Shell 管理。
- 基础信息。
- 命令执行。
- 文件管理。
- 数据库管理。
- MCP 服务状态。

写入和命令类工具与人工审批状态实时联动。

### 16.2 IDA MCP

Reverse 使用 IDA Pro 9.1 完成：

- 数据库生成。
- 函数枚举。
- 反编译和反汇编。
- 交叉引用。
- 数据流和调用图。
- 字符串、结构体与全局变量分析。

### 16.3 GDB MCP

Reverse 使用多会话 GDB MCP 完成：

- 安全创建调试会话。
- 断点、观察点和运行控制。
- 寄存器、栈、内存和符号检查。
- 反汇编、Heap 和上下文分析。
- Core Dump 分析。

attach、任意远程连接和 unsafe 工具默认不暴露。

## 17. RAG、OCR、解码与二进制能力组合

灵枢可以在一次文件任务中组合：

```text
安全解压
  → 文件类型识别
  → OCR / TonyEnc 解码
  → IntelPwn 基线分析
  → IDA 静态逆向
  → GDB 动态验证
  → Skills 专业策略
  → Summary/PDF
```

这使系统不局限于 Web 渗透，也能处理 Reverse、Pwn、Crypto、Forensics、Malware 等题型。

## 19. 多用户与超级管理员

平台具备完整身份与管理能力：

- 用户注册和登录。
- JWT 身份认证。
- 用户会话所有权校验。
- Superadmin 特殊登录入口。
- 用户查询、删除和密码重置。
- 模型 Provider 添加、修改、启用和删除。

## 20. Summary Agent 与 PDF 报告

任务结束后，Summary Agent 读取完整会话和结构化状态，生成 Markdown 总结。

PDF 渲染支持：

- 标题和多级标题。
- 粗体、斜体、行内代码。
- 列表、表格、引用和代码块。
- 中文换行。
- 微软雅黑常规和粗体。
- 红黑白视觉样式。
- 页眉、页脚和页码。
- 原子文件生成。

报告不只是聊天导出，而是包含证据、审批、攻击链、失败尝试和风险建议的正式交付物。

## 21. NSSCTF Agent Arena 自动闭环

系统支持：

- 自动领取题目。
- 获取题面、附件和容器。
- 上传附件并创建灵枢任务。
- 自动分析和提交 Flag。
- 保存正确性、剩余错误次数和 rating。
- 正确 Flag 触发确定性任务完成。
- 处理领取冷却时间。

这证明灵枢可以接入外部评测平台形成自动闭环。

## 22. 幻觉抑制技术特色

灵枢不把模型输出直接当作事实，通过以下机制抑制幻觉：

- Agent 单一职责。
- Orchestrator 唯一状态写入。
- 工具证据优先。
- 事实、推测和未验证事项分级。
- 严格工具 JSON Schema。
- completed 强制 evidence。
- RAG 与历史经验必须再次验证。
- 动作指纹与失败熔断。
- 人工审批和范围审核。
- Summary 无外部工具。
- 审计哈希链和 Workspace Artifacts。

完整方案见《大模型幻觉抑制技术方案》。

## 23. 项目差异化优势

### 23.1 相比单智能体方案

| 单智能体常见问题 | 灵枢方案 |
|---|---|
| 一个模型负责全部任务 | 多 Agent 专业分工 |
| 模型自行决定攻击 | Orchestrator＋人工审批 |
| 只有聊天记录 | 状态、事件、Artifacts、检查点和哈希链 |
| 上下文越来越长 | 角色分区与 Workspace Offloader |
| 工具输出塞满上下文 | 完整输出落盘，模型读取摘要 |
| 重复失败循环 | 动作指纹与熔断 |
| 刷新后丢失过程 | 消息、推理和工具历史持久化 |
| 报告为原始 Markdown | 格式化中文 PDF |

### 23.2 相比普通安全自动化脚本

| 固定脚本常见限制 | 灵枢方案 |
|---|---|
| 流程固定 | Brain 动态计划、Orchestrator 动态调度 |
| 难处理非结构化附件 | 多模态文件分流、OCR、逆向与 Skills |
| 难接受中途新情报 | 用户插话和官方中断机制 |
| 缺少人机协同 | 多方案审批与优先级调整 |
| 经验无法复用 | RAG＋AgenticMemory |
| 工具孤立 | Toolkit＋MCP 统一注册 |
