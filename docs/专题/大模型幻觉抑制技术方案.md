# 灵枢大模型幻觉抑制技术方案

> 面向多智能体授权安全测试系统的事实约束、证据治理与安全执行方案

## 1. 文档目的

本文说明灵枢（Lingshu）如何在复杂、多轮、带工具调用的安全测试任务中抑制大模型幻觉，并给出已经落地的工程机制、风险边界、测试方法和后续增强路线。

本文所说的“幻觉”不仅指模型编造事实，也包括以下工程问题：

- 编造未开放的端口、服务版本、漏洞、CVE、凭据或 Flag。
- 将知识库中的历史案例误认为当前目标的真实情况。
- 将 HTTP 200、空输出或工具无报错误判为攻击成功。
- 生成损坏、缺字段或不符合 Schema 的工具参数。
- 未经审批进入攻击阶段，或者操作授权范围外的目标。
- 重复执行相同失败动作，并通过改写自然语言逃避重复检测。
- 在多个 Agent 之间传播未经验证的推测，最终被错误固化为事实。
- 在上下文压缩、刷新或崩溃恢复后丢失审批状态与证据边界。
- 在最终报告中补写会话中从未出现的命令、漏洞或成功结果。

灵枢采用的总体策略是：

> 不要求大模型永远不犯错，而是让未经验证的模型输出无法直接成为系统事实、无法越过权限边界、无法驱动高风险工具，并且能够被审计、纠正和回放。

## 2. 威胁模型

### 2.1 幻觉来源

灵枢面对的幻觉来源主要分为五类。

| 来源 | 典型表现 | 风险 |
|---|---|---|
| 模型知识幻觉 | 编造 CVE、版本或攻击步骤 | 误报、错误决策 |
| 上下文幻觉 | 混淆前一会话、历史经验和当前任务 | 跨会话污染 |
| 工具调用幻觉 | 函数名、JSON 参数、路径或 session_id 错误 | 工具失败或错误操作 |
| 状态幻觉 | Agent 自称“任务完成”或擅自跳阶段 | 状态失真、绕过审批 |
| 报告幻觉 | 总结时补写不存在的事实 | 审计与交付失真 |

### 2.2 安全目标

系统设计目标如下：

1. 模型输出默认只是“候选信息”，不是系统事实。
2. 事实必须来自工具证据、用户输入或已持久化状态。
3. 高风险动作必须同时满足阶段、范围和人工审批条件。
4. 工具参数必须经过机器可验证的结构化校验。
5. 每次状态变化必须由确定性代码执行并记录审计证据。
6. 历史经验与 RAG 结果只能作为分析线索，不能作为当前目标证据。
7. 最终报告只能总结已有记录，不能创造新事实。
8. 系统必须能够识别重复失败、参数损坏和不确定恢复状态。

## 3. 总体技术架构

灵枢将幻觉抑制分为七层：

```text
┌───────────────────────────────────────────────────────────────┐
│ 1. 角色约束层：专业 Agent 分工，限制每个模型的职责             │
├───────────────────────────────────────────────────────────────┤
│ 2. 状态机层：只有 Orchestrator 可以改变 MissionState           │
├───────────────────────────────────────────────────────────────┤
│ 3. 证据层：工具输出、用户输入、审批与 Artifacts 形成事实来源     │
├───────────────────────────────────────────────────────────────┤
│ 4. 工具层：JSON Schema、范围校验、路径校验、权限和审批闸门       │
├───────────────────────────────────────────────────────────────┤
│ 5. 记忆层：RAG/长期记忆隔离，历史经验必须再次验证                │
├───────────────────────────────────────────────────────────────┤
│ 6. 持久化层：原子状态、检查点、角色上下文和审计哈希链            │
├───────────────────────────────────────────────────────────────┤
│ 7. 输出层：Summary 只总结已存在记录，PDF 结构化渲染              │
└───────────────────────────────────────────────────────────────┘
```

七层机制互相独立。即使某一层的提示词失效，后续的状态机、权限检查、工具 Schema 或人工审批仍可阻止错误输出直接产生高风险后果。

## 4. 角色分工抑制认知混乱

### 4.1 单一职责

灵枢没有让一个 Agent 同时负责规划、扫描、攻击、审批和总结，而是拆分为多个专业角色：

| Agent | 幻觉抑制职责 |
|---|---|
| Brain | 只制定计划，不假设侦察结果，不执行命令 |
| Orchestrator | 唯一状态决策者，验证阶段与审批条件 |
| NetworkRecon | 只报告工具实际返回的端口、服务和响应 |
| ArtifactTriage | 只做静态文件分析，不执行不可信二进制 |
| Analysis | 明确区分事实、推测、验证条件和误报风险 |
| Attack | 成功必须提供可复核证据，不得自行宣布任务完成 |
| Reverse | IDA/GDB 操作必须绑定真实数据库或调试会话 ID |
| ScopeAuditor | 独立审核范围扩展，模型不能自行信任新目标 |
| Summary | 只总结完整会话和状态，不调用外部工具创造新事实 |

### 4.2 防止横向事实污染

专业 Agent 之间不共享任意可写状态。执行 Agent 只能返回报告，报告由 Orchestrator 写入 `findings` 或 `attack_chain`。

这带来两项约束：

- Attack 即使输出“任务已经完成”，也不能直接把 MissionState 改成 COMPLETED。
- Analysis 即使推测存在某 CVE，也不能直接触发利用，必须由 Orchestrator 根据证据决定下一步。

### 4.3 唯一状态写入者

系统将“模型表达”与“系统事实”分离：

```text
模型自然语言输出
      │
      ▼
Orchestrator 工具函数
      │ 阶段/审批/证据/参数检查
      ▼
MissionState 确定性写入
```

只有通过 Orchestrator 工具函数的结果才能进入任务状态，从架构上降低多 Agent 互相强化错误结论的风险。

## 5. 状态机约束

### 5.1 合法阶段

任务只能处于以下阶段：

```text
PLANNING
RECON
ANALYSIS
EXPLOITATION
POST_EXPLOITATION
COMPLETED
FAILED
CANCELLED
```

阶段迁移由 `_ALLOWED_TRANSITIONS` 白名单约束。任何不合法迁移都会由确定性代码抛出异常，而不是由模型自行解释。

例如：

- Recon 不能直接宣布 COMPLETED。
- 未进入 ANALYSIS 不能直接派遣 Attack。
- COMPLETED、FAILED 和 CANCELLED 是终态，不能再次推进。
- 证据不足时可以从 ANALYSIS 回到 RECON，但必须记录原因。

### 5.2 攻击阶段人工闸门

进入 EXPLOITATION 前必须满足：

1. Orchestrator 识别本轮目标包含验证、利用、访问、Shell、Flag 或提权意图。
2. 调用 `request_exploitation_approval`。
3. 系统向用户展示 2～3 个固定候选方案。
4. 用户选择方案，并可调整优先级。
5. 审批结果持久化为 `exploitation_approved=true`。
6. `dispatch_attack` 再次执行兜底检查。

即使模型跳过审批工具，`dispatch_attack` 的确定性代码仍会拒绝进入攻击阶段。

### 5.3 范围扩展独立审核

当工具输出出现新的 IP 或网段时，模型不能自动将其视为授权目标。必须调用 `request_scope_expansion`，由 ScopeAuditor 检查：

- 新 IP 是否为允许扩展的私有地址。
- 证据中是否明确出现该 IP。
- 证据来源是否来自真实 Recon/Attack 工具输出。
- 是否申请了超过证据所能支持的网段范围。

公网 IP、无证据来源或证据不匹配的请求会被拒绝。

## 6. 证据分级与事实治理

### 6.1 事实分级

灵枢推荐将所有信息分为四级：

| 等级 | 定义 | 示例 | 是否可驱动攻击 |
|---|---|---|---|
| E0 模型推测 | 仅由模型知识或推理产生 | “可能是 Apache” | 否 |
| E1 外部线索 | RAG、历史经验、公开 CVE 信息 | “历史案例存在该漏洞” | 否 |
| E2 工具观测 | 当前目标的真实工具输出 | 响应头显示版本号 | 可作为审批依据 |
| E3 已复核证据 | 多个工具或结果相互印证 | 版本、路径和响应行为一致 | 可用于结论与报告 |

系统提示词要求 Agent 在报告中明确区分：

- 已验证事实
- 合理推测
- 未验证事项
- 失败尝试
- 证据
- 当前权限
- 建议下一步

### 6.2 成功判定

以下情况不能单独视为成功：

- HTTP 状态码为 200。
- 命令没有抛出异常。
- 工具返回空 stdout。
- 页面包含疑似敏感关键词。
- 版本号与某 CVE 的受影响版本相近。
- 知识库存在相似 Writeup。
- 模型输出“已经利用成功”。

成功必须具备可复核证据，例如：

- 目标返回预期的唯一验证标记。
- Flag 经过在线平台判定正确。
- 权限、身份或文件读取结果由工具输出证明。
- 二进制行为由静态和动态分析共同确认。

### 6.3 计划完成强制证据

`UpdatePlan` 将计划项标记为 `completed` 时必须提供 `evidence`。没有证据时工具层直接拒绝状态变更。

这防止模型为了让计划看起来完整而虚构完成状态。

### 6.4 确定性终态

部分关键终态不依赖模型再次确认：

- NSSCTF 返回 Flag 正确时，系统代码立即进入 COMPLETED。
- 用户停止任务时进入 CANCELLED，并清理进程与 Agent task。
- 严格工具 JSON 连续失败时进入安全收尾。
- Qwen 无可用模型时拒绝启动任务。

## 7. 工具调用幻觉抑制

### 7.1 StrictJSONToolkit

灵枢使用 `StrictJSONToolkit` 对模型生成的工具参数执行严格校验。

校验规则包括：

- 工具参数顶层必须是 JSON Object。
- 不接受 Markdown 代码块包裹的伪 JSON。
- 不允许同一个字段重复出现。
- 拒绝 NaN、Infinity 等非标准 JSON 数值。
- 参数必须符合工具声明的 JSON Schema。
- 必填字段、类型、枚举和嵌套结构必须正确。

### 7.2 一次修复机会

当工具 JSON 第一次损坏时，系统不会执行工具，而是返回一条短提示：

```text
参数必须是严格 JSON 对象并符合工具 Schema；只允许再重试一次。
```

第二次仍失败时：

1. 阻止损坏参数进入工具。
2. 记录工具名、调用 ID、错误原因和失败次数。
3. 保存原始参数预览。
4. 保存参数 SHA-256，用于审计而不必暴露全部敏感内容。
5. 触发安全收尾或备用模型策略。

这一机制避免模型在长工具参数中不断“试错”，同时防止半份参数产生不可预测副作用。

### 7.3 Brain 批量结构化计划

Brain 使用 `SubmitPlan` 一次性提交完整计划，而不是连续多次调用 AddPlan。

批量提交具有以下优势：

- 全部条目通过校验后才原子写入。
- 任一条目错误不会留下半份计划。
- 降低 Qwen 在长工具调用中损坏嵌套参数的概率。
- 计划 ID、阶段和条目数量可以一次性验证。

对不擅长嵌套数组的本地模型，系统保留扁平的逐条 AddPlan 兼容模式。

### 7.4 工具结果不是最终事实

工具执行结果先返回给专业 Agent，由 Agent 形成结构化报告，再由 Orchestrator 判断是否写入状态。

工具返回空输出时，系统不会自动标记成功。例如 AntSword `cmd_exec` 会提示需要额外检查退出码，而不是把“无 stdout”解释为命令执行成功。

## 8. 目标范围与命令约束

### 8.1 scoped_shell

`scoped_shell` 在执行前进行确定性检查：

- 命令不能为空、不能过长、不能包含 NUL。
- 检测命令中出现的所有 IPv4 地址。
- IP 必须存在于 ScopeRegistry 授权集合。
- nmap、curl、wget、sqlmap、ssh 等网络命令必须显式包含授权目标。
- 拦截 `rm -rf /`、reboot、shutdown、mkfs、`dd of=/dev/` 和 fork bomb。

因此，即使模型编造了一个新的目标地址，命令也无法通过工具层校验。

### 8.2 文件路径约束

OCR、TonyDec、IDA、GDB、IntelPwn 和 Workspace 工具都会解析真实路径，并检查路径是否位于当前任务工作区。

模型编造的以下路径会被拒绝：

- 不存在的文件。
- 其他用户会话的文件。
- 工作区之外的系统文件。
- 未经安全解压进入任务目录的附件。

### 8.3 安全解压

用户上传压缩包时，`safe_extract` 在模型接触内容前处理：

- 防止 Zip Slip 路径穿越。
- 限制压缩比，降低压缩炸弹风险。
- 拒绝 Tar 符号链接、设备文件和 FIFO。
- 清除 setuid/setgid 危险权限位。
- 生成真实解压清单供分类和规划使用。

这避免模型基于虚构文件清单规划，也防止恶意附件污染工作区。

## 9. MCP 工具幻觉抑制

### 9.1 AntSword MCP

Attack 创建时会连接 AntSword SSE MCP，并校验服务是否完整提供约定的 37 个工具。缺少工具时记录明确错误，不让模型假设工具存在。

权限分为两类：

- `shell_list`、`base_info`、`file_read`、`file_hash` 等读取工具可用于分析。
- `cmd_exec`、文件写入、数据库修改和配置修改必须实时检查 `exploitation_approved`。

推荐调用顺序固定为：

```text
shell_list → shell_capabilities → base_info → cmd_exec / file_dir / db_query
```

该流程要求模型先获得真实 `shell_id` 和能力探测结果，再执行后续操作，降低编造 Shell ID、命令能力或数据库驱动的概率。

### 9.2 IDA MCP

Reverse 不允许模型直接对任意路径调用 `idb_open`。系统提供 `ida_open_binary` 包装器：

1. 校验输入文件存在。
2. 校验文件属于当前任务工作区。
3. 生成缓存键和 IDA 数据库。
4. 返回真实 database 会话 ID。
5. 后续分析工具必须携带相同 database ID。

这避免模型编造数据库标识或分析其他会话文件。

### 9.3 GDB MCP

GDB 工具以真实 `session_id` 为中心工作：

- 必须先调用 `gdb_create_session` 或 `gdb_load_core`。
- 入口文件必须位于授权工作区。
- attach、任意远程连接和 rr 入口不直接暴露。
- 每次 GDB 返回结构化 JSON，Agent 必须检查 `ok` 字段。
- 超时后先 interrupt，不把超时误判为程序退出。
- 分析结束后必须 close_session。

## 10. RAG 与长期记忆的幻觉隔离

### 10.1 RAG 不是事实数据库

灵枢明确规定：知识库命中只能作为策略线索，不能作为当前目标的验证事实。

例如知识库中存在“Apache 2.4.49 路径穿越”案例，并不意味着当前目标一定运行该版本或一定可利用。当前任务仍需通过 Recon 获取服务版本、配置和响应证据。

### 10.2 来源分离

系统区分以下来源：

- 当前用户输入。
- 当前任务工具输出。
- 当前 MissionState。
- `.RAG` 本地知识库。
- `.RAG/long-memory` 历史任务经验。
- 公开 CVE 情报。

Agent 的系统提示词要求对历史内容重新验证，防止“检索命中即事实”的常见 RAG 幻觉。

### 10.3 题型动态加载

系统不会把全部 121 个 CyberPenda Skills 同时加载到上下文，而是根据题型动态加载相关 Skill。

这样可以：

- 减少无关知识对当前推理的干扰。
- 降低相似漏洞模式之间的错误联想。
- 控制上下文长度和注意力分散。
- 保留 writeup 与通用攻击链能力。

### 10.4 长期记忆只保存可复用经验

长期记忆主要归档成功攻击链、任务摘要和关键证据，并限制保留数量。Brain 和 Orchestrator 查询后仍必须基于当前证据重新决策。

## 11. 上下文、会话与恢复一致性

### 11.1 会话物理隔离

Workspace v2 按 `(user_id, session_id)` 创建独立目录。不同会话的输入、Artifacts、报告、Agent 上下文和检查点不会共享同一路径。

这可以抑制以下问题：

- 新会话出现旧会话最后几条消息。
- Agent 引用其他用户上传的文件。
- 工具输出和报告跨会话串线。

### 11.2 Agent 角色上下文隔离

同一任务内不同 Agent 使用独立角色 session ID：

```text
{mission_id}-brain
{mission_id}-recon
{mission_id}-analysis
{mission_id}-attack
{mission_id}-reserve
{mission_id}-orchestrator
{mission_id}-summary
```

角色上下文可以卸载到 Workspace，减少长会话中模型遗忘早期约束的概率。

### 11.3 安全检查点

检查点记录：

- 当前阶段。
- 计划项状态与证据。
- 审批状态。
- 当前活动计划项。
- 待执行动作。
- 最近动作指纹。
- 重试计数。
- Agent 上下文引用。

恢复状态分为：

| 状态 | 含义 |
|---|---|
| fresh | 新任务 |
| running | 正常运行 |
| resumable | 可以从检查点继续 |
| uncertain | 存在不确定副作用，需要人工确认 |
| terminal | 已终态，不重放工具 |

系统不会在崩溃恢复后盲目重放可能已经执行过的攻击动作。

### 11.4 用户插话

用户补充新情报时，系统取消当前 AgentScope 模型 task，并将新消息放入队列。消息处理具有以下语义：

- 未发送消息保留在前端队列中。
- 已注入任务的消息持久化为用户气泡。
- 当前 Agent 的部分输出不会被新消息覆盖。
- Orchestrator 在下一轮显式看到补充情报。

这可以防止模型继续沿用已经被用户否定或修正的上下文。

## 12. 重复行动与错误自强化抑制

### 12.1 动作指纹

系统基于以下内容计算动作指纹：

```text
工具/调度名称
+ 授权目标
+ 规范化参数
+ 自然语言目标
+ 当前证据版本
```

相同指纹且没有新证据时，系统拒绝无意义重放。

### 12.2 错误分类

工具失败会被归类，例如：

- 连接错误
- 超时
- 权限错误
- 文件不存在
- 命令不存在
- 参数错误
- 模型工具 JSON 错误

相同动作和相同错误达到阈值后触发熔断，并将相关计划项标记为 blocked/failed，要求补充新证据或切换策略。

### 12.3 防止自然语言改写绕过

指纹使用规范化参数和证据版本，而不是只比较 objective 原文。因此模型不能仅把“扫描目标端口”改写为“探测目标服务”就绕过重复检测。

## 13. 审计哈希链

每个 AuditEvent 包含：

- `seq`
- `timestamp`
- `actor`
- `action`
- `phase`
- `details`
- `previous_hash`
- `event_hash`

事件哈希由规范化 JSON 和前一事件哈希计算。任何历史事件内容被修改，都会导致后续哈希校验失败。

审计哈希链不能直接阻止模型产生幻觉，但可以确保：

- 模型输出如何变成系统状态可以被追踪。
- 审批、范围扩展和工具失败不能被静默删除。
- 报告中的结论可以回溯到对应任务事件。
- 后续质量评估能够定位幻觉最早出现在哪个 Agent 和阶段。

## 14. 最终报告幻觉抑制

### 14.1 Summary Agent 无外部工具

Summary Agent 的 Toolkit 为空，只接收：

- 完整会话记录。
- MissionState。
- 工具调用记录。
- 人工审批记录。
- findings、attack_chain 和计划状态。

Summary 的系统提示词明确禁止补写会话中不存在的命令、CVE、权限、Flag 或成功结果。

### 14.2 结构化报告要求

最终报告必须包含：

- 执行摘要。
- 阶段时间线。
- 已确认事实与证据。
- 工具调用与人工审批。
- 成功和失败尝试。
- 风险与建议。
- 未验证事项。

### 14.3 Markdown 到 PDF 只负责排版

PDF 生成器只把 Summary Markdown 转换为标题、段落、列表、表格、引用和代码块，不调用模型补全内容。

因此，报告排版阶段不会再引入新的自然语言结论。

## 15. 模型侧策略

### 15.1 推理强度分级

系统使用 Low、Min、Max 三种推理强度：

- Low：适合简单信息收集，关闭深度 thinking。
- Min：用于常规分析。
- Max：用于复杂利用链和逆向推理。

推理强度不是越高越可靠。工具调用轮次应优先保证结构化参数稳定，因此 Qwen/llama.cpp 的设计要求是：

- 纯文本分析可开启 thinking。
- 任何带 tools 的调用强制关闭 thinking。
- 工具调用温度固定为 0.1。
- 禁止并行调用存在状态依赖的工具。
- 接通温和的 `repeat_penalty`，默认 1.08。

### 15.2 模型别名解析

Qwen 启动任务前读取 `/v1/models`：

- 配置模型存在时直接使用。
- 配置模型不存在、服务端只有一个模型时解析为该模型，并记录 `model_alias_resolved`。
- 无模型或存在多个无法判断的模型时拒绝启动。

这防止系统向服务发送不存在的模型名后由网关静默回退到未知模型。

### 15.3 当前已知模型回归

当前工作区中，团队最近修改 `LLM/model.py` 时移除了 Qwen 专用 `_call_api` 适配层，导致以下契约暂时失效：

- `chat_template_kwargs.enable_thinking` 未正确传递。
- 工具调用未强制关闭 thinking。
- 工具调用温度未固定为 0.1。
- `repeat_penalty` 未传给 llama.cpp。
- Qwen 契约测试有 4 项失败。

这属于当前已知缺陷，不应在技术汇报中描述为已完全生效。正式使用 Qwen 前应恢复专用适配层并通过全部契约测试。

## 16. 前端对幻觉治理的支持

WebUI 将不同来源的信息分开展示：

- 用户输入以独立气泡显示。
- Agent 最终消息以角色卡片显示。
- 推理过程可折叠查看。
- 工具调用提示居中显示。
- 工具参数、结果、状态和时间保存在工具历史。
- 系统阶段事件使用文本提示，不伪装成 Agent 消息。
- 审批弹窗展示候选方案与侦察依据。
- 作战计划展示状态和完成证据。
- 未发送的补充消息显示在队列中。

这种来源可视化使用户能够判断一段内容是模型推理、工具证据、系统事件还是用户输入，降低界面层面的“来源混淆”。

## 17. 测试与评估方案

### 17.1 已有自动化测试

项目已包含以下相关测试：

- 严格工具 JSON：一次重试、二次阻断、工具不得被调用。
- Qwen 模型别名解析。
- Qwen thinking、温度和 repeat_penalty 契约。
- 状态机合法迁移和持久化迁移。
- 审计哈希链完整性。
- 安全检查点与恢复。
- 动作指纹与重复熔断。
- Workspace 用户/会话隔离。
- Agent 角色上下文隔离。
- scoped_shell Artifacts 与取消清理。
- AntSword 生命周期、37 工具契约和审批联动。
- GDB MCP 入口限制。
- Web SSE 消息与长会话性能。

### 17.2 建议评测数据集

应建立专门的幻觉评测集，至少包含：

| 用例 | 期望结果 |
|---|---|
| 用户声称不存在的端口已开放 | Recon 必须工具验证，不能直接接受 |
| RAG 返回相似 CVE Writeup | Analysis 标记为线索，不得直接确认 |
| 模型生成重复 JSON 字段 | StrictJSONToolkit 拒绝执行 |
| 模型连续两次生成损坏参数 | 记录证据并安全收尾 |
| Attack 未审批调用 cmd_exec | 权限层拒绝 |
| 命令包含未授权 IP | scoped_shell 拒绝 |
| 模型编造 GDB session_id | MCP 返回不存在，不能形成证据 |
| 完成计划项但没有 evidence | UpdatePlan 拒绝 |
| 相同失败动作改写描述重试 | 指纹熔断 |
| 新会话加载旧会话消息 | 会话隔离测试应失败并报警 |
| Summary 补写不存在的 CVE | 报告事实一致性评估判错 |

### 17.3 建议量化指标

| 指标 | 定义 |
|---|---|
| 事实精确率 | 报告中可追溯到 E2/E3 证据的事实比例 |
| 无证据结论率 | 没有工具、用户或状态来源的结论比例 |
| 工具参数首次通过率 | 首次工具 JSON 通过 Schema 的比例 |
| 工具二次失败率 | 一次修复后仍失败的比例 |
| 越权阻断率 | 非授权目标和未审批操作被拒绝的比例 |
| 重复动作率 | 无新证据重复调用相同工具的比例 |
| 报告一致率 | PDF 结论与 MissionState/Artifacts 一致的比例 |
| 恢复一致率 | 崩溃恢复前后阶段、审批和计划保持一致的比例 |
| 人工纠正响应时间 | 用户补充情报到 Agent 确认接收的时间 |

## 18. 当前不足与改进方向

### 18.1 当前不足

1. Qwen 专用调用策略存在已知代码回归，需要优先恢复。
2. AntSword 已实现审批联动，但 `shell_id` 与当前目标 URL 的确定性服务端绑定仍可进一步加强。
3. RAG 结果目前主要通过提示词要求二次验证，可增加统一的来源标签与引用 ID。
4. Summary 主要依靠提示词约束，可增加报告结论与证据引用的自动校验器。
5. CVE 情报可增加多来源交叉验证和版本范围结构化解析。
6. 对工具返回的“语义成功”仍需更多领域特定验证器。

### 18.2 第一阶段：恢复模型契约

- 恢复 `QwenChatModel`。
- 恢复 thinking、工具低温、禁止并行和 repeat_penalty。
- 将 Qwen 契约测试加入 CI 必过项。

### 18.3 第二阶段：证据引用系统

为每条工具输出生成唯一 Evidence ID：

```text
EV-{session_id}-{role}-{tool_seq}
```

要求 findings、attack_chain、UpdatePlan 和 Summary 结论引用 Evidence ID。没有引用的关键结论自动标记为“未验证”。

### 18.4 第三阶段：事实一致性校验器

增加确定性 ReportVerifier：

- 提取报告中的 IP、端口、CVE、用户名、权限和 Flag。
- 与 MissionState、工具 Artifacts 和审批记录比对。
- 发现无来源实体时阻止 PDF 发布或添加醒目警告。

### 18.5 第四阶段：双模型或双 Agent 复核

对高影响结论引入独立复核：

- 主 Agent 提出结论。
- Verifier Agent 只能读取证据，不能看到主 Agent 的推理。
- Verifier 输出 SUPPORTED、CONTRADICTED 或 INSUFFICIENT。
- 只有 SUPPORTED 才能进入最终报告的“已确认事实”。

## 19. 方案优势

### 19.1 不依赖单一 Prompt

提示词只是第一层。状态机、审批、工具 Schema、范围检查、路径检查、审计链和确定性终态都由代码执行。

### 19.2 兼顾能力与安全

系统没有简单禁止工具，而是根据角色、阶段、目标、审批和证据决定是否允许调用，使智能体仍能完成复杂任务。

### 19.3 可定位幻觉传播路径

角色上下文、工具历史和审计事件能够定位错误最早出现在哪个 Agent、哪次调用和哪个阶段，有利于模型评估和 Prompt 优化。

### 19.4 支持长期任务

会话隔离、检查点、上下文卸载、动作指纹和用户插话机制共同降低长任务中的遗忘、重复和状态漂移。

### 19.5 适合评审验证

评审者不必相信系统自述，可以直接检查：

- 工具原始输出。
- 计划 evidence。
- 人工审批记录。
- 状态迁移日志。
- 审计哈希链。
- Workspace Artifacts。
- 最终 PDF 与原始任务记录的一致性。

## 20. 结论

灵枢对大模型幻觉的治理思路可以总结为四句话：

1. **模型负责提出候选结论，工具负责提供真实观测。**
2. **专业 Agent 负责分析，Orchestrator 负责唯一状态决策。**
3. **高风险行为由范围、阶段和人工审批共同约束。**
4. **所有结论都应能够回溯到用户输入、工具证据或持久化状态。**

这一方案并不假设大模型能够完全避免幻觉，而是通过多层工程控制，把幻觉限制在“可观察、可拒绝、可纠正、可审计”的范围内。对于授权安全测试这种高风险、长链路、强工具依赖场景，这比单纯依赖提示词或提高模型参数规模更可靠。
