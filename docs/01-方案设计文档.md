# 灵枢（Lingshu）方案设计文档

**项目类型：** 面向授权安全测试的多智能体协作系统
**文档版本：** 1.0
**编制日期：** 2026-08-20
**代码基线：** HEAD `e2353b0`（2026-08-19，含 GLM 模型支持、DeepSeek 网关模式、Markdown 报告下载等）

## 1. 项目概述

灵枢（Lingshu）是一个基于 AgentScope 2.x 的多智能体授权安全测试系统。系统以「任务目标、授权范围、可审计性」为核心约束，通过 Brain → Orchestrator → Recon/Attack/Analysis/Reserve → Summary 的专家协作链，完成从任务理解、侦察、研判、人工审批、验证/利用到报告生成的完整闭环。

系统不以「自动攻击」为设计目标，而以**授权边界、最小影响、人工闸门、证据留存、可恢复执行**为基本原则：所有网络与文件操作必须在授权目标范围内执行；进入攻击阶段前必须获得人工批准；每一步关键动作都进入可校验的审计哈希链。

### 1.1 能力概览

| 能力域 | 说明 |
|---|---|
| 双入口 | CLI（`main.py`）与 FastAPI Web 服务（`api.py`）共用同一 `run_mission()` 核心工作流 |
| 多模型 | DeepSeek（Responses 协议 + 网关模式）、智谱 GLM、Qwen（llama.cpp）、任意 OpenAI 兼容 Provider，经统一工厂 `LLM/model.py::create_model` 创建 |
| 三层记忆 | `.RAG` 知识库（静态事实）+ `.LongMemory` 长期经验记忆 + 会话级短期记忆（上下文压缩治理） |
| 工具生态 | 自研 `Tools/`（scoped_shell、Plan、CVE_Search、OCR、指纹、知识库等）+ MCP（AntSword、IDA、GDB） |
| 前端 | Vite + React WebUI（`webui/`）为主，原生 JS（`../frontend_bak/`）为降级兜底 |
| 报告 | Markdown 总结 + PDF 报告 + JSONL 原始会话导出 |
| 平台集成 | AgentScope Service 封装（`integrations/agentscope_service/`）、NSSCTF / Slab 在线判题、AntSword 服务生命周期托管 |

## 2. 设计目标

### 2.1 功能目标

1. 支持 CLI 与 WebUI 两种使用方式，任务状态实时同步。
2. 支持 DeepSeek、GLM、Qwen 及自定义 OpenAI 兼容 Provider 的多档模型（Low/Min/Max）切换。
3. 支持 `.RAG` Markdown 知识库检索（Milvus Lite 向量化）、长期经验记忆归档与查询、会话级短期记忆压缩。
4. 支持 AntSword、IDA、GDB 等 MCP 工具按专家角色接入，生命周期受控。
5. 支持流式消息、推理过程、工具参数/输出、审批事件、计划变更事件的持久化与 SSE 推送。
6. 任务结束后生成结构化 Markdown 报告与中文 PDF，支持完整 JSONL 会话导出；支持在线判题平台 Flag 提交。
7. 支持任务中断/取消/恢复（检查点 + Workspace），崩溃后不重复询问审批。

### 2.2 非功能目标

- **安全性**：默认授权、目标范围语义校验、破坏性命令拦截、攻击阶段人工审批、MCP 可写工具逐次联动审批。
- **可审计性**：任务状态、阶段迁移、计划、工具调用、审批均形成带 SHA-256 哈希链的审计事件。
- **可恢复性**：MissionState 原子持久化 + checkpoint 镜像，支持崩溃恢复与安全停止。
- **可扩展性**：Agent、工具、模型 Provider、知识库、报告模板均可独立扩展。
- **防幻觉**：以「唯一状态决策者 + 证据驱动 + 严格参数闸门 + 确定性终态收尾」抑制 LLM 编造结果（详见第 7 章与《05-技术选型报告.md》）。

## 3. 总体架构

```text
用户 / WebUI / CLI
        │
        ▼
FastAPI API 层（JWT 认证、会话、SSE 事件、审批、知识库、模型配置、文件报告）
        │
        ▼
run_mission() 核心工作流（main.py）
        │
        ├── Brain（Sophia）：战略理解与计划登记
        ├── Orchestrator（Alex）：唯一状态调度者
        │     ├── dispatch_recon   → Recon（Ethan/Iris）
        │     ├── analysis + cve_search → Analysis（Nora）
        │     ├── dispatch_attack  → Attack（Mike/Victor…，内嵌 Analysis）
        │     ├── dispatch_reverse → Reserve（Ryan，IDA/GDB MCP）
        │     ├── request_scope_expansion → ScopeAuditor（Grace）
        │     └── complete_mission → 终态收尾 + 长期记忆
        ├── Summary（Mia）：终态后独立生成 Markdown/PDF 报告
        ├── 三层记忆：.RAG 知识库 / .LongMemory / 会话上下文
        └── MCP：AntSword、IDA、GDB
```

### 3.1 状态机

```text
PLANNING → RECON → ANALYSIS → EXPLOITATION
                         │          │
                         │          ├── POST_EXPLOITATION → COMPLETED
                         │          └── FAILED
                         └── (任意活跃阶段) → CANCELLED / FAILED
```

- 合法迁移由 `TaskState.py::MissionState.transition` 按 `_ALLOWED_TRANSITIONS` 白名单强制校验，非法迁移直接抛错并记录审计。
- **仅 Orchestrator 可变更任务状态**，其他 Agent 只返回结果；LLM 无法绕过状态机推进阶段。

### 3.2 专家职责

| 专家 | 人设 | 职责 | 执行权限 |
|---|---|---|---|
| Brain | Sophia 战略规划 | 理解任务、参考经验记忆、制定四阶段计划（经 SubmitPlan 原子登记） | 仅计划登记，无状态修改权 |
| Orchestrator | Alex 行动指挥 | 调度专家、推进阶段、审批、终态 | 唯一状态/计划管理权 |
| Recon | Ethan/Iris | 网络被动侦察、归档文件 triage | 授权范围内侦察 |
| Analysis | Nora | 漏洞研判、CVE 关联 | 纯推理，不执行命令 |
| Attack | Mike/Victor 等（按题型动态人设） | 低影响验证、CVE/命令/WebShell 工具 | 受审批闸门 + 范围约束 |
| Reserve | Ryan | IDA/GDB 二进制逆向与动态分析 | MCP 会话受控执行 |
| ScopeAuditor | Grace | 范围扩容独立审核 | 仅被 request_scope_expansion 调用 |
| Summary | Mia | 汇总过程生成 WRITEUP 报告 | 只读会话与任务状态 |

## 4. 核心机制设计

### 4.1 唯一状态决策者

- Orchestrator 是唯一可调用 `transition()` 的角色（`agent/Orchestrator.py`），Brain/Recon/Attack 等仅返回结果，从机制上杜绝多 Agent 竞态改写状态。
- 状态持久化在 `MissionState`（`.TaskMemory/sessions/{session_id}.json`），原子写入（临时文件 + `os.replace` + fsync），支持 schema 自动迁移。

### 4.2 人工审批闸门

- **首次进入 EXPLOITATION 前**，Orchestrator 必须调用 `request_exploitation_approval`（`agent/Orchestrator.py:356`）获得人工批准；`dispatch_attack` 内部兜底检查，LLM 跳过申请也无法进入攻击阶段。
- 审批通道由 `_ApprovalBroker`（`main.py:594`）统一协调：
  - CLI 模式：终端阻塞询问 y/n；
  - API 模式：推送 `approval_required` SSE 事件，用户消息经 `feed()` 分发（支持批准 / 补充侦察 / 拒绝三态 + 方案选择）。
- 批准状态持久化于 `MissionState.exploitation_approved`（只问一次，崩溃恢复不重复询问），审批结果记入审计链。
- AntSword 可写类 MCP 工具每次调用实时联动审批状态（`agent/Attack.py` `_check_permissions`）。

### 4.3 授权范围约束

- `ScopeRegistry`（`Tools/ScopeRegistry.py`）语义级维护授权范围：初始目标 + DNS 解析 IP + 用户声明目标；扩容只能经 `request_scope_expansion` 由 ScopeAuditor 独立审核（RFC1918 + 证据出现该 IP 才 APPROVED）。
- `scoped_shell`（`Tools/tooling.py:583`）三重校验：破坏性命令黑名单（rm -rf /、reboot、mkfs、dd of=/dev/、fork bomb）→ 命令中所有 IPv4 必须命中授权范围 → 网络工具（nmap/curl/sqlmap 等）必须显式包含授权目标。
- 命令以独立进程组执行，超时/取消按进程组 SIGKILL，统一由 `ProcessTracker` 清理。

### 4.4 审计哈希链

- 每条审计事件携带 `seq / previous_hash / event_hash`（SHA-256 规范化 JSON），`verify_audit_chain()` 可整体校验，篡改任一条都会断链（`TaskState.py:191`）。
- 拒绝、熔断、审批、终态收尾全部入链；工具 JSON 校验失败也记录证据（参数哈希）后安全收尾。

### 4.5 作战计划工具化

- Brain 经 `SubmitPlan` 原子登记 4~8 条计划（id 连续），Orchestrator 经 `AddPlan/UpdatePlan/DeletePlan/ListPlan` 维护（`Tools/Plan.py`）。
- **标记 completed 强制要求 evidence**（防伪造闸门），全部操作进审计链并实时推送 `plan_updated` 事件。
- `complete_mission` 终态确定性收尾：in_progress→completed/failed、pending→skipped。

## 5. 三层记忆设计

| 层 | 数据源 | 存储 | 使用方 | 防污染机制 |
|---|---|---|---|---|
| 知识库（静态事实） | `.RAG/` 按 00~11 分类 Markdown（含冷记忆卡片） | Milvus Lite 向量库 `.TaskMemory/rag/knowledge.db` + manifest | Brain（RAG 中间件）、Attack | 只读注入、`source` 来源标注、检索结果「仅供参考」定位 |
| 长期经验记忆 | 任务终态（target/goal/plan/attack_chain/success/summary/flag） | `.LongMemory/agentic_memory.json`（热记忆 ≤50 条） | Orchestrator、Analysis（QueryMemory） | `_redact` 脱敏（去 IP/Flag/凭据）、冷归档卡片强制声明需当前证据重新验证 |
| 短期会话记忆 | Agent ReAct 上下文 + 用户消息 | AgentState 分区 + SQLite（sessions/messages） | 全部 Agent | `ContextConfig` 触发压缩，`SUMMARY_SCHEMA` 强制保留 7 个恢复语义字段 |

- **三层职责分离**：知识库回答「是什么」（CVE 情报、工具用法、题型经验），长期记忆回答「怎么打」（历史成功链路，脱敏后可复用），短期记忆回答「进行到哪」（当前任务上下文、证据、审批状态）。
- **闭环**：长期记忆溢出时经脱敏生成 Markdown 卡片归档进 `.RAG/long-memory/`，再次被 RAG 索引，实现「经验 → 知识」沉淀。

## 6. 模型层设计

- 统一工厂 `LLM/model.py::create_model(provider, Ver)` 按 Provider 分流：
  - `deepseek` → `DeepSeekResponsesModel`（OpenAI Responses 协议，支持 native web_search 与 `gateway_mode`：`base_url` / 完整 `/responses` 网关）；
  - `zhipu` → `ZhipuResponsesModel`（GLM，固定 Responses，支持 native_tools/thinking/reasoning）；
  - `qwen` → `OpenAIChatModel`（llama.cpp OpenAI 兼容，`thinking_enable` 控制思考级别）；
  - 其它 → `OpenAICompatible`（按注册的 `api_style` 分流 Responses / Chat Completions）。
- `RuntimeConfig`（`config.py:53`）从 .env 读取默认值，`model_registry.load_runtime_overrides()`（`model_registry.py:389`）用 Superadmin 在 Web 端注册的配置覆盖（API Key 经 Fernet 加密存储），embedding 配置变更触发 RAG 热重载。
- 档位映射：Low/Min/Max 经 `RuntimeConfig.model_name()` 映射到各 Provider 的三档模型名。

## 7. 防幻觉设计（七层防线）

1. **角色约束**：单一职责 + 认知隔离（Brain 不做侦察、Analysis 不执行命令），防止横向事实污染。
2. **状态机锁**：唯一状态决策者，非法迁移直接拒绝。
3. **证据强制**：计划 completed 必须有 evidence；成功判定以真实工具输出/平台返回为准。
4. **审批闸门**：攻击动作双保险（Orchestrator 检查 + dispatch_attack 兜底 + MCP 逐次联动）。
5. **动作指纹与熔断**：`Tools/fingerprint.py` 对相同动作指纹去重，连续失败熔断并标记计划项。
6. **范围与参数硬约束**：scoped_shell 三重校验 + ScopeRegistry 动态授权 + `StrictJSONToolkit`（重复字段/非有限数值/JSON Schema 校验，连续两次失败抛 `ToolJSONValidationError` 安全收尾）。
7. **审计链 + 上下文治理 + 确定性收尾**：SHA-256 哈希链防篡改；上下文压缩保留恢复语义；超迭代/残缺工具调用收敛为 FAILED；`submit_nss_flag` 正确由平台返回判定，强制进入 COMPLETED。

## 8. 数据流设计

1. 用户登录创建会话（API）或直接 CLI 传参（target/goal）。
2. `run_mission()` 解析并规范化目标（network/archive/single_file/directory），安全解压上传文件（防路径穿越），题型启发式分类，提取用户声明目标并入授权范围。
3. Brain 检索知识库与经验记忆，形成计划并原子登记。
4. Orchestrator ReAct 主循环调度 Recon/Analysis/Attack/Reserve，嵌套调用 `run_interruptible_agent_reply()`，ReAct 迭代预算按题型分配。
5. 事件经回调进入 SSE（`api.py` `_make_session_callback`），同时异步批量落库（`_persistence_worker`）。
6. 用户输入经 `send_message` 进入 `input_queue`，必要时 `interrupt_agent_tasks` 打断当前 Agent 后注入 steering 指令。
7. 终态后 Summary Agent 读取结构化状态与事件转录，生成 Markdown + PDF 报告；JSONL 导出保留结构化字段与原始数据库行。

## 9. 前端设计

- **主前端** `webui/`：Vite + React + TypeScript，`App.tsx` 单页实现会话列表、流式渲染、工具历史、审批弹窗、知识库管理、模型配置管理、报告下载；生产构建产物由 `api.py` 静态托管（含 SPA fallback）。
- **兜底前端** `../frontend_bak/`：原生 JS（`session_state.js` / `api_client.js` / `agent_transport.js`），仅当 `webui/dist` 不存在时提供降级页面。
- 事件协议：SSE 全量事件（`message_delta`、`tool_start`、`plan_updated`、`approval_required`、`phase_changed` 等），前端按事件类型增量渲染。

## 11. 设计取舍

- **SSE 而非 WebSocket**：降低前端接入复杂度，适配既有事件模型，断线重连以 snapshot 恢复。
- **SQLite 本地审计存储**：适合单机/竞赛部署；高并发生产可迁移 PostgreSQL（schema 由 session_store 抽象层隔离）。
- **任务状态与消息分离保存**：MissionState 支撑恢复/重跑/报告，消息表支撑前端分页与 JSONL 导出。
- **嵌套调用而非并发多 Agent 消息传递**：保证单调度者语义、审计顺序确定性、参数隔离，避免竞标/竞态。
- **Summary 失败降级**：保留结构化摘要，不因报告失败覆盖任务终态。
- **工作区模式**：`LINGSHU_WORKSPACE_MODE=docker`（默认）按会话起独立 `kali-full` 容器，工具在容器内执行；`local` 为宿主机 LocalWorkspace；`legacy` 兼容旧部署。docker 模式容器采用 host 网络 + `NET_RAW`/`NET_ADMIN` 能力，工作区目录 bind mount 到容器 `/workspace`。
