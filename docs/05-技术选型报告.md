# 灵枢（Lingshu）技术选型报告

**代码基线：** HEAD `e2353b0`（2026-08-19）
**编制日期：** 2026-08-20
**范围：** ① 为什么选择 AgentScope 而非 LangChain；② 为什么选择「知识库 + 长期记忆 + 短期记忆」三层记忆结构；③ 为什么采用七层防线式幻觉抑制方案。

---

## 1. 选型背景

灵枢是一个面向**授权安全测试**的多智能体系统，核心诉求不是「把 LLM 接进来」，而是**把多个 LLM 专家的协作行为锁进一条可审计、可恢复、防幻觉的执行轨道**。由此产生三条硬性选型标准：

1. **多智能体是一等公民**：系统需要 Brain/Orchestrator/Recon/Attack/Analysis/Reserve/Summary 等多个角色各司其职，框架必须原生支持 Agent 抽象、角色会话隔离与协作调度，而非把 Agent 当「Chain 的包装」。
2. **状态与上下文治理能力**：任务有严格状态机（PLANNING→…→COMPLETED/FAILED），上下文有压缩、溢出（offload）、会话分区需求，框架应原生提供而非全部自研。
3. **中国模型生态友好**：生产模型为 DeepSeek / 智谱 GLM / Qwen（llama.cpp），框架需对 OpenAI Responses 协议、OpenAI 兼容 Chat、国产模型接入有成熟支持。

候选方案：AgentScope 2.x（阿里开源，多智能体应用框架）与 LangChain / LangGraph（海外主流 LLM 应用框架）。

## 2. 为什么采用多专家（多 Agent）协作模式

### 2.1 为什么不是单 Agent

授权安全测试是**多知识域、多阶段、高风险**的复合任务：

- 知识域跨度大：网络侦察、Web 漏洞、二进制逆向、取证、密码学、CVE 情报；
- 阶段差异大：规划 → 侦察 → 研判 → 利用 → 报告，思考/执行/审核的行为模式不同；
- 风险差异大：侦察与利用、分析与执行的信任级别完全不同。

单 Agent 方案存在四个不可调和的问题：

1. **上下文爆炸与认知混杂**：战略、战术、执行、报告要求塞进同一个提示词，模型注意力分散、前后不一致；
2. **权力不分立**：同一个 Agent 既策划又执行又自我审批，越权与幻觉无制衡；
3. **幻觉放大**：研判与执行同体，模型容易「边编边执行」，伪造结果没有独立校验方；
4. **不可扩展**：新增能力（如逆向）只能继续往同一个提示词里塞，相互干扰。

多专家模式把复合任务按**职责与信任级别**拆分为多个认知隔离的专家：每个专家只做一件事、只拿自己需要的工具、只在自己的信任边界内行动。

### 2.2 专家分工与协作拓扑

协作拓扑为**星型**：Orchestrator 是唯一调度者，其余专家只响应 `dispatch_*` 调用并回流结果。

| 专家 | 人设 | 层 | 分工 | 信任级别 |
|---|---|---|---|---|
| Brain | Sophia | 战略 | 理解任务、检索知识库与经验记忆、制定四阶段计划（SubmitPlan 原子登记） | 只做计划，无执行/状态权 |
| Orchestrator | Alex | 战术 | 唯一调度者：推进状态机、dispatch 各专家、审批、终态收尾 | 唯一状态写入者 |
| Recon | Ethan/Iris | 执行 | 网络被动侦察 / 归档文件 triage，收集端口/服务/指纹/攻击面 | 授权范围内侦察 |
| Analysis | Nora | 研判 | 漏洞研判、CVE 关联，输出结论与验证建议 | 纯推理，不执行命令 |
| Attack | Mike/Victor 等 | 执行 | 低影响验证与利用，内嵌 Analysis + cve_search + scoped_shell | 受审批闸门 + 范围约束 |
| Reserve | Ryan | 执行 | IDA/GDB 二进制逆向与动态分析 | MCP 受控执行 |
| ScopeAuditor | Grace | 审核 | 范围扩容独立审核（RFC1918 + 证据出现该 IP 才 APPROVED） | 只审范围，不决策 |
| Summary | Mia | 报告 | 终态后汇总全过程生成 WRITEUP 报告 | 只读会话与任务状态 |

### 2.3 为什么这样分工

1. **战略 / 战术 / 执行三层分离**：Brain 只制定计划（What）、Orchestrator 只调度（When/Who）、Recon/Attack 只执行（How），避免「既当裁判又当运动员」。
2. **权力分离（Separation of Duties）**：
   - 策划者（Brain）不执行，执行者（Attack）不能改状态；
   - 研判者（Analysis）不利用，利用者（Attack）的研判结论独立回流，不能自我背书；
   - 范围审核者（ScopeAuditor）独立于执行者，扩容必须经 `request_scope_expansion` 审核；
   - 只有 Orchestrator 可调用 `transition()`，状态推进从机制上不可越权。
3. **认知隔离防幻觉**：单一职责 = 提示词短 + 上下文纯净 + 事实不横向污染，这是七层防线第①层「角色约束」的架构基础（见第 5 章）。
4. **最小权限工具集**：AntSword MCP 只注册给 Attack、IDA/GDB 只注册给 Reserve、scoped_shell 按角色绑定——无关专家拿不到高危工具（AgentScope Toolkit 按 Agent 隔离）。
5. **人机协同锚点**：人工审批只面对 Orchestrator 一个「行动指挥」，三态决策（批准/补充侦察/拒绝）语义清晰，审批链路可审计。

### 2.4 模式特点

- **单调度者星型拓扑**：非竞标/网格模式，审计顺序确定、无状态竞态；Agent 间通过 dispatch 工具嵌套调用回流（`run_interruptible_agent_reply`），而非并发消息传递。
- **专家名册动态化**：Attack 人设按题型切换（`agent/experts.py::build_expert_assignments`），同一工具集适配不同攻击专家。
- **可插拔**：每个专家是独立工厂函数（`create_*_agent`），新增专家 = 一个新模块 + Orchestrator 上一个 `dispatch_*` 工具。
- **职责即安全边界**：信任级别与工具权限绑定，审计链的 `actor` 字段天然记录「谁在什么信任级别下做了什么」。

## 3. 为什么选择 AgentScope（与 LangChain 的对比）

### 3.1 直接对比

| 维度 | AgentScope 2.x（选用） | LangChain / LangGraph |
|---|---|---|
| Agent 抽象 | **Agent 是一等公民**：`Agent` 基类 + `ReActConfig` + `AgentState` 会话分区，多智能体协作（对话/辩论/并发/路由/Handoff）为原生工作流 | Agent 是组件拼装产物（`create_react_agent`、AgentExecutor），核心抽象是 Chain/Runnable/Graph；多智能体需在 LangGraph 中自行设计 StateGraph |
| 协作模式 | 原生支持 Conversation / Multi-Agent Debate / Concurrent / Routing / Handoffs 五种工作流 | LangGraph 图编排强在 DAG 流转，但「谁调度谁、消息如何回流」需开发者自建约定 |
| 状态与上下文 | `ContextConfig` 原生（`trigger_ratio`/`reserve_ratio`/`tool_result_limit`）触发式压缩；`DockerWorkspace.offload` 超长上下文溢出落盘；`AgentState` 按角色分区 | 无原生上下文压缩/offload；LangGraph 的 state 是图节点共享字典，需自行实现压缩策略与持久化 |
| 工具系统 | `FunctionTool`/`Toolkit`/`AllowedFunctionTool` 分层权限，`StrictJSONToolkit` 可在框架宽松 JSON 修复器**之前**插桩做严格校验；MCP、Agent Skill 原生支持 | Tool 抽象成熟，但工具调用参数的严格校验/审计插桩需依赖回调钩子自行实现 |
| 记忆 | Memory / Long-Term Memory 为原生概念，RAG 中间件（`rag.middleware`）、Plan 组件、Pipeline 均为内置 Feature | 记忆依赖外部包（如 langmem、mem0），RAG 与链编排绑定，需要组装 |
| 模型层 | 统一模型抽象：`OpenAIResponseModel` / `OpenAIChatModel` / `OpenAIEmbeddingModel`，对 Responses 协议与国产模型（Qwen/GLM/DeepSeek）支持完善 | 以 OpenAI SDK 风格为主，Responses 协议适配滞后，国产模型需自定义 |
| 调试与平台 | AgentScope Studio（`agentscope.app`）可视化多智能体运行、Tracing、Evaluation 内置 | LangSmith 为商业化服务，自托管复杂度高 |
| 维护与版本 | 阿里开源，面向多智能体应用持续演进；本项目 `requirements.txt` 钉版 `agentscope==2.0.6`，契约有自动化测试守护（`test_agentscope_260_contract.py`） | 生态大但版本碎片化、API 变动频繁（LangChain 0.1→0.3→1.0 迁移成本高），对国产模型支持依赖社区适配器 |
| 中文生态 | 官方文档/社区中文友好，教程覆盖本项目用到的全部能力面（Workflow/Agent/State/Memory/RAG/Plan/MCP/Studio） | 中文资料多为翻译/二创，深度技术参考较少 |

### 3.2 本项目中的实证落点

AgentScope 2.x 的能力在灵枢中几乎全部直接落地，无需自研替代品：

- `Agent` + `ReActConfig(max_iters)`：Orchestrator 的 ReAct 主循环与各专家 Agent（`agent/*.py` 工厂函数）。
- `ContextConfig` + `DockerWorkspace.offload`：`agent/context.py` 的压缩契约（0.75/0.12/4000）与角色会话分区 `{mission_id}-{role}`。
- `AgentState`：按角色隔离会话，`session_id` 确定性分区（`context.py:83`）。
- `Toolkit` / `AllowedFunctionTool`：`Tools/tooling.py:468` 统一注册，`StrictJSONToolkit` 在宽松 JSON 修复器前做严格 schema 校验。
- `RAG` 中间件与 `Plan` 组件：`Tools/KnowledgeBase.py`（检索工具注入 Brain/Attack）、`Tools/Plan.py`（计划工具化）。
- MCP 原生接入：AntSword / IDA / GDB 三个 MCP server（`agent/Attack.py`、`agent/Reserve.py`）。
- AgentScope Studio 平台化：`integrations/agentscope_service/` 把整个任务封装为单个 `LingshuMissionAgent`，事件翻译、角色历史镜像、审批透传，可直接挂入 AgentScope 账号面板。

### 3.3 为什么不是 LangChain

1. **多智能体协作语义不符**：灵枢的协作是「单调度者 + 若干被调度专家」的星型拓扑，强调**唯一状态写入者**与审计顺序确定性；LangChain 的 Chain 组合适合线性/分支流水线，LangGraph 虽可表达图，但「谁可以写状态」这类治理约束需要开发者自行在图上叠加，容易产生竞态。
2. **上下文治理缺位**：安全测试任务会产生大量工具输出（命令回显、反汇编、RAG 片段），AgentScope 的 ContextConfig + offload 是原生能力；LangChain 生态需引入额外记忆组件且压缩策略要自研，与「压缩后必须保留授权范围/审批状态/证据路径」这类领域硬要求（`SUMMARY_SCHEMA`）集成成本高。
3. **版本稳定性与国产模型**：LangChain API 高频变动对长期维护不利；本项目生产模型全部为国产（DeepSeek/Qwen/GLM），AgentScope 对 Responses 协议与这些模型的适配是开箱即用（`LLM/model.py` 四个 Provider 工厂全部基于 AgentScope 模型基类实现）。
4. **平台化诉求**：需要把系统嵌入 AgentScope 账号体系做可视化与审计，AgentScope Service 层直接复用；LangChain 生态无对等物。

> 结论：AgentScope 2.x 的「Agent 一等公民 + 原生上下文治理 + 国产模型支持 + 平台化」与本项目「多专家协作 + 状态机治理 + 防幻觉」的诉求精确匹配，LangChain 在可观测性生态上有优势，但核心诉求上不占优。

## 4. 为什么选择「知识库 + 长期记忆 + 短期记忆」三层记忆结构

### 4.1 问题：单层记忆为什么不够

LLM 的上下文窗口有限，而安全测试任务同时需要三类性质完全不同的信息：

| 信息 | 性质 | 生命周期 | 可信度 |
|---|---|---|---|
| 领域知识（CVE 情报、工具用法、题型方法论、渗透流程） | 公开事实，静态 | 长期（随知识库更新） | 高（来源可标注、可引用） |
| 历史经验（本系统此前成功/失败的攻击链） | 私有经验，动态积累 | 跨会话长期 | 中（仅供参考，须当前证据重验） |
| 会话状态（当前目标、证据、审批状态、计划项、Flag 提交） | 任务内事实 | 单次会话 | 最高（必须真实，是恢复与审计的根基） |

若混入单一向量库或单一上下文：① 历史经验可能被当成当前事实（经验幻觉）；② 会话证据可能被知识库噪音稀释；③ 任务恢复时无法区分「已知事实」与「模型臆测」。因此按**生命周期与可信度**切分为三层，各层独立存储、独立注入、独立治理。

### 4.2 三层各自的设计

**① 知识库层（RAG，静态事实）——回答「是什么」**

- 数据源：`.RAG/` 下按 00~11 分类的只读 Markdown（渗透测试、攻防对抗、安全运维、加固、应急、工具、合规、密码学、CTF、漏洞与框架知识、CVE 漏洞库），含 `long-memory/` 冷记忆卡片。
- 实现：`Tools/KnowledgeBase.py` — Qdrant 容器化向量索引 + 通用知识/冷经验双 collection + manifest 增量同步（sha256 比对）+ 检索注入；`.RAG/13-字典库` 保持文件精确查询。
- 使用方：Brain（RAG 中间件）与 Attack；API 提供检索/重建端点。
- 防污染：只读、`source` 来源标注、检索结果以「仅供参考」定位注入（Brain 提示词明确「不能替代真实侦察证据」）。

**② 长期经验记忆层（AgenticMemory）——回答「怎么打」**

- 数据源：任务终态（target/goal/plan/attack_chain/success/summary/flag）。
- 实现：`.LongMemory/agentic_memory.json`，热记忆上限 50 条 + `techniques{service→[{cve,ts,success}]}` 索引；`QueryMemory` 工具供 Orchestrator/Analysis 检索。
- 防污染（三层）：`_redact()` 脱敏（移除 URL/IP/域名/Flag/API-Key/口令）→ 只提取 CVE 等结构化标签 → 溢出时生成 `type: mission_lesson`、`sensitivity: sanitized` 的冷记忆卡片，强制声明「必须以当前授权目标的侦察证据重新验证」。
- 闭环：冷记忆卡片进入 `.RAG/long-memory/` 被 RAG 重新索引，实现「经验 → 知识」沉淀，同时保持脱敏边界。

**③ 短期会话记忆层（任务上下文）——回答「进行到哪」**

- 数据源：Agent 的 ReAct 上下文（消息、工具结果）+ 用户消息 + MissionState。
- 实现：AgentState 按 `{mission_id}-{role}` 分区；超长经 `ContextConfig` 触发压缩，`SUMMARY_SCHEMA` 强制保留 7 个恢复语义字段（`authorized_scope / approval_status / plan_items / evidence_paths / failed_fingerprints / flag_submission / next_action`）；PostgreSQL 持久化消息/流式快照，「再打一次」时从旧 MissionState 生成摘要注入。
- 防污染：压缩不丢恢复语义；工具输出超限落盘 artifacts 只回传尾部+sha256，避免上下文被巨型输出撑爆。

### 4.3 为什么不选「单一向量库存一切」或「全塞上下文」

- **单一向量库**：无法表达可信度分层——把「CVE 公开情报」与「本系统经验」与「本任务证据」同库检索，检索结果失去可信度锚点，正是幻觉放大源。且经验/证据需要脱敏与版本化治理，向量库难以表达。
- **全塞上下文**：上下文窗口与成本不可控（单会话实测均值 241 条消息、22494 次工具调用/439 会话），且「记忆 = 上下文」会让旧证据污染新判断；分层后每层按需注入（Brain 决策时检索知识库+经验，执行时引用会话证据），隔离与成本双赢。
- **不引入 mem0 等外部记忆框架**：避免多一层存储与脱敏边界；本项目记忆量级（≤50 条热经验 + Qdrant 知识索引）用 JSON + 脱敏归档即可，且归档逻辑是安全领域的强定制需求，自研可控。

## 5. 为什么采用「七层防线」幻觉抑制方案

### 5.1 威胁模型：安全测试场景的 7 类幻觉

| 类型 | 表现 | 危害 |
|---|---|---|
| 事实虚构 | 声称「端口开放/服务存在」但实际未验证 | 误导决策、报告造假 |
| 结果伪造 | 声称「攻击成功/拿到 Flag」但无真实输出 | 系统性欺骗（竞赛/审计场景致命） |
| 状态越权 | 跳过阶段、直接推进到 EXPLOITATION | 破坏流程治理 |
| 范围逃逸 | 命令打到非授权 IP | 越权测试，法律风险 |
| 计划造假 | 计划 completed 但无证据 | 过程不可信 |
| 上下文污染 | 旧会话/他角色信息混入当前判断 | 事实错乱 |
| 参数损坏 | 工具参数坏 JSON/越界值 | 工具误用、进程崩溃 |

### 5.2 设计原则

1. **机器可执行的硬约束优先于提示词软约束**：提示词会被模型无视，硬约束（状态机白名单、schema 校验、命令黑名单、哈希链）在任何提示词失效时仍然兜底。
2. **「LLM 声称」与「系统事实」分离**：成功判定不依赖模型自述——`submit_nss_flag` 以平台返回为准，计划 completed 以 evidence 字段为准，侦察结论以真实工具输出为准。
3. **按风险分级治理**：高风险动作（攻击执行、范围扩容）走人工审批；中风险（工具调用、状态迁移）走机器硬约束；低风险（文本生成）靠角色约束与审计留痕。

### 5.3 七层防线与选择理由

| 层 | 机制 | 代码落点 | 为什么这样设计 |
|---|---|---|---|
| ① 角色约束 | 单一职责 + 认知隔离（Brain 不侦察、Analysis 不执行命令、唯一 Orchestrator 写状态） | `agent/*.py` 系统提示词与工具集 | 降低单 Agent 认知负担，切断「横向事实污染」路径；这是成本最低的第一道软防线 |
| ② 状态机锁 | 合法迁移白名单 `_ALLOWED_TRANSITIONS`，非法迁移抛错；仅 Orchestrator 可 transition | `TaskState.py:214` | 把「流程治理」从提示词升级为机器强制——LLM 无论怎么生成都无法越权推进 |
| ③ 证据强制 | 计划 completed 必须 evidence；Flag 正确由平台返回判定 | `Tools/Plan.py`、`agent/Orchestrator.py::submit_nss_flag` | 直接封死「结果伪造」：无证据的完成声明被工具拒绝，成功口径客观化 |
| ④ 审批闸门 | 首次进入 EXPLOITATION 前人工批准；`dispatch_attack` 兜底；AntSword 可写工具逐次联动；非肯定答复视为拒绝 | `agent/Orchestrator.py:356`、`main.py::_ApprovalBroker`、`agent/Attack.py` | 攻击动作是系统最高风险面，机器硬约束不足以覆盖语义判断，必须人机双保险 |
| ⑤ 动作指纹与熔断 | 相同指纹动作去重、连续失败熔断并标记计划项 | `Tools/fingerprint.py` | 防「无意义重放」空转（LLM 常见死循环模式），保护资源与审计干净 |
| ⑥ 范围与参数硬约束 | 破坏性命令黑名单 + IP 白名单（ScopeRegistry）+ 网络工具必须显式含授权目标；`StrictJSONToolkit` 严格 schema，连续两次失败抛错安全收尾 | `Tools/tooling.py:530/71`、`Tools/ScopeRegistry.py` | 范围逃逸与参数损坏是「机器可判定」的两类风险，用确定性规则而非模型判断彻底封死 |
| ⑦ 审计链 + 上下文治理 + 确定性终态 | SHA-256 前向哈希链防篡改；`ContextConfig`+`SUMMARY_SCHEMA` 压缩保语义；超迭代/残缺工具调用/JSON 校验失败收敛 FAILED；终态确定性收尾残留计划项 | `TaskState.py:191`、`agent/context.py`、`main.py` 主循环 | 事后可验证（审计）+ 过程不退化（压缩）+ 结果不悬置（收敛）——形成闭环信任 |

### 5.4 为什么不采用其他方案

- **纯提示词约束**：已被证实不可靠（模型可忽略/曲解），只能作为第一道防线存在，不能作为唯一防线。
- **全量人工审批**：439 会话产生 22,494 次工具调用，全量人工审批成本不可行；只对高风险动作（攻击/范围扩容）审批，低风险靠硬约束，是人机成本的最优分配。
- **规则引擎完全替代 LLM**：安全测试的开放性（题型多样、目标异构）无法穷举规则；LLM 负责「开放决策」，硬约束负责「边界收敛」，二者互补而非替代。
- **事后人工复核**：可作为补充，但无法阻止越权执行已经发生；前置闸门（审批 + 硬约束）才是止损点。

### 5.5 效果验证

- 测试侧：`test_audit_chain.py`（篡改检测）、`test_fingerprint.py`（熔断）、`test_qwen_contract.py`（StrictJSON 闸门）、`test_scoped_shell_v2.py`（命令约束）、`test_workspace_*`（路径逃逸）等 24 个文件覆盖七层防线（详见《03-测试文档.md》）。
- 运行侧：审计链全程记录（含拒绝/熔断/审批事件）、计划 completed 均带 evidence、终态收敛率可由状态机保证。

## 6. 结论与演进方向

- **AgentScope 2.x** 是本项目多智能体架构的正确基座：Agent 一等公民、原生上下文治理、国产模型支持、平台化能力四者齐备，LangChain 在核心诉求上不构成替代。
- **三层记忆** 按生命周期与可信度切分，配合脱敏/来源标注/恢复语义保留，是「知识可用 + 经验可复用 + 状态可信」的最小充分结构；Qdrant collection 可随业务增长扩容，经验库也可迁至 SQL/对象存储。
- **七层防线** 以「硬约束优先、风险分级、声称与事实分离」为纲，把 LLM 的开放决策锁进可审计执行轨道；后续演进方向：审批超时自动拒绝、终态自动审计链校验、上下文压缩质量监控、GLM/slab 时代的运行统计归因。
